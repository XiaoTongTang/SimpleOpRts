# 04 · 改造步骤

## 0. 迁移总原则

> **先把行为做到一模一样，再往上加能力。**

这条不是洁癖。你现在有 5 个模板、3 种武器、4 个 HTML 页面在跑。如果一边改架构一边改数值，出问题时无法判断是「架构 bug」还是「平衡变了」。

所以 P0 / P1 的验收标准是**战斗结果与改造前完全一致**（差分测试，见第 6 节）。加能力从 P2 开始。

## 2. P0 · 几何层 + 空间索引 + 扫掠判定

### 2.1 新增 `js/spatial.js`

> **完整设计见 `05-空间索引层.md`。** 这里只列接口与本节要做的事。

```js
/** 均匀网格，用于圆 / 线段的范围查询 */
export class Grid {
  constructor(cols, rows, cell)   // 世界固定，格子数固定
  clear()                          // 复用桶数组，不重新分配
  insert(i, u)                     // 只存**下标**，不存对象
  queryCircle(x, y, r, out)        // 宽相位：盖住的格子里的全部单位
  querySegment(p0, p1, r, out)     // 沿线段走格子（DDA），不是包围盒
}

/** 扫掠圆判定，见 02-命中判定-扫掠圆.md */
export function sweptHit(p0, p1, r, c, R) { ... }
```

三条要点：

1. **只存下标**，位置永远只有一份（在 `units[i]` 上）
2. `querySegment` 必须**沿线段走格子**，不能用包围盒——否则长线段直接失去优势
3. `cell = 64`：主力查询半径 2~50，64 能让它们只压住 1~7 格

**范围**：本层只服务武器系统。群体层（L1）**不接入**，原因见 `05` 第 5.6 节。

### 2.5b 为什么 `rRep` 不能从 `hitR` 推导

`hitR` 是**战斗几何**（子弹能不能打中），`rRep` 是**编队密度**（单位之间挤多紧）。让后者从前者推导，等于让移动层依赖武器层——而移动层的数据契约里根本不该出现"能不能被打中"这种问题。

而且它会把一个真实的设计轴抹平：5 个模板的 `rRep` 是 17 / 30 / 34 / 22 / 32，分别对应蜂群的紧凑、游击的松散、要塞的等距阵列。统一成 `2.5 × 4.5 = 11.25` 之后，这些差异全部消失。

**如果将来真要让两者联动**，正确做法是加一个中立的物理尺寸字段，两层各自乘自己的系数：

```js
// templates.js —— 数据，不属于任何一层
{ key: "swarm", size: 4.5, p: { ... } }

// group-layer.js
const rRep = P.rRep ?? (size * 3.8);     // 移动层自己的系数

// weapon-system.js / defense-system.js
u.hitR = size * 1.0;                      // 战斗层自己的系数
```

两层都只依赖中立的 `size`，彼此之间没有引用。所以「大船 + 松散阵型」这种设计仍然写得出来。

**通用判据**（建议推广到后续所有改造）：

> 层与层只能通过**世界状态**互相影响（位置、血量、存活），不能通过**参数引用**互相影响。
>
> 密集阵型被 AoE 打得更惨 —— 涌现，允许。
> `rRep = f(hitR)` —— 架构泄漏，禁止。

## 4. P2 · `shieldMul`

从这里开始才真正加能力。

### 4.1 精确的伤害分配算法

语义：`shieldMul` = 这一发伤害中**有资格被护盾吸收**的比例。

```js
export function applyDamage(u, dmg, shieldMul = 1) {
  let absorbed = 0;
  if (u.shield > 0 && shieldMul > 0) {
    const eligible = dmg * shieldMul;              // 这一发最多能被盾吃多少
    absorbed = Math.min(u.shield, eligible);
    u.shield -= absorbed;
  }
  u.hp -= dmg - absorbed;                          // 没被吃掉的（含不可被吃的部分）进血
  return u.hp <= 0;
}
```

验算：

| `dmg` | `shieldMul` | 盾 | 吸掉 | 掉血 | 说明 |
|---|---|---|---|---|---|
| 20 | 1.0 | 50 | 20 | 0 | 全额被盾吃（= 现在的 `pierce:false`）|
| 20 | 0 | 50 | 0 | 20 | 完全穿透（= 现在的 `pierce:true`）|
| 100 | 0.4 | 10 | 10 | 90 | 盾只挡了 10，其余 90 全进血 |
| 100 | 0.4 | 1000 | 40 | 60 | 60% 直接绕过护盾 |

第 4 行是这个字段的核心价值：**它让「部分穿透」成为可表达的属性**，而不只是布尔开关。

### 4.2 兼容 shim（可选）

如果不想一次改完 4 个页面，可以先加一个过渡：

```js
export function applyDamage(u, dmg, shieldMul = 1) {
  if (typeof shieldMul === "boolean") shieldMul = shieldMul ? 0 : 1;  // 旧 pierce
  // ...
}
```

P1 之后就可以删掉这一行。

### 4.3 给三种武器设定初始值

| 武器 | `shieldMul` | 理由 |
|---|---|---|
| `ray` 贯穿射线 | 0 | 保持原设计（无视护盾） |
| `laser` 激光 | 1.0 | 保持原设计（全额被抵扣） |
| `torpedo` 鱼雷 | 1.0 | 保持原设计 |
| `railgun` 轨道炮 | 0.15 | 新武器，主打破盾 |
| `plasma` 等离子炮 | 1.0 | 新武器，被盾克制 |

**注意**：P2 如果只改 `ray` 为 0、其余为 1，行为仍然和 P1 一致。真正的变化要等你开始调中间值。

## 5. P3 · 朝向（纯视觉，可选）

```js
u.angle = Math.atan2(u.vy, u.vx);   // 速度极小时保持上一帧，避免抖动
```

- `drawUnitGlyph` 已经在用 `atan2(vy, vx)`，只是没存。存下来即可
- **抖动问题**：速度接近 0 时 `atan2` 会乱转。加死区：`if (sp < 3) keep old angle`
- **没有炮口偏移**：`mount` 已经砍掉，武器一律从单位中心、朝任意方向开火

**优先级说明**：砍掉 `mount` 之后，朝向不再影响任何判定，原先「前置量」的收益随之消失（提前量是弹丸自己算的，和舰船朝向无关）。所以它从玩法项降级为纯表现项，可以最后做，也可以不做。

> **已删除：护盾弧（原 P3）**。原设计是给每个单位一个有朝向的护盾弧，让「包抄」有战术意义。
> 删除理由：它依赖 `facing`，而砍掉 `mount` 之后朝向只是装饰；更根本的是，
> 弧盾 = 把「护盾」从数值变成几何，而几何护盾更自然的形态是**范围力场**（一个罩子罩住一群人），
> 不是每人一片扇形。真要做护盾几何，应该从「场」这个对象入手，而不是从单位入手。

## 6. 验收：差分测试

这是整份文档里最实用的一节。

### 做法

1. 改造**前**，在 `plinko-battle.html` 里固定 `Math.random` 的种子（项目里已经有 seeded xorshift 的实现，见 `poster.html`）。
2. 跑 900 帧，每 30 帧记录一次指纹：
   ```js
   const sig = units
     .map(u => `${u.squad}:${u.hp.toFixed(2)}:${u.shield.toFixed(2)}:${u.x.toFixed(1)}:${u.y.toFixed(1)}`)
     .sort().join("|");
   ```
3. 存成 `baseline.json`。
4. 改造后跑同样流程，逐帧 diff。

### 允许的差异

| 来源 | 幅度 | 处理 |
|---|---|---|
| 矩形 → 胶囊的末端圆角 | ±14px 判定边缘 | 允许，但要在日志里标注 |
| 网格导致的敌人选择顺序变化 | 可能改变整场战斗 | **不允许**，必须修 |
| 浮点累积顺序变化 | 1e-6 量级 | 允许 |

**「网格导致的选择顺序变化」是最容易踩的坑**：现在 `stepWeapons` 是「遍历单位数组取最近」，换成网格之后，如果多个目标距离相同（或 `rRep` 内的并列），选中的那个可能不同，进而导致整场战斗蝴蝶效应。

修法：距离相同时按 `u.index`（稳定的创建序号）tiebreak，不要依赖数组顺序。

## 7. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 网格 tiebreak 引入不确定性 | 战斗不可复现 | 用稳定 id 排序（见 6） |
| `querySegment` 漏格 | 高速弹穿过去不判定 | 采样步长取 `cell/2`，并对半径外扩一格 |
| 弹丸每帧分配对象 | GC 抖动 | `p0/p1` 用复用对象池，或内联标量 |
| `rRep` 被顺手改动 | 阵型变松/变紧，整个手感都变 | **不动 `rRep`**。见 2.5b：它属于移动层，和本组改造无关 |
| 多挂点导致火力翻倍 | 平衡崩 | 多挂点放到 `fire.energy` 总预算之后再做 |

## 8. 一句话总结

**P0 加的是"单位有体积"，P1 加的是"武器是数据"。**
这两件做完，加一把机枪是加 12 行 JSON；不做，加一把机枪是改 3 个文件加回归 4 个页面。
