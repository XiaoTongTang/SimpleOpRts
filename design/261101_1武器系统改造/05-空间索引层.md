# 05 · 空间索引层

## 0. 文档定位与范围决策

本篇描述**空间索引（均匀网格）**这一层：它做什么、里面放什么、怎么被调用、为什么只对一部分查询有效。

### 已定决策

> **D11 · 空间索引只服务武器系统。群体层（L1）完全不接入。**

这一条把范围收得很窄，是有意的：

| 层 | 接不接 | 为什么 |
|---|---|---|
| 武器 · 弹丸命中 | ✅ 接 | 半径 2~14，每帧每弹一次，最高频 |
| 武器 · 爆炸 | ✅ 接 | 半径 22~50，每次爆炸一次 |
| 武器 · 找目标 | ⚠️ 接口留着，暂不接 | 半径 = 射程 250~380，网格只值 2~3 倍，且频率低（见 §5） |
| 群体层 L1 | ❌ 不接 | 半径 17~350，大头（寻敌 350）网格完全不值；真正该做的是小队聚合，那是另一件事 |
| 防御 · 充能器 | ❌ 不接 | 同上，量小，先留着 |
| 渲染 | ❌ 不接 | 400 单位全画，不需要裁剪 |

### 这个决策带来的一个好处

群体层不接索引，**帧内顺序问题自动消失**：

如果 L1 也要查网格，就必须「先建索引 → 再算力 → 再积分」两段式，否则前面的单位读到新位置、后面的读到旧位置，力的方向不对称。

现在 L1 保持原样（算力与积分同一个循环），索引只在**移动全部结束之后**建一次。顺序变成一条直线，没有快照问题。

> **附带记录（不属于本篇范围）**：L1 现在那个「算力和积分同循环」的写法有一个独立的问题——单位在数组里的顺序会影响结果，而死亡会 `splice` 重排数组。这不是索引层造成的，也不会被索引层修掉。要修是另一个改动（拆成两段），单独评估。

## 1. 它是什么：横向服务，不是一层

L1 / L2 / L3 是**有游戏语义**的层：它们知道阵营、知道谁怕谁、知道编队。
索引层**什么都不知道**——它不认识敌人，不认识伤害，不认识小队。

一句话契约：

> **「这个形状附近有哪些单位？」——只回答这个，不回答别的。**

所以它在架构图里不该和 L1/L2/L3 并列，而在它们下面：

```
        ┌──────── L3 指挥 ────────┐
        ├──────── L2 小队 ────────┤
        ├──────── L1 群体 ────────┤   ← 不接索引
        ├──── 武器 / 防御系统 ─────┤   ← 只有武器接
        └════════ 空间索引 ════════┘   ← 横向服务，无游戏语义
```

### 用平铺数组，不用哈希表

严格说你要的是**均匀网格**，不是"空间哈希"。

哈希表存在的理由是「世界无边界或极大，坐标要压成键」。你的战场是一块固定矩形，格子下标直接算出来：

```js
const idx = gy * cols + gx;     // 整数，O(1)
```

比 `Map.set(`${gx},${gy}`, ...)` 快一个数量级，而且不产生字符串垃圾。

## 2. 里面放什么：区分「被查的」和「发问的」

| 角色 | 是谁 | 进不进索引 |
|---|---|---|
| **被查的** | 单位 | ✅ 进。因为**别人要找它**：弹丸找命中、爆炸找波及 |
| **发问的** | 弹丸 | ❌ 不进。它每帧问"我路上有谁"——它是问的人，没人在找它 |

**索引存在的理由是"我要在一大堆东西里快速定位"。** 弹丸从来只被当作寻找者，不被当作目标。

### 唯一的例外：点防 / 拦截

如果以后做"我这个单位周围 120px 有没有敌方弹丸"，那**弹丸变成了被查的**，需要第二个网格：

```js
const gridUnits = new Grid(...);   // 单位。永远需要
const gridProj  = new Grid(...);   // 弹丸。只在有点防时需要
```

规则：**有几种"需要被找到的东西"，就建几个网格。** 不要做一个混装所有东西的"万能网格"——混装会让查询结果需要类型过滤，反而更慢。

### 它返回的是「候选集」，不是「答案」

这点最容易误解：

```js
const cands = grid.queryCircle(x, y, 50);
//  ← 这是"半径 50 盖住的那些格子里，全部单位的下标"
//     里面会有几个其实在 50 之外（因为它们住在边界格子里）

for (const i of cands) {
  const o = units[i];
  if (dist2(x, y, o.x, o.y) <= 2500) { /* 真的在范围内 */ }
}
```

这叫 **宽相位（broad phase）+ 窄相位（narrow phase）**：

- 网格负责「把 400 个里可疑的 10 个挑出来」—— 快，但不精确
- 精确判定负责「这 10 个里哪几个真的在里面」—— 只有 10 个，慢得起

**网格永远不回答"是否命中"，只回答"值得检查谁"。** `sweptHit` 就是窄相位。

## 3. 契约

```js
export class Grid {
  constructor(cols, rows, cell)   // 世界固定，格子数固定
  clear()                          // 复用桶数组，不重新分配
  insert(i, u)                     // 只存**下标**，不存对象
  queryCircle(x, y, r, out)        // → out 里追加下标
  querySegment(p0, p1, r, out)     // → out 里追加下标
}
```

### 铁律：只存下标，位置永远只有一份

格子里放的是 `units[i]` 的**索引**，不是 `{x, y}` 的副本。

如果存副本，你就有了两份真相。单位一动，两边不同步，症状是"明明在这儿却查不到"，而且极难 debug。

### 参数 `out` 由调用方提供

不要每次返回新数组——那会每秒产生几十万个短命数组。调用方复用一个 `out` 数组：

```js
const scratch = [];
// 查询时
scratch.length = 0;
grid.queryCircle(x, y, r, scratch);
```

## 4. 帧内位置

因为群体层不接索引，顺序非常干净：

```
① L1 / L2 更新位置（原样，不变）
② 建索引：grid.clear() + 把所有单位 insert 一次
③ 武器结算：弹丸推进 → 查询 → 命中 → 爆炸
④ 防御结算（不查索引）
```

关键只有一条：**② 必须在①之后、③之前。**

因为②读的是最终位置；③只读不写位置（弹丸位置是弹丸自己的，不影响单位索引）。所以一次建表、整帧有效，不需要重建。

```js
// 主循环
stepUnits(units, squads, G, dt, W, H);   // ① 位置变了

grid.clear();
for (let i = 0; i < units.length; i++) grid.insert(i);   // ② 重建

stepWeapons(units, squads, projectiles, grid, dt, hits, now, fx);  // ③
stepChargers(units, squads, G, dt, fx);                 // ④ 不查
```

## 5. 为什么武器层的几种查询收益差这么多

### 5.1 先把地图切成格子

```
战场 1600 × 600 px，格长 64 px
列数 = 1600/64 = 25
行数 =  600/64 ≈ 10
总格子 = 250
每格单位数 = 400 / 250 = 1.6
```

### 5.2 推理

一次查询的工作量 ≈ **被形状盖住的格子里的单位数**。
暴力扫描的工作量 = **全部 400**。

```
① 每边格子数 k = 2r/cell + 1        ← +1 是因为形状压到格子边界会多压一排
② 盖住格子数   = k²
③ 候选单位数   = k² × 1.6
④ 收益         = 400 / (k² × 1.6) = 250 / k²
```

`400` 在分子分母里都出现，约掉了。所以：

> **收益 = 总格子数 / 盖住的格子数。**

- 最好情况（`r → 0`）：只盖 1 格 → 收益 ≈ **250**，正好等于格子总数
- 最坏情况（盖满全图）：收益 = **1**，等于没做

### 5.3 圆形查询：半径平方决定一切

| 查询半径 | 直径 | k | 盖住格子 | 候选 | 收益 |
|---|---|---|---|---|---|
| 2 | 4 | 1.06 | 1.1 | 1.8 | **221×** |
| 14 | 28 | 1.44 | 2.1 | 3.3 | **121×** |
| 34 | 68 | 2.06 | 4.3 | 6.8 | **59×** |
| 50 | 100 | 2.56 | 6.6 | 10.5 | **38×** |
| 100 | 200 | 4.13 | 17 | 27 | 15× |
| 200 | 400 | 7.25 | 53 | 84 | 4.8× |
| 350 | 700 | 11.9 | 142 | 227 | 1.8× |

半径翻倍 → 每边格子翻倍 → **格子数翻四倍** → 收益除以四。这是二维空间的几何必然，不是实现问题。

### 5.4 线段查询：只有一维，便宜得多

`querySegment` **不能**实现成"取线段的包围盒再查圆"，那会退化成 `(长 + 2r)²` 的大方块。

正确做法是**沿线段走格子（DDA）**——只碰线扫过的那一串格子：

```
线段长 250，半径 14，格长 64
盖住格子 ≈ (250/64 + 2×14/64 + 2) × (2×14/64 + 1)
         ≈ (3.9 + 0.44 + 2) × 1.44
         ≈ 9 格        （而不是包围盒的 78 格）
```

**一条又长又细的线，只压住沿线的几格。** 这就是为什么 hitscan 的长线段也能用网格。

### 5.5 武器层实际查询（含频率）

| 查询 | 形状 | 尺寸 | 每帧次数 | 盖住格子 | 暴力/次 | 收益 |
|---|---|---|---|---|---|---|
| **弹丸命中** | 线段 | 15 × r2~5 | **~400** | ~2.4 | 400 | **~100×** |
| **hitscan 命中** | 线段 | 250~380 × r2~14 | ~3 | ~9 | 400 | **~28×** |
| **爆炸** | 圆 | r22~50 | ~0.5 | ~6.6 | 400 | **~38×** |
| 找目标 | 圆 | r = 射程 250~380 | ~3 | 78~165 | 400 | **1.5~3×** |

**结论很清楚：接前两个，第三个留着不用。**

前三行的「每帧次数」差着两个数量级——弹丸命中每帧 400 次，找目标每帧 3 次。即使找目标完全暴力（400 次距离计算 × 3 = 1200 次/帧），总成本也不到弹丸命中的千分之一。

**要不要用网格，取决于「半径」与「频率」的乘积，不是半径单独。**

### 5.6 所以为什么群体层不接

L1 的查询半径是 17~350，且**最频繁的那几个恰好落在中段**：

| L1 查询 | 半径 | 收益 |
|---|---|---|
| 分离 `rRep` | 17~34 | 30~59× ✅ |
| 威胁 `r4` | 50~200 | 5~38× ⚠️ |
| 社交 `rAtt` | 86~200 | 5~15× ⚠️ |
| 寻敌 `r5` | 270~350 | 1.5~2× ❌ |

分离能赚，但**一个查询赚不代表整层该接**——接进来就要付出：建索引时机、两段式积分、力的对称性、数组顺序依赖，一整套重构。

而 L1 真正的性能问题不在"查询慢"，在**算法本身是 O(n²)**：

> 对齐（alignment）和凝聚（cohesion）算的是"同小队邻居的平均速度"和"质心"。
> 而一个 12 人小队的 12 个成员算出来的这两个量**几乎完全一样**。
>
> 那就没必要每个单位各扫一遍全场——**提到小队层算一次就够，O(n)。**

这个改动的收益（400² → 400）比接网格（160k → 160k/50）大得多，而且不需要索引。

**所以正确的顺序是：先做小队聚合，再看还需不需要索引。** 现在结论是：不需要。

## 6. 容量与格子

### 6.1 为什么 `cell = 64`

判据是「格长 ≈ 最高频查询的半径」，让主力查询只压住 1~2 格。

你的频率头部集中在 **2~50**：
- 弹丸 `contactR` 2~14（每帧 400 次，绝对主力）
- 爆炸 `blastR` 22~50

`cell = 64` 时：
- `r = 2` → 1.1 格（已经贴着理论下限，再切细没有收益）
- `r = 50` → 6.6 格（仍很划算）

**不要为了照顾 350 的查询把格长调到 256**——那会让 `r = 2` 从 1.1 格变成 2.2 格，主力查询直接慢一倍。

### 6.2 尺寸计算

```js
const CELL = 64;
const cols = Math.ceil(W / CELL);
const rows = Math.ceil(H / CELL);
const nCells = cols * rows;         // 1600×600 → 25 × 10 = 250
```

注意 `W / H` 会随窗口变化。窗口变化时**重建整个 Grid**（很少发生，无所谓）。

### 6.3 复用桶，避免 GC

```js
this.buckets = new Array(nCells);
for (let i = 0; i < nCells; i++) this.buckets[i] = [];

clear() {
  for (let i = 0; i < this.nCells; i++) {
    this.buckets[i].length = 0;      // ← 只清长度，不 new 数组
  }
}
```

如果每帧 `new Array(250)`，就是每秒 15,000 个数组 → GC 抖动 → 帧时间不稳。

## 7. 实现

```js
export class Grid {
  constructor(cols, rows, cell) {
    this.cols = cols;
    this.rows = rows;
    this.cell = cell;
    this.nCells = cols * rows;
    this.buckets = new Array(this.nCells);
    for (let i = 0; i < this.nCells; i++) this.buckets[i] = [];
    this._stamp = new Int32Array(this.nCells);   // querySegment 去重用
    this._sid = 0;
  }

  clear() {
    for (let i = 0; i < this.nCells; i++) this.buckets[i].length = 0;
  }

  insert(i, u) {
    const gx = Math.min(this.cols - 1, Math.max(0, (u.x / this.cell) | 0));
    const gy = Math.min(this.rows - 1, Math.max(0, (u.y / this.cell) | 0));
    this.buckets[gy * this.cols + gx].push(i);
  }

  /** 圆形查询（宽相位） */
  queryCircle(x, y, r, out) {
    const c = this.cell, cs = this.cols, rs = this.rows;
    const x0 = Math.max(0, ((x - r) / c) | 0);
    const x1 = Math.min(cs - 1, ((x + r) / c) | 0);
    const y0 = Math.max(0, ((y - r) / c) | 0);
    const y1 = Math.min(rs - 1, ((y + r) / c) | 0);
    for (let gy = y0; gy <= y1; gy++) {
      const row = gy * cs;
      for (let gx = x0; gx <= x1; gx++) {
        const b = this.buckets[row + gx];
        for (let k = 0; k < b.length; k++) out.push(b[k]);
      }
    }
    return out;
  }

  /** 线段查询（沿线段走格子，不是包围盒） */
  querySegment(p0, p1, r, out) {
    const c = this.cell, cs = this.cols, rs = this.rows;
    const rad = Math.max(0, Math.ceil(r / c));        // 半径占几格
    const dx = p1.x - p0.x, dy = p1.y - p0.y;
    const len = Math.hypot(dx, dy);

    this._sid++;
    const stamp = this._stamp, sid = this._sid;

    // 按半格步长采样，保证不跳格
    const steps = Math.max(1, Math.ceil(len / (c * 0.5)));
    for (let s = 0; s <= steps; s++) {
      const t = s / steps;
      const gx = Math.min(cs - 1, Math.max(0, ((p0.x + dx * t) / c) | 0));
      const gy = Math.min(rs - 1, Math.max(0, ((p0.y + dy * t) / c) | 0));

      for (let oy = -rad; oy <= rad; oy++) {
        const ny = gy + oy;
        if (ny < 0 || ny >= rs) continue;
        const row = ny * cs;
        for (let ox = -rad; ox <= rad; ox++) {
          const nx = gx + ox;
          if (nx < 0 || nx >= cs) continue;
          const idx = row + nx;
          if (stamp[idx] === sid) continue;           // 这一格本帧已收过
          stamp[idx] = sid;
          const b = this.buckets[idx];
          for (let k = 0; k < b.length; k++) out.push(b[k]);
        }
      }
    }
    return out;
  }
}
```

## 8. 确定性与正确性

**单格归属，天然无重复**
每个单位只放进**一个**格子（按自身位置算）。所以 `queryCircle` 遍历多格时不会返回重复下标。

**`querySegment` 要去重**
采样步长会导致同一格被多次采到。用 `stamp` 数组（`Int32Array`，存"上一次查询编号"）去重，零分配。

**遍历顺序固定**
格子上标按 `gy * cols + gx`，行主序。不要用 `Object.keys` 或 `Map` 迭代——顺序取决于插入历史。

**并列时用 id 破平**
如果某处逻辑是"取最近的敌人，同距取第一个"，那个"第一个"会随数组顺序变。用 `u.id`（稳定创建序号）破平，不要依赖 `units[]` 的下标。

**越界 clamp，不抛错**
单位可能被力推到边界外一瞬。`insert` 和查询都 `clamp` 索引，静默处理。

**格长变化要重建**
窗口大小变了 → `cols/rows` 变 → 必须重建 Grid。不要在旧的桶数组上继续用。

## 9. 验收

### 9.1 判定必须与暴力扫描逐位一致（最重要）

网格是**优化**，不是**规则**。它不该改变任何一个命中结果。

做法：加一个开关，跑两种实现对比：

```js
if (DEBUG_BRUTE) {
  cands.length = 0;
  for (let j = 0; j < units.length; j++) cands.push(j);   // 暴力：全部候选
} else {
  grid.querySegment(...);
}
```

然后沿用 `04` 的差分测试：固定种子，跑 900 帧，逐帧比对每个单位的 `hp / shield / x / y`。

**期望：完全一致。** 任何一帧有差异，都是网格漏格或重复计数。

### 9.2 漏格测试

写一个单向断言：暴力全选的结果里，凡是 `sweptHit` 命中的单位，**必须**也在网格给的候选集里。

```js
// 网格候选必须 ⊇ 真正命中的集合
for (const o of allUnits) {
  if (sweptHit(p0, p1, r, o, o.hitR) >= 0) {
    assert(cands.includes(idxOf(o)), "漏格！");
  }
}
```

这条比性能测试重要得多——**漏格是静默的 bug，只表现为"偶尔打不中"**，玩家会以为是散布。

### 9.3 性能对比

关掉网格跑 1000 帧记时间，开网格再跑一次。期望：

- 弹丸命中查询数量级下降（每帧 ~400 次查询，候选从 400 → 2~5）
- 整帧时间下降，但**不要指望翻倍**——渲染、力场、伤害结算都没变

如果开了网格反而更慢，先确认两件事：① 有没有在每帧 `new Array`；② 有没有在对 `r ≥ 128` 的查询用它。

## 10. 反模式

| 反模式 | 后果 |
|---|---|
| 格子里存 `{x, y}` 副本 | 两份真相，位置不同步 |
| 边移动边查询 | 前后单位看到不同快照（本层目前不会发生，因为 L1 不接） |
| 用 `Map<string, []>` | 字符串键拼接，比整数下标慢一个数量级 |
| 每帧 `new Array` 重建桶 | GC 抖动，帧时间不稳 |
| `querySegment` 用包围盒 | 退化成大方块，长线段直接失去优势 |
| 拿它做碰撞解算 / 连续碰撞 | 它只是索引，不是物理引擎 |
| 给渲染做裁剪 | 400 单位没必要，纯增复杂度 |
| 返回新数组 | 每秒几十万个短命数组 |

## 11. 未接入的部分（将来）

**群体层**
要接的话前提是**先做小队聚合**：把对齐、凝聚提到小队层算（O(n)），只留分离和威胁走局部查询。做完之后如果还是慢，再接网格——而且只接分离（r 17~34，收益 30~59×），不接寻敌（r 350，收益 1.8×）。

**充能器**
`stepChargers` 是「每个充能器 × 全场单位」的扫描，形状和武器找目标一样。量小（充能器只有 5~10 个），先不动。

**点防 / 弹丸拦截**
需要**第二个网格**装弹丸。别复用单位的网格——两类东西生命周期不同（弹丸每帧增删，单位只在死亡时删），混在一起每次重建都要全量插，不划算。

**多尺寸网格**
如果将来两级查询（r≈4 和 r≈300）都变得频繁，可以建两个不同格长的网格（32 / 160）。**先别做**，等 profiling 说话。
