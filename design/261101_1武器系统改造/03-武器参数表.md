# 03 · 武器参数表

## 1. 设计原则

**① 正交**：一个字段只描述一件事。「命中」和「爆炸」是两个字段，不是同一个半径的两种用法。

**② 可推导**：能从别的字段算出来的，就不单独存。`range` 由 `speed × lifetime` 导出，避免出现「射程 380、弹速 210、寿命 5 秒」这种自相矛盾的配置。

**③ 无枚举分支**：`delivery` 只有两个值，且两个值的代码路径**共享同一条扫掠判定**，没有第三个 `switch` 分支。

**④ 数字即设计**：所有字段都能用一句话向玩家解释（见第 6 节的公示卡）。

## 2. 字段定义

```js
{
  id: "autocannon",
  name: "自动机炮",

  fire: {
    cd: 0.12,                // 两轮齐射的间隔（秒）
    burst: 3,                // 一轮打几发
    burstDelay: 0.05,        // 一轮内的间隔
    fan: 4,                  // 扇形总宽度（度）：确定性铺开，不是随机散布
    chargeup: 0,             // 蓄力时间（秒），> 0 时开火前要先蓄满
    energy: 1.2,             // 每发的能量消耗
  },

  delivery: "projectile",    // "projectile" | "hitscan"

  proj: {
    speed: 900,              // px/s。hitscan 时只用它算扫掠长度
    lifetime: 0.6,           // 秒。射程 = speed × lifetime
    contactR: 2,             // 弹丸命中半径（小 = 难打中）
    accel: 0,                // px/s²，可为负（减速弹）
    pierce: 0,               // 可额外穿透几个目标；-1 = 无限
    homing: null,            // null | { turnRate: 2.6, seekR: 420 }
  },

  impact: {
    dmg: 6,
    blastR: 0,               // 命中后的范围伤害半径；0 = 纯单体
    blastDmg: 0,
    shieldMul: 0.6,          // 可被护盾吸收的比例：1 全吸收 / 0 完全穿透
    status: null,            // null | { id: "burn", dur: 3 }
  },

  fx: { muzzle: "spark", trail: null, hit: "impact_small" },
}
```

### 几个容易搞错的点

**为什么没有 `mount`（炮塔 / 射界 / 转向）**

设计上已经删掉。理由：

- 大群 RTS 里，玩家看的是「这一坨会不会打赢」，不是「这艘船炮口朝哪」。**朝向的战术收益无法被感知。**
- 有射界就必须有转向，有转向就必须有「转身时不能开火」的窗口——在 400 单位同屏的情况下，这只会制造随机的手感波动，不制造决策。
- 省掉的复杂度不小：`arc` 判定、`turn` 积分、目标在背后时的处理、多挂点时的射界交叠。

**代价（要认）**：武器一律从单位**中心**、朝**任意方向**开火。视觉上单位仍有朝向（`u.angle`），但它纯粹是装饰，不影响任何判定。由此 P3（朝向与炮口偏移）从「玩法」降级为「表现」。

**`fan` 是确定性扇形，不是随机散布**

这一条是刻意的：**武器表里不出现任何随机数。**

```js
// 一轮 burst 发，均匀铺开在 fan 度内，第 i 发的偏角：
const n = fire.burst;
const a = n === 1 ? 0 : (i / (n - 1) - 0.5) * (fire.fan * Math.PI / 180);
```

`burst = 3, fan = 6` → 三发分别偏 `-3° / 0° / +3°`，每轮**完全一样**。

为什么不用随机：

| 随机散布的问题 | 后果 |
|---|---|
| 它是隐藏的 DPS 倍率 | 玩家无法把「+2° 散布」翻译成任何后果 |
| 它让 DPM 不可解析 | 违反 `README` 里的 D6「成本必须可算」 |
| 它让差分测试失效 | P0/P1 要靠逐帧对比验证行为不变，随机数一进来就没法比 |

**那"打不准"怎么办？** 不需要靠散射。它由两件事自然产生：

1. **飞行时间 + 目标机动**。弹速 900 打 500px，飞 0.55s；目标侧移 96px/s → 落点偏 53px，远超 `contactR + hitR ≈ 6.5`。
2. **`contactR` 的大小**。它决定"擦边算不算中"。

所以「机枪打小快目标容易脱靶」是**涌现**的，不需要额外的精度参数。反过来说，**hitscan 武器永远是 100% 命中**——因为光速到达，没有飞行时间，这在物理上也对。

需要"齐射铺开"的武器（霰弹、防空炮）用 `fan` + 大 `burst` 表达，例如 `burst: 8, fan: 16`。

**`shieldMul` 的语义**

是「这一发伤害中**可用于被护盾吸收**的比例」，不是伤害倍率。

| 值 | 含义 | 对应现有的 |
|---|---|---|
| `1.0` | 全额先扣盾，溢出到血 | `pierceShield: false` |
| `0` | 完全不看护盾，直伤血量 | `pierceShield: true` |
| `0.4` | 40% 扣盾，60% 直伤 | 新增能力 |

精确的分配算法见 `04-改造步骤.md` 第 4.1 节（`defense-system.js` 只改这一个函数）。

**`contactR` 与视觉的绑定**
弹丸画多大，`contactR` 就是多大。**判定与渲染必须用同一个数**，否则玩家会觉得「明明擦过去了却算命中」。

**`pierce` 计数**
`0` = 撞到第一个目标就消失；`3` = 可以穿过 3 个额外目标（共 4 个）；`-1` = 无限贯穿。

## 3. 现有三种武器如何映射

保持**行为完全一致**（作为 P1 的回归基准）：

| 字段 | `ray` 贯穿射线 | `laser` 激光 | `torpedo` 鱼雷 |
|---|---|---|---|
| `delivery` | `hitscan` | `hitscan` | `projectile` |
| `proj.speed` | 2000 | 2000 | 210 |
| `proj.lifetime` | 0.125 | 0.15 | 1.81 |
| **推导 `range`** | **250** ✅ | **300** ✅ | **380** ✅ |
| `proj.contactR` | **14**（原 `width: 28` 的一半） | 2 | 5 |
| `proj.pierce` | `-1`（原实现贯穿所有） | 0 | 0 |
| `impact.dmg` | 20 | 24 | 18 |
| `impact.blastR` | 0 | 0 | 50 |
| `impact.blastDmg` | — | — | 18（同主伤害） |
| `impact.shieldMul` | **0** | 1.0 | 1.0 |
| `fire.cd` | 2.6 | 2.0 | 6.0 |

**关键验证**：`ray` 原来是 `shape: "rect", width: 28, range: 250`。
换成 `hitscan` + `contactR: 14` 后，扫掠出的是一个 **胶囊**（长 250 + 两端半圆），
而原来是一个**矩形**。两者在 250 的长轴上完全一致，只在末端 14px 的方角/圆角上有差别——比原来更正确，视觉上看不出来。

三种武器（三个 `switch` 分支）→ **一次扫掠 + 三组参数**。

## 4. 新武器样例

| id           | 名称   | 投递      | 速度   | 寿命   | 射程   | 命中R | 伤害  | cd   | 盾比   | 特性                     |
| ------------ | ---- | ------- | ---- | ---- | ---- | --- | --- | ---- | ---- | ---------------------- |
| `autocannon` | 自动机炮 | proj    | 900  | 0.6  | 540  | 2   | 6   | 0.12 | 0.6  | burst 3                |
| `railgun`    | 轨道炮  | hitscan | 3000 | 0.25 | 750  | 3   | 90  | 4.5  | 0.15 | pierce 3, chargeup 1.2 |
| `missile`    | 导弹   | proj    | 260  | 4.0  | 1040 | 4   | 30  | 1.6  | 0.8  | homing, blastR 24      |
| `plasma`     | 等离子炮 | proj    | 420  | 1.4  | 588  | 8   | 45  | 2.8  | 1.0  | blastR 36              |
| `flak`       | 防空炮  | proj    | 700  | 0.45 | 315  | 3   | 8   | 0.35 | 0.9  | blastR 22, burst 8, fan 16 |

注意这张表里的**射程差异是怎么来的**：全部由 `speed × lifetime` 导出，没有一个独立的 `range` 字段。

- `railgun`：750 射程，但 `chargeup 1.2` + `cd 4.5` → 慢、重、必须预判
- `autocannon`：540 射程，`contactR: 2` → 打小目标容易脱靶
- `missile`：1040 射程，飞 4 秒，**目标有 4 秒时间跑掉或拦截**

这就是 D5 那条决策的价值：**同样的射程，可以用不同的弹速做出完全不同的武器性格。**

## 5. 推导量

这些不进配置表，由代码算：

```js
range      = proj.speed * proj.lifetime
cycleTime  = fire.cd                                  // 两轮之间的间隔
burstTime  = fire.burst * fire.burstDelay
单轮伤害    = fire.burst * impact.dmg
DPS        = 单轮伤害 / (cycleTime + burstTime)
能量/秒     = fire.burst * fire.energy / (cycleTime + burstTime)
```

命中期望要乘一个**命中率**，而命中率现在**不是常数**了——它取决于目标大小、弹速、机动。这正是这次改造带来的新维度，也是 UI 需要显示的东西（见第 6 节）。

## 6. 公示卡（给玩家的白话摘要）

每个字段都要能翻译成一句话，否则就是隐藏倍率：

```
【自动机炮】
  每 0.17 秒一轮，一轮 3 发
  每发 6 伤害，射程 540
  弹速快，但弹体很小 —— 打小目标容易擦过
  护盾能吃住 60%
```

```
【轨道炮】
  蓄力 1.2 秒，之后每 4.5 秒一发
  一发 90 伤害，能连穿 4 个目标
  射程 750，无视 85% 的护盾
  —— 打成一列的时候最划算
```

第三行的「弹体很小 / 能连穿 4 个」就是 `contactR` 和 `pierce` 的翻译。
**不要给玩家看数字，给玩家看后果。**

## 7. 与移动系统的关系：轨迹修饰就是"力"

如果之后要加「追踪 / 弹跳 / 规避」这类轨迹修饰，它们**不改这张表的任何字段**，而是在弹丸上挂力：

```js
// 弹丸每帧：先算轨迹，再判定命中
for (const m of p.mods) { const f = m.force(p); ax += f.x; ay += f.y; }
p.vx += ax * dt;  p.vy += ay * dt;
const p0 = { x: p.x, y: p.y };
p.x += p.vx * dt; p.y += p.vy * dt;
const p1 = { x: p.x, y: p.y };
// 然后 sweptHit(p0, p1, ...)
```

| 轨迹修饰 | 力（复用 `group-layer.js` 的核函数） |
| ---- | --------------------------- |
| 追踪   | 对目标的 `cohW` 钟形核             |
| 弹跳   | 对边界的 `sepW`（反转径向分量）         |
| 规避   | 对障碍的 `sepW`                 |
| 绕身环绕 | 对施法者的**切向**力（不是向心）          |

**这就是判定和弹道解耦的意义**：轨迹怎么配，`sweptHit` 一行都不用改。

详见 `../noita-武器系统解剖与RTS适配.md` 第 7 节。

## 8. 多挂点（方向性建议）

Starsector 的配置感**主要不来自枪的种类多，而来自一艘船有多个挂点**。

现在的模型是「一个小队一种武器」（`sq.p.weapon`）。建议改成：

**注意：挂点只是配置位，不带射界。** 既然已经砍掉 `mount`（D8），三个挂点的武器都能朝任何方向开火，"挂点"就退化成"三个独立的武器槽"。这没关系——配置感来自**搭配**，不来自朝向。

```js
// templates.js
loadout: [
  { weapon: "railgun" },     // 槽 1：舰首重炮
  { weapon: "autocannon" },  // 槽 2
  { weapon: "flak" },        // 槽 3
]
```

这和 4 槽位武器程序天然合流：**一个挂点 = 一个槽位**。

代价：火力翻倍，需要重新平衡（用 `fire.energy` 做总预算约束）。
收益：同样 5 把枪，能配出「重炮 + 点防」「全导弹」「全自动炮」等明显不同的舰队风格，而不用做第 6 把枪。
