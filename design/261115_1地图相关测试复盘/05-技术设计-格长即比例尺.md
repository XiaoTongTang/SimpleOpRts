# 技术设计 · 格长就是地图的比例尺

> 状态：**已定稿**（4 个决策点已拍板，见 §0.1）
> 日期：2026-11-15
> 归属：`design/261115_1地图相关测试复盘/`
> 关联：`01/02/03` 是现有测试的逐条解释，本文是**推翻其中"格长=分辨率"口径**的设计

## 0. 一句话

**`cellSize` 是"一格等于多少 PX"，世界尺寸 = 格数 × 格长。改格长 = 整张地图等比放大，
但格子数、墙的格子数据、流场格数一模一样。**

`cellSize` 8 → 24，同一张 250×150 的图从 2000×1200 px 变成 **6000×3600 px**：
墙还是那 250×150 个格、流场还是算 250×150 个格，只是每一格变大了 3 倍。

### 0.1 决策记录（2026-11-15，已定）

| # | 议题 | 决定 |
|---|---|---|
| **D1** | 倒角深度 | **取消"深度"这个设定。** 只要一格触发倒角，就**固定切掉一半**（沿对角线切，半格面积），不设参数、不设像素常量 |
| **D2** | 世界尺寸上限 | **不限制**（只在格数上保留 `MAX_MAP_CELLS` 防内存） |
| **D3** | 换格长的方式 | **直接改 `DEFAULT_CELL_SIZE` 常量**，然后重开一局。**删除一切运行时可换格长的功能与入口**（命令、按钮、URL 参数） |
| **D4** | 流场是否按船宽膨胀 | **不膨胀**（维持既有决定，寻路不感知船宽） |

## 1. 我上一版理解错在哪（诊断，不是辩解）

| # | 我做的 | 错在哪 | 后果 |
|---|---|---|---|
| 1 | 把世界尺寸钉死在 2000×1200 px | 世界尺寸应当**由格数与格长派生** | 放大格长时只能压缩格数，地图大小纹丝不动 |
| 2 | 改格长时用 `regridMap` 把墙**重采样**到新格长 | 墙的格子数据是**权威**，一格都不该动 | 250 列被压成 84 列，墙的细节被"降采样"掉 |
| 3 | 把 `cellSize` 当"分辨率" | 它是**比例尺**（一格多少 px） | 实验变量从"单位/地图的相对尺度"变成了"网格精度"，完全跑偏 |
| 4 | 导入地图时用文件里的 `cellSize` 解释世界尺寸，再重采样 | **地图 JSON 没有 `cellSize`**，只有 `width`/`height`，且单位是**格数** | 250×150 的图被算成"2000×1200 的世界"，格长自然又变回 8 |

一句话概括第 4 条：文件说"我有 250 列 × 150 行"，我却把它读成"我有 250 个 8px 的格子"，
于是再怎么改格长，也只能在 2000px 的范围内挪腾 —— 看起来当然"还是 8"。

## 2. 单位与术语（先把定义统一）

| 概念 | 符号 / 代码 | 单位 | 含义 |
|---|---|---|---|
| PX | `px` | 世界像素 | **全局唯一的长度单位**。半径、射程、速度、Couzin 半径、格长……全是它 |
| 格数 | `cols` / `rows` | 格 | 地图的**权威维度**："这张图有 250 列、150 行" |
| 格长 | `cellSize` | px / 格 | 一格占多少 PX。**比例尺开关** |
| 世界尺寸 | `width` / `height` | px | **派生量**：`cols × cellSize`、`rows × cellSize` |
| 格坐标 | `cx` / `cy` | 格 | `floor(x / cellSize)` |

关键关系（只有这一条）：

```
width  = cols × cellSize
height = rows × cellSize
x ↔ cx:  cx = floor(x / cellSize)      x = (cx + 0.5) × cellSize   (格心)
```

**PX 的含义一点没变**：船半径 6 px 在两套比例尺下都是 6 px。变的是"6 px 在 6000 px 的地图上有多小"。

## 3. 目标模型

### 3.1 `MapGrid`：格数是权威，世界尺寸是派生

```js
// 唯一构造方式：给格数 + 格长
new MapGrid({ cols, rows, cellSize, walls, name })

// width / height 变成 getter（派生，不可写）
get width()  { return this.cols * this.cellSize; }
get height() { return this.rows * this.cellSize; }
```

- `walls`：`Uint8Array(cols * rows)`，1 = 墙。**换格长时这块数据不重建、不重采样。**
- `isWall(cx, cy)`、`cellXOf(x)`、`isWallAt(x, y)`、`nearestFloor(cx, cy)` 全部只依赖 `cellSize` 做换算，逻辑不变。
- `rev`（版本号）：每次新建地图就 +1。换格长只发生在"改常量 + 重启"路径上（D3），
  届时必然是一张新图，`rev` 自然递增 → 流场缓存整体失效，不需要额外处理。

### 3.2 默认战场：按格数定义

```js
export const DEFAULT_WORLD_COLS = 250;   // 8 px 时 = 2000 px，与现在一致
export const DEFAULT_WORLD_ROWS = 150;   // 8 px 时 = 1200 px
export const DEFAULT_CELL_SIZE  = 8;     // 比例尺开关：8 → 24 就是 ×3

blankMap(DEFAULT_WORLD_COLS, DEFAULT_WORLD_ROWS, DEFAULT_CELL_SIZE);
```

于是：

| 格数 | `DEFAULT_CELL_SIZE` | 世界尺寸 |
|---|---:|---|
| 250 × 150 | 8 | 2000 × 1200（现状） |
| 250 × 150 | 16 | 4000 × 2400 |
| 250 × 150 | 24 | **6000 × 3600** |
| 300 × 300 | 8 | 2400 × 2400 |
| 300 × 300 | 24 | **7200 × 7200** |
| 300 × 300 | 64 | 19200 × 19200（极端档，看 §8 风险） |

`DEFAULT_WORLD_W` / `DEFAULT_WORLD_H` 这两个"像素锚"**删除**，不再有"世界固定 2000×1200"这回事。

### 3.3 地图文件格式

```json
{ "name": "某图", "width": 250, "height": 150, "grid": [[0,0,-1,...], ...] }
```

- `width` / `height`：**格数**（不是 px），必须与 `grid` 的列数/行数一致 —— 现有校验已经是这个口径，**格式不变**。
- **没有 `cellSize` 字段**。解析器忽略它（读到也不采纳），世界尺寸由引擎的 `DEFAULT_CELL_SIZE` 决定：
  `map.width = 250 × cellSize`。
- `walls` 原样搬进 `MapGrid`，**不重采样**。

### 3.4 比例尺开关的唯一入口

```js
// map.js
export const DEFAULT_CELL_SIZE = 8;   // ← 只改这一个数
```

- 世界尺寸、网格绘制、流场换算、碰撞的搜格窗口、相机的铺满缩放，全部**自动**跟着变（都是从 `map.cellSize` 派生的）。
- **运行时没有任何换格长的入口**（D3）：`cmdSetCellSize` 命令、HUD 按钮、`?cell=` 查询串**全部删除**。
  改格长的唯一方式 = 改这一个常量 + 重新启动（新地图 = 新世界，天然是一次"重开"）。

## 4. 变化清单：改格长时什么变、什么不变

以 250×150 的图、格长 8 → 24（世界 2000×1200 → 6000×3600）为例：

| 项 | 变不变 | 说明 |
|---|---|---|
| 格数 `cols/rows` | **不变** | 250 × 150 |
| 墙的格子数据 | **不变** | 同一批 `walls`，一格不重采样 |
| 世界尺寸 | **×3** | 2000×1200 → 6000×3600 |
| 流场的格数 / 建场耗时 | **不变** | 还是一格一格算 250×150 格；单张 ≈7 ms（8px 档实测） |
| 流场每格覆盖的世界距离 | **×3** | 一格从 8 px 变 24 px，路径更"方"，拐角更钝 |
| 墙的碰撞多边形 | 跟着变 | 每格 24 px；倒角一律**切掉半格**（沿对角线），所以墙角被啃掉的物理长度也 ×3（§5） |
| 单位半径 / 射程 / 速度 / Couzin 半径 / 出生散布 | **全部不变** | 用户明确要求：单位和一切参数不动 |
| 单位相对地图的大小 | **÷3** | 6 px 半径在 6000 px 宽的图上是 1/1000（原来是 1/333） |
| 横穿地图的时间 | **×3** | SPD 96 px/s：2000 宽 → 21 s；6000 宽 → 62 s |
| 相机铺满（fit）缩放 | **÷3** | 由世界尺寸派生，自动 |
| 小地图、网格线、HUD 坐标 | 自动 | 都从 `map.width/height/cellSize` 取 |
| 空间索引格 (`CELL = 64`) | 不变（§6.3） | 纯加速结构 |
| 出生点散布 / 编队间距 / 阵型参数 | 不变 | 后果：大地图上开局队形显得极紧（有意观察的现象） |

**这一节的读法**：改格长**不改变**任何"算法与参数"，只改变"单位相对地图有多小"。
所以它不是性能实验，而是**尺度实验** —— 看鸟群算法在"船相对地图越来越小"时，队形/绕行/贴墙/抖动怎么变。

## 5. 倒角：没有"深度"这个设定（D1 已定）

**规则只有一句话：一格只要触发倒角，就固定切掉一半。**

- 没有 `CHAMFER_DEPTH_PX`，也没有"深度参数"。几何写死成**半格平面**：

```js
// C = cellSize，格左上角为原点；四个角各自的半平面
// TL: 保留 (x - left) + (y - top) >= C      ← 切线从 (left, top+C) 连到 (left+C, top)
// TR: 保留 (right - x) + (y - top) >= C
// BR: 保留 (right - x) + (bottom - y) >= C
// BL: 保留 (x - left) + (bottom - y) >= C
```

- 切线正好是格子的**对角线**：一个暴露角切掉 **半格面积**（沙盒原样）。
- **阈值判定不变**：只有"两条正交邻格都是空地"的角才算暴露角；四邻全空的孤立单格**不切**（切了就没有碰撞）。

### 5.1 和比例尺的关系（这是 D1 的实际后果，必须写清楚）

倒角以**格**为单位表达，所以格长放大时，墙角被啃掉的**世界长度同步放大**：

| 格长 | 一格 | 切掉的对角长度 | 被切掉的面积 | 视觉/手感 |
|---:|---:|---:|---|---|
| 8 px | 8 px | 11.3 px | 半格 = 32 px² | 现状（沙盒原样） |
| 24 px | 24 px | 33.9 px | 半格 = 288 px² | 墙面是"三倍长的 45° 斜面" |
| 64 px | 64 px | 90.5 px | 半格 = 2048 px² | 已经很长的斜坡 |

这是"整张图等比放大"的自然结果：**斜面的物理长度和世界尺寸一起放大**，
而不是像上一版那样把它钉成 8 px 常量。取消了深度设定之后，倒角在**格空间**里完全恒等，
所有几何都只依赖 `cellSize` 一个数，没有第二个可调项。

> 由此带来的手感想定：格长 24 时，船（半径 6~23 px）相对墙角斜面（33.9 px）显得更小，
> 贴角滑行会更"顺"（斜面占比更大），这是尺度实验里预期要观察到的差异之一，不是 bug。

## 6. 其余技术点（决策已定，此节是落实口径）

### 6.1 世界尺寸上限（D2：不限制）

- 不做任何世界像素尺寸上限。300×300 格 × 64 px = 19200×19200 也是合法的。
- 唯一的闸门仍是**格数**：`MAX_MAP_COLS/ROWS = 1024`、`MAX_MAP_CELLS = 200000`（防的是内存与建场耗时，
  与"世界多宽"无关）。
- 空间索引按世界尺寸建桶：19200/64 = 300 → 300×300 = 9 万个桶，`Grid` 现在是按需生长的数组，没问题。
- 相机最远仍是 fit（整图铺满），近处细节靠滚轮放大；网格线在极低缩放下自动每 2/4/8 格画一条（已有逻辑）。

### 6.2 换格长后单位坐标（D3：改常量 + 重开，不缩放）

- 换格长**只发生在**"改 `DEFAULT_CELL_SIZE` → 重新启动"这一条路径上，启动本身就是新世界、新一局。
- 因此**不需要**任何"把单位坐标 ×3"的隐形规则，也不存在"旧状态迁移到新比例尺"的问题。
- 运行时的 `cmdSetCellSize` 命令、HUD 按钮、`?cell=` 查询串全部删除；`pnpm test` 里对应的用例一并删除。

### 6.3 空间索引格 `CELL = 64`

保持写死 64 px。它是纯加速结构（只决定"每帧查邻居要扫几个桶"），不影响任何正确性，
也和比例尺无关：格长 64 时它正好等于一格，格长 4 时等于 16 格，两种都成立。

### 6.4 流场缓存与 `rev`

- 换格长只发生在"改常量 + 重启"路径上，成功启动时地图是**新建**的，`rev` 自然递增 → 缓存天然失效，
  不需要额外处理。
- 唯一要留意的实现细节：**边长为 `cellSize` 的直角/对角步长必须从 `map.cellSize` 现算**，
  不能把 8 之类的数写死在 `flow-field.js` 里（现在没有写死，改的时候守一下）。

### 6.5 流场是否要按单位半径膨胀（D4：不膨胀）

- 维持 `当前度量单位分析.md` 的 D3：寻路不感知船宽，不对 `walls` 做膨胀。
- 比例尺实验会把这个缺口放大：格长 24 时一格 24 px，1 格宽的缝对 12 px 宽的船绰绰有余（能过）；
  格长 4 时 1 格缝只有 4 px，船过不去但流场认为可通行（顶着墙）。**这属于已知后果，不在本次处理。**
- 若将来要补，改动点只在 `flow-field.js` 建场前对 `walls` 做 `k = ceil(minRadius / cellSize)` 格膨胀，
  只影响寻路用的位图，不动碰撞原图。

### 6.6 出生点 / 编队 / Couzin 参数

用户明确"单位和别的所有参数完全不需要任何变化"，所以：

- `SPAWN_SPREAD = 55`、阵型参数、Couzin 半径、`SPD = 96` 全部不动。
- 后果（要接受，不是 bug）：格长 24 时，一张 6000 px 宽的图上，cohRadius 180 px 只覆盖 3% 的宽度，
  小队会显得**极其分散**、绕大圈、难以聚成一团；寻路一格 24 px 的量化会让路径更"折线"。
  这正是"地图尺度拉大后鸟群算法表现如何"要观察的东西。

## 8. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 巨大世界（19200²）下相机最远仍能铺满，但**近处细节**（船 6 px）几乎不可见 | 属观察需要，不是错误 | 用滚轮放大；`clampZoom` 上限已按 fit 自适应 |
| 单位相对变小后，武器射程（250~480 px）相对地图变成 1/25，战斗集中在极小区域 | 玩家可能觉得"永不接战" | 正是尺度实验要暴露的问题；调参留给实验之后 |
| 流场路径在 24 px 格上很"方"，船 6 px 沿 24 px 网格走 | 观感粗糙 | 已有 `directionAt` 双线性平滑；不做更多插值 |
| 换格长必须改常量 + 重启 | 打断当前观察 | 接受（D3） |
| 倒角随格长等比变大（24 px 格上是 33.9 px 斜面） | 墙角越"斜"、薄墙端头越尖 | 接受（D1：倒角在格空间恒等，是等比放大的自然结果） |
| 地图文件若写了 `cellSize` | 会被忽略 | 忽略并留注释；不报错（格式本身没有这个字段） |
