# 02 · 流场寻路（`test/flow-field.smoke.mjs`，37 条）

> 被测对象：`src/core/sim/flow-field.js`（建场 / 取方向 / 缓存）、`src/core/core.js`（调度与端到端）
> 建场流程：目标格 → Dijkstra 代价场 → 逐格回填方向；每支有信标的小队一张，按目标格共享缓存。

## [1] 空地上方向指向目标（4 条）

场景：40×30 格空图（320×240），目标在 (164, 124)，探测点在左上 (16, 16)。

| ID   |   行 | 断言原文                   | 它守的业务规则                        | 怎么验的                               | 结论  |
| ---- | --: | ---------------------- | ------------------------------ | ---------------------------------- | --- |
| F-01 |  46 | 场就绪                    | 建场函数在正常输入下返回可用场（不是 null / 半成品） | `f.ready === true`                 |     |
| F-02 |  47 | 可达格数 > 90%             | 空图上几乎所有格都能走到目标                 | `f.reachable > 0.9 × 格子总数`（1200 格） |     |
| F-03 |  52 | 有方向                    | 探测点不是死格，能取到一个单位方向              | `directionAt(...)` 非 null          |     |
| F-04 |  55 | 与真实方向的夹角 ≤ 23°（8 邻域量化） | 方向大体指向目标；8 邻域方向量化，理论误差上限 22.5° | 用向量点积求夹角                           |     |

> 说明：这条是**精度上限**断言，不是"必须精确指向"。它挡的是历史问题——
> 8 邻域等距平局没做 tie-break 时，方向会整体偏 36°（场上表现为船斜着走、绕远路）。

## [2] 目标落在墙里（4 条）

场景：40×30 图中间一块 4×4 墙；把一个点直接下在墙里 (21,16)→世界 (172,132)。

| ID | 行 | 断言原文 | 它守的业务规则 | 怎么验的 | 结论 |
|---|---:|---|---|---|---|
| F-05 | 62 | 场仍然建出来了 | 玩家点到墙上不该"没反应"（要么吸附，要么明确失败，不能崩） | `buildFlowField` 返回非 null | |
| F-06 | 63 | 目标格被挪到空地 | 目标格自动吸附到最近空地 | `!map.isWall(f.targetCellX, f.targetCellY)` | |

| F-08 | 72 | 全图都是墙时返回 null | 无解时明确失败，不返回坏场（否则船会拿到全零方向乱走） | 6×6 全墙图 → `null` | |

## [3] 有墙：沿墙绕，不指进墙里（3 条）

场景：40×30 图，x=20 一列竖墙（y=0–21），下方留缺口；目标在右上 (272, 32)。

| ID | 行 | 断言原文 | 它守的业务规则 | 怎么验的 | 结论 |
|---|---:|---|---|---|---|
| F-09 | 85 | 墙左侧有方向 | 墙的另一侧仍能建出有效场（不是"被墙切断就全零"） | 墙左侧格 (18,4) 取方向非 null | |
| F-10 | 90 | 方向不会直接指进墙里 | 贴墙的格，方向不该正对墙面（会一直顶墙推不动） | ⚠️ 见下方说明 | |
| F-11 | 94 | 缺口下方有方向 | 缺口下方存在绕行路径（不是死区） | 缺口下方格 (20,25) 取方向非 null | |

> ⚠️ **F-10 的验法有问题**（量纲错误，建议重点审）：它算的是
> `nx = 18 + left.x`、`ny = 4 + left.y`，把**单位方向向量**直接加到**格号**上再四舍五入去查墙。
> 实际查到的是 (19,5) 这种邻居格，而不是"沿方向走一步"的那格。所以它今天必然通过，
> 但并没有验证它声称的那件事。业务上想验的应是：
> 「从该格的**世界坐标**沿方向走一格，落点不在墙里」。

## [8] 端到端：下达信标 → 建场（10 条）

场景：`GameCore` 1600×960，seed 4；取蓝方两支非散兵小队，同时给同一个信标 (800, 480)。

| ID | 行 | 断言原文 | 它守的业务规则 | 怎么验的 | 结论 |
|---|---:|---|---|---|---|
| F-25 | 159 | 一开始没有场 | 没命令时不算场（CPU 不浪费） | 初始 `squads[a].flow === null` | |
| F-26 | 162 | 信标下完还没算（排队中） | 建场是**排队**的，不在命令里同步算（否则命令那帧会卡） | `core.flowQueue.length === 2` | |
| F-27 | 165 | 一帧只算一张（定数调度） | 每帧固定建 1 张 —— 确定性要求（按毫秒预算会让不同机器分叉，同 seed 跑不出同一场） | 走 1 帧后 `flowCache.size === 1` | |
| F-28 | 166 | 第一支队伍拿到场了 | 排队后确实有队伍先拿到 | 两支里至少一支 `flow` 非 null | |
| F-29 | 169 | 两帧之后两支都有场 | 一帧一张，两帧两张，顺序稳定 | 走 2 帧后两支都非 null | |
| F-30 | 170 | 同目标只缓存了一张 | 同信标的两队共享同一张场（不重复算） | `flowCache.size === 1` | |
| F-31 | 173 | 清信标后场被丢掉 | 取消命令要回收场（否则继续用旧场跑） | `clearGoal` 后 `flow === null` | |
| F-32 | 178 | 空图上有方向 | 默认空图上也能建出有效场 | 在 (200,200) 取方向非 null | |
| F-33 | 179 | 场地规模正确（cols×rows） | 场数组尺寸与地图网格一致（不一致会静默读错格） | `f.cols/rows` 等于 `map.cols/rows` | |
| F-34 | 181 | 池子不参与（没有信标） | 散兵池不受小队命令影响 | 池子的 `flow === null` | |

## [9] 端到端：绕进「开口朝上的口袋」（3 条）

场景：80×60 格（640×480），左侧 x=56 与右侧 x=70 各一堵竖墙（y=18–42），底部 y=42 封住 → **开口朝上**的口袋。
8 艘矛隼从口袋左边出发，信标在口袋内 (508, 244)。成功 = 小队质心进入信标 40 px 内；最多跑 2400 帧（40 秒）。

> 为什么用"开口朝上"：开口朝下时船贴墙滑行 + 无命令游走会在 20 秒内自己蹭出去，测不出流场作用。

| ID | 行 | 断言原文 | 它守的业务规则 | 怎么验的 | 结论 |
|---|---:|---|---|---|---|
| F-35 | 231 | 有流场：能绕进朝上的口袋里 | 流场真的解决"绕进去"（贴墙滑行做不到） | 有流场时能到达 | |
| F-36 | 233 | 有流场在 15 秒内到达 | 绕行速度在可接受范围 | 帧数 < 900 | |
| F-37 | 235 | 无流场明显更慢（耗时至少 1.4 倍） | 证明差距来自流场本身 | 对照组每帧把 `flow` 掐成 null，比帧数 | |

> ⚠️ F-36 的 900 帧、F-37 的 1.4 倍都是**调参敏感**阈值：改 Couzin 参数、巡航速度、船体速度都会漂。
> 历史上（迁移期）这两条挂过一次。
