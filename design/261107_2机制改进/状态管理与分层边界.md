# 状态管理与分层边界（Pixi + React 接入后）

日期：2026-11-08
对上位文档：`design/261107_1画面升级/261107_渲染层接口.md`（那一篇定义「画什么 vs 用什么画」）
对应代码：`prototype/js/renderer.js`、`prototype/js/renderer-canvas2d.js`、`prototype/plinko-battle.html`

---

## 1. 要回答的问题

渲染层换 PixiJS、UI 层换 React + React 状态管理库之后，**游戏的最终状态管理放在哪里**？

约束条件来自玩法本身：

> 游戏进行过程中，玩家要能**随时**修改小队配置与舰船搭配。

这一条决定了答案。如果只是"进入战斗前配一次"，UI 和模拟谁持有配置都行；但**在战斗中改**意味着配置改动要立刻被模拟采用、要受资源规则校验、还要能中途被拒绝。

---

## 2. 先拆三种状态

"状态放哪"不能统一回答。项目里有三种生命周期完全不同的状态，混在一起是后期失控的主因。

| 状态 | 例子 | 变化频率 | 生命周期 |
|---|---|---|---|
| **模拟状态** | 单位坐标 / 速度、HP、冷却、弹丸、寻敌目标、空间索引 | 60 Hz，每帧原地修改 | 一局 |
| **构筑状态** | 小队编制、舰船装配、武器 / 插件、生产线、模组库存、指挥值占用 | 玩家操作时 | 跨局（存档） |
| **UI 状态** | 哪个面板打开、当前选中哪支小队、拖拽中的预览、悬浮提示 | 交互时 | 瞬时 |

---

## 3. 结论

**最终状态管理放在游戏核心（GameCore）里，不放 React store。**

理由不是"架构好看"，而是**构筑状态受资源规则约束**：

- 指挥值总量有限（`母舰.舰队指挥值总量`）
- 可占领建筑上限有限
- 预制模组数量有限
- 每艘船有承载力上限（武器 / 插件占用）

玩家在战斗中改编制时，这次改动**可能不合法**——超指挥值、模组不够、生产线不空闲。而校验规则属于模拟层。

如果 React 是构筑状态的权威，就要在 React 里复制一份指挥值规则来判断合法性，等于把游戏规则放进 UI 层。两边迟早不一致，而且**规则永远只有一份**这个前提直接被破坏。

所以正确形态是：**core 是唯一真相源，React 只持有"编辑草稿"和"只读镜像"**。

---

## 4. 架构形态

```
                玩家操作
                   │  命令（command），不改状态
                   ▼
      ┌─────────────────────────┐
      │        GameCore         │  ← 唯一真相源
      │  sim state   （60Hz）   │     原地修改，纯数组，无框架
      │  build state （权威）   │     编制 / 装配 / 生产 / 库存
      │  RunState    （种子）   │     存档、回放、测试的唯一输入
      └─────────────────────────┘
         │                  │
   每帧 getView()      节流快照 10Hz + 事件
         │                  │
         ▼                  ▼
    ┌─────────┐      ┌──────────────┐
    │  Pixi   │      │   Zustand    │  ← 只是投影 + 草稿 + UI 状态
    └─────────┘      └──────────────┘
                            │ selector
                            ▼
                          React
```

关键点：**Pixi 和 React 是两个平级消费者，彼此不认识。**

- Pixi 在 rAF 里直接调 `core.getView()`，**不经过 React**
- React 只在 store 变化时重渲染，**不参与每帧绘制**
- 两者都只读 core，写只通过命令

---

## 5. 三方分工

### 5.1 GameCore（纯 JS，禁止 import React / Pixi）

| 内容 | 说明 |
|---|---|
| 单位数组、空间索引、武器系统、防御系统 | 现有模块直接搬进来 |
| 权威构筑状态 `build` | `{ squads, loadouts, production, modules, commandUsed }` |
| `RunState` | 种子、时间、事件日志 → 存档与回放 |

对外只暴露三类东西：

```js
core.step(dt)                       // 推进一帧
core.getView()                      // 给渲染层的只读投影
core.command(cmd)                   // 唯一的写入入口，返回结果
```

### 5.2 Zustand（React 侧）

| slice | 内容 | 来源 |
|---|---|---|
| `buildMirror` | core 构筑状态的只读投影 | core 事件推送 |
| `draft` | 玩家正在编辑未确认的草稿 | 本地交互 |
| `ui` | 面板开关、选中项、悬浮态 | 本地交互 |

### 5.3 Pixi（世界层）

只读 `core.getView()`，不写任何东西。契约见上位文档《渲染层接口》。

---

## 6. 为什么选 Zustand 而不是 Redux / Context

判断依据只有一条：**能不能在 React 之外读写**。游戏循环跑在 rAF 里，React 根本不参与，所以必须支持：

```js
// ① 从游戏循环里往 store 推数据（React 不参与）
useGameStore.getState().applySnapshot(snapshot);

// ② 组件外订阅（调试面板 / Pixi 读取构筑态时用）
useGameStore.subscribe(s => s.buildMirror, onChange);
```

| 方案 | 结论 |
|---|---|
| **Zustand** | `getState()` / `setState()` / `subscribe()` 全部可在组件外调用，无需 Provider，重渲染粒度可控 → **选它** |
| Redux | 同样能组件外访问，但 action / reducer 样板量对单人项目偏重，收益（时间旅行）我们不需要 |
| Context | 一次更新重渲染整棵子树。60Hz 附近的更新会把主线程打满 → 不用 |

用 `subscribeWithSelector` 让组件只订阅自己关心的字段，避免"改一个小队的参数，整个侧栏重渲染"。

## 7. 战斗中改配置：必须分两档

这是本设计的核心，也是最容易被写成一种机制、后期补救的地方。

### 7.1 第一档：只改参数 → 直接写，下一帧生效

阵型参数、接敌策略、武器开关这类，不涉及实体增删。

```js
core.setSquadParam(squadId, "cohesion", 0.6);
```

L2 层本来就要求"输出参数在 0.3 s 内插值过渡"，所以这里写进去不会造成力的阶跃。**不需要事务**。

### 7.2 第二档：改实体 → 事务命令，帧边界应用

增减舰船、换武器、换船体、换插件。涉及生成 / 销毁实体，还可能被资源规则拒绝。

```js
const r = core.command({ type: "applyLoadout", squadId, loadout });

// 成功
{ ok: true,  applied: [...], refunded: [...], commandUsed: 412 }

// 失败：reasons 直接给 UI 标红
{ ok: false, reasons: ["超出指挥值 12", "预制模组不足 3"] }
```

三条约束：

1. **校验写在 core，UI 只负责显示。** 规则永远只有一份。
2. **只在帧边界应用**，不能在一帧的中间改数组。否则会出现"实体已删但武器仍在结算"的脏状态。
3. **应用是差量的**：能保留的单位保留（位置、速度、当前目标不变），只增删差集。全量重建会让玩家一改配置就看见整队瞬移，直接破坏观感。

### 7.3 为什么 UI 不能自己算合法性

举个具体冲突：UI 里玩家拖滑条把小队的护卫舰从 4 艘加到 8 艘。UI 认为合法（没超编队上限），但 core 知道此时**总指挥值只剩 3**。如果 UI 先乐观更新并重建了列表，玩家会看到"已经加上了"，随后 core 拒绝，列表再回滚 —— 这个闪烁本身就是 bug 报告。

正确做法：滑条只改 `draft`，松手 → 发命令 → 按返回结果落库或标红。

## 8. 边界表（谁拥有什么）

| 问题 | 答案 |
|---|---|
| 小队编制的权威 | GameCore（因为有指挥值 / 承载力约束） |
| 玩家拖滑条时谁在改 | React 的 `draft`；松手 / 确认才提交 core |
| 面板上显示的血量 | core 推来的 10 Hz 快照，不是 React 自己算 |
| 建造队列进度 | core；UI 按快照显示，**不自己倒计时** |
| 相机位置 | core 拥有（模拟要用视口做裁剪），React 读来做小地图 |
| 选中了哪支小队 | React（纯 UI 状态，core 不需要知道） |
| 存档存什么 | 只存 `RunState`（含 build）；React store 全部可从 RunState 重建 |

---

## 9. 三条纪律

1. **UI 只能发命令，不能写状态。** 任何 `units[i].hp = x` 出现在 React 代码里就是 bug。
2. **每帧数据不进 React。** 单位数组、弹丸、粒子一个都不能进 store。只进 UI 真正要显示的那几个数字，且节流到 ~10 Hz。
3. **core 先于 React 存在。** core 必须能在没有 React 的情况下跑起来。现有的纯 canvas 页面（`couzin-command.html` 那种形态）正好可以作为"无 UI 的回归测试"。

## 10. 与现状的差距

现状盘点（2026-11-08）：

| 项 | 状态 |
|---|---|
| 模拟模块零 DOM / 零 canvas 依赖 | ✅ 已达成（`group-layer` / `squad-layer` / `spatial` / `weapon-system` / `defense-system` / `templates` / `weapons` 全部 0 命中） |
| 模拟 → 渲染的依赖方向 | ✅ 单向，模拟层从不 import 渲染模块 |
| 渲染接口 | ✅ 已有 `WorldRenderer` + Canvas2D 实现 |
| 统一走渲染接口 | ⚠️ 4 个页面只有 `plinko-battle.html` 走接口 |
| 模拟 / 渲染文件边界 | ⚠️ `plinko.js` 里同时有 `stepBoard`（模拟）和 `drawBoard(ctx)`（渲染） |
| 事件 vs 视觉 | ⚠️ 模拟层直接 `fx.push({ type:"beam", hue, life })`，并自带 `RAY_AIM / RAY_FLY` 视觉常量 |
| 确定性 | ❌ 模拟层 13 处 `Math.random()`，无法回放 / 无法稳定单测 |
| core 抽取 | ❌ 状态仍散在页面里（`S` / `squads` / `units` / `projectiles`） |

结论：**骨架是对的，缺的是收口。** 在接 React 之前，必须先做第 11 节的 1、2 步，否则 React 接上来会同时继承"模拟决定表现"和"状态住页面里"两个问题。

## 11. 落地顺序

| 步骤 | 内容 | 为什么排这个顺序 |
|---|---|---|
| **S1** | 抽 `core.js`：把页面里的 `S`、`squads`、`units`、`projectiles`、`fx` 收进 core，页面只保留输入与渲染 | 不抽出来，后面每一步都在给临时结构打补丁 |
| **S2** | `fx` 改成语义事件：模拟只 push「谁、对谁、什么武器、命中点」，`render-fx.js` 做事件→视觉的映射，`RAY_*` 搬进渲染层 | 这是"模拟不决定表现"的最后一道口子 |
| **S3** | 拆 `plinko.js` → `plinko.js`（sim）+ `render-plinko.js`（画） | 让"模拟文件里没有 ctx"成为机器可检查的规则 |
| **S4** | Pixi 渲染器实现 `WorldRenderer`，与 Canvas2D 并存、开关切换 | 接口已在，风险最低的一步，可先验证观感 |
| **S5** | 上 React + Zustand，只做**只读**面板（战况、小队列表） | 先验证"core → store → React"这条链路不泄漏 |
| **S6** | 加 `draft` 与 `command()`，把编辑能力接上 | 这时才真正需要事务与校验 |
| **S7** | 注入 seeded RNG + `RunState` 序列化 | 存档、回放、构筑系统共用 |

---

## 12. 验收标准

接 React 之后，用这几条判断分层是否成立（都是可以实测的，不是主观判断）：

1. **关掉 React，core 仍然能跑完整一局**（用现有 canvas 页面 + 无 UI 模式）。
2. **React 代码里搜不到对 `units` / `projectiles` 的写操作**（只读引用可以）。
3. **改一支小队的参数，只有相关的组件重渲染**（用 React DevTools 的 render 高亮验证）。
4. **满编 400 单位时，React 不产生任何每帧 setState**（在 store 里打点计数）。
5. **catch 到一个非法编辑时，UI 上显示的是 core 返回的 `reasons`**，不是前端自己拼的文案。

## 13. 已知风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 快照频率定太高 | 10 Hz 只是起点。侧栏显示的小队血条如果明显滞后，会显得"卡" | 只对**当前选中**的小队提到 30 Hz，其余保持低频 |
| 相机归 core 导致输入延迟 | 相机在 core 里意味着输入要先走命令 | 相机是本机专属状态，可以破例放在渲染层，存档时再写回 RunState |
| 事务命令被滥用 | 所有改动都走 `command()` 会让简单的滑条也变得笨重 | 明确分档（见第 7 节），只有涉及实体增删才走事务 |
| React 与 Pixi 抢 rAF | 两套循环会导致掉帧 | **只允许一个主循环**，React 不注册 rAF，靠 store 更新驱动 |
