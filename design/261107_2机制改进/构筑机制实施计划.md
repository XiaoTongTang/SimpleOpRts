## P2 · 支援能力 sim（⚠ 会改战场表现）

**目标**：删掉「每 2.5 秒套 80 盾 + 电量 + 冷却」，换成持续恢复光环。

### 交付物

| 文件                               | 动作                                                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `src/core/sim/support-system.js` | **新增**：`stepSupport(units, grid, dt, fx)`，两遍遍历 + 每帧重算 `effShieldCap`                                      |
| `src/core/sim/defense-system.js` | **删** `stepChargers()`、`u.energy`、`u.castCd`、`u.charger`                                                  |
| `src/core/core.js`               | **删** `G` 里的 `shieldHp/chargerRange/chargerCd/energyMax/energyCost/energyRegen`；`step()` 改调 `stepSupport` |
| `src/core/sim/squad-layer.js`    | **删** `P_DEFS` 里的 `chargers` 行                                                                            |
| `src/core/sim/templates.js`      | **删** 每个模板的 `chargers: n`                                                                                 |
| `src/render/render-units.js`     | `if (u.charger)` → `if (u.abilities.some(a => a.resource === "shield"))`                                  |
| `src/render/render-fx.js`        | `shieldlink` / `shieldup` 改为持续样式 + 0.4s 节流                                                                |
| `test/support.smoke.mjs`         | **新增**                                                                                                    |

### 验收

1. 修复 / 充能可观测：一支残血编队靠近维修模块后血量线性上升；
2. **顺序无关性**：把 `units` 数组打乱后跑同一个 `stepSupport`，血盾结果完全一致（单测）；
3. `dt` 上限生效：传 `dt = 5` 与传 `dt = 0.05` 的结果一样；
4. fx 数量上限：24 艘编队被照射，1 秒内 fx 事件 ≤ 60；
5. 代码里搜不到 `energy` / `castCd` / `u.charger`。

### 风险与对策

这一阶段必然改变战斗强度（原来是爆发套盾，现在是持续回血/回盾）。

- 在**独立分支**做，先不合主干；
- 做一份固定随机种子的前后对比（5 分钟战斗的击杀数、存活率），确认没有量级偏差；
- 需要先给 `Math.random()` 加种子（这是已知欠账），否则对比不可复现 —— 见「前置小任务」。

## P3 · 多武器齐射

**目标**：让「一条船装两门炮」真的打出两条弹道。这是构筑**有意义**的前提。

### 交付物

| 文件 | 动作 |
|---|---|
| `src/core/sim/weapon-system.js` | `u.weapon` → `u.weapons[]`，每个槽位独立的 `cd / burstLeft / burstTimer / target` |
| `src/core/sim/defense-system.js` | `initCombat()` 按 `weapons[]` 建状态 |
| `src/core/data/ship-template.js` | `compileShip()` 输出完整 `weapons[]`（去掉"只喂第一个"的临时话） |

### 验收

1. 两门炮 = 每帧两次独立的开火判定，弹道从各自 `slot.pos` 出发；
2. 只装一门炮时，伤害结果与 P3 之前**逐帧一致**（防止顺手改坏了平衡）；
3. 每条船的内存增量可接受（护卫舰 2 槽 = 2 个状态对象，24 艘 = 48 个）。

### 风险

`weapon-system.js` 是 15KB 的核心文件，改动面大。对策：保持 `u.weapon` 作为兼容别名（指向 `weapons[0]`），让渲染层与旧测试逐步迁移。

## P7 · 正式构筑 UI（独立计划，不在关键路径）

依赖「React + Zustand + Pixi 真身」迁移，那是另一条正在挂账的线。本计划只保证**接口是干净的**：

- `shipLibrary` 的 CRUD 是纯函数，UI 换成 React 时不用动；
- `computeShip()` 幂等、无副作用，可以直接在 React 里每帧调（草稿预览）；
- `core.command()` 是唯一写入入口，React 侧不需要知道校验逻辑。

建议 P7 和 React 迁移合并成一个计划做，别分两次动 UI。

## 终态验收（整件事做完了的标准）

1. 从零建一个舰船模板 → 存进库 → 编进小队 → 下订单 → 造出来，全程不需要改代码；
2. 同一船体的两种装配，在战场上表现**可测地不同**（火力密度 / 生存时间）；
3. 支援舰能自动照顾范围内友军，玩家不需要点任何技能；
4. 改编制不重建全场、不复活、不丢血比；
5. `pnpm test` 全绿；`balanceReport()` 无 `alert`；代码里搜不到 `energy` / `chargers`。
