> 对应需求：`构筑机制设计.md` 的「舰船数据结构设计」一节

## 0. 总览

构筑系统 = **4 类模板 + 1 份解锁记录**：

| 模板 | 谁写的 | 可变性 | 本文 |
|---|---|---|---|
| 船体模板 HullTemplate | 开发者 | 只读，靠蓝图解锁 | ✅ |
| 武器模板 WeaponTemplate | 开发者 | 只读，靠蓝图解锁 | ✅ 补构筑字段 |
| 插件模板 PluginTemplate | 开发者 | 只读，靠蓝图解锁 | ✅ |
| 能力模板 AbilityTemplate | 开发者 | 只读，靠蓝图解锁 | **另见 `支援能力设计.md`** |
| 舰船模板 ShipTemplate | **玩家** | 新建/改名/改配/删除 | ✅ |
| 解锁记录 PlayerCatalog | 存档 | 只增不减 | 只定接口（§12） |

关系：**舰船模板 = 1 个船体模板 + 每个插槽里装了什么**。

## 1. 核心原则：手填是权威，算法只给推荐

三个值 —— **指挥值 `command`、建造时间 `buildTime`、承载量 `capacity`** —— 全部**硬编码在模板里**，直接手改就能调平衡。

算法（§6）只负责算一个 `recommended`，用来做两件事：

1. **填初值**：新加一条模板时，先跑算法拿到基准数，再按手感微调；
2. **防漂移**：随时对比「手填值 vs 推荐值」，偏离超过阈值就报警，防止数值在几十次改动里慢慢跑飞。

```
模板里存的：  command: 4      ← 权威，运行时只读这个
算法算出的：  recommendCommand(hull) → 4   ← 不入模板，只在编辑器/审计/单测里跑
```

好处：任何一个数想调，改一个字段就生效，不需要反推公式；同时公式还在，能发现「这条模板被改歪了」。

**三个字段在所有模板里的语义：**

| 字段 | 船体模板 | 武器 / 插件模板 |
|---|---|---|
| `command` | 自身占用的指挥值（母舰为 0） | 附加指挥值，**默认 0**（见 D1） |
| `buildTime` | 船体基准工时 | 附加工时 |
| `capacity` | 承载上限（**给**） | 承载占用（**占**） |

舰船级：

```
command   = hull.command   + Σ item.command
buildTime = hull.buildTime + Σ item.buildTime
capacity  = hull.capacity  + Σ item.mods.capacity
capacityUsed = Σ item.capacity
```

「船体给上限、装备占用量」用同一个字段名是刻意的：这样装配校验就是一句话 `used ≤ cap`，不需要区分正负号。

## 2. 共同约定

| 约定 | 内容 |
|---|---|
| id 命名 | `hull.xxx` / `plugin.xxx` / `ship.xxx`；武器沿用现有裸名 `laser` 等 |
| id 稳定性 | id 是存档与蓝图解锁的唯一依据，**永不重命名**；改显示名只改 `name` |
| 单位 | 时间 = 秒；距离 = 世界像素；血量/护盾/承载/指挥 = 点 |
| 只读 | 模板表启动时深冻结，运行时不允许就地修改 |
| 校验契约 | 校验函数返回 `{ ok, reasons: string[] }`，沿用 core 现有约定 |
| 缺省 | 插槽键必须存在，空槽写 `null`（不省略键，UI 靠键铺格子） |
| 数值来源 | `command` / `buildTime` / `capacity` 手填；其余派生值现算 |

## 3. 船体模板 HullTemplate

### 3.1 字段表

```js
{
  id:        "hull.falcon",       // string  唯一键
  name:      "矛隼级",             // string  显示名
  class:     "frigate",           // enum    frigate | destroyer | cruiser | mothership
  tier:      1,                   // int     同级内档次（排序/稀有度用）
  sprite:    { sheet, frame },    // object  贴图引用，见 imgs/*_atlas.json

  // ---- 三个手填值（权威） ----
  command:   4,                   // int     占总人口
  buildTime: 8.0,                 // float   船体基准工时（秒）
  capacity:  14,                  // int     承载量上限

  slots:     { weapon: [...], plugin: [...] },
  armor:     { ... },
  mothership:{ ... }              // 仅母舰有
}
```

**`class`**：只影响建造工时推荐系数与 UI 分组，不影响别的属性（与需求原文「近乎只读的类型」一致）。
**`tier`**：同级内的高档船体（壁垒级 vs 矛隼级），只用于排序与蓝图稀有度，**不参与任何数值推导**（承载量由槽位布局推，见 §6.2）。
**`sprite`**：`{ sheet: "护卫舰素材1", frame: "frigate_01" }`，直接对上前几天做的 atlas json。

### 3.2 插槽模型

```js
slots: {
  weapon: [
    { id: "w1", size: "S", pos: [-5, -7] },
    { id: "w2", size: "S", pos: [ 5, -7] }
  ],
  plugin: [
    { id: "p1" },
    { id: "p2" }
  ]
}
```

**为什么是数组而不是 `{ S: 2, M: 0 }` 计数**：

1. UI 要能一格一格拖拽，需要稳定的槽位 id；
2. `pos` 能标出开火点在船体上的位置，让弹道从炮口出而不是从船心出（现在是从船心出，很难看）；
3. 槽位后续可以加特殊限制（"只能装导弹"），计数法做不到。

**`pos` 是可选字段**，缺省 = 船心。可以先只填 `id` 和 `size`，表现层再逐步补坐标。

> **v2 变更：已删除 `arc` 字段。** RTS 不做武器转角限制，所有武器默认全向。曲射/侧舷齐射那类需求等真的能做战术朝向时再说。

**尺寸兼容规则**：`SIZE_RANK = { S: 0, M: 1, L: 2 }`

| 槽位 | 可装 | 说明 |
|---|---|---|
| S 槽 | S | |
| M 槽 | S、M | 大槽能装小武器，但浪费槽位 |
| L 槽 | S、M、L | |

即「**大槽是上限，不是限定**」。**插件槽不分尺寸**（需求只说「插件槽数量」）。

### 3.3 母舰专有块

```js
mothership: {
  moduleCap:     60,      // 预制模组存储上限
  moduleRegen:   0.6,     // 预制模组自然恢复 / 秒（生产线忙也照常）
  lines:         3,       // 生产线数量
  efficiency:    30,      // 生产效率总和（工时/分钟）
  commandCap:    900,     // 舰队指挥值总量
  captureLimit:  3        // 可占领建筑上限
},
abilities: [{ id: "ability.repair_drone", count: 4 }]   // 维修无人机走能力模板，见 支援能力设计.md
```

**刻意的取舍：生产效率是「总量」，每条线的具体分配是运行时状态，不进模板。**
模板只说「这艘母舰有 3 条线、总共 30 点效率」，玩家在局内把 30 点分给 3 条线（比如 20/5/5）。这样同一艘母舰可以有不同的生产方式，不需要为每种分配存一个模板。

### 3.4 阶段一船体清单（手填值 = 推荐值，见 §6）

| id | 名称 | class | tier | hp | hpRegen | shield | shieldRegen | 武器槽 | 插件槽 | **capacity** | **command** | **buildTime** |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| `hull.falcon` | 矛隼级 | frigate | 1 | 60 | 2.0 | 0 | 0 | 2×S | 2 | **14** | **4** | **8.0** |
| `hull.bulwark` | 壁垒级 | frigate | 2 | 75 | 2.5 | 30 | 1.5 | 1×M + 1×S | 2 | **17** | **6** | **12.0** |
| `hull.hammer` | 重锤级 | destroyer | 1 | 130 | 3.0 | 30 | 2.0 | 1×M + 2×S | 3 | **24** | **10** | **26.0** |
| `hull.citadel` | 堡垒级 | cruiser | 1 | 280 | 6.0 | 60 | 4.0 | 2×M + 2×S | 4 | **34** | **22** | **63.8** |
| `hull.ark` | 方舟级 | mothership | 1 | 3000 | 20 | 0 | 0 | 1×S | 2 | **10** | **0** | **0** |

受击尺寸：`hullHitR` = 6 / 6.5 / 9 / 13 / 40，`shieldHitR` = 10 / 10.5 / 14 / 19 / 40（护盾壳比船体大一圈）。

`command` 列的 **4 / 6 / 10 / 22** 与现有 `state.js` 里的 4 / 10 / 22 一致（多出来的 6 是新增的 2 档护卫舰），所以初始编制仍是 **816 / 900**，换模板表不打破现有平衡。

**关于 L 槽**：`size: "L"` 目前只有防御塔武器（`mountable: false`，玩家装不上）。所以堡垒级从「1×L + 2×M + 1×S」改成「2×M + 2×S」，L 档能力先保留在 schema 里，等首门大型武器上线再开槽。

## 4. 插件模板 PluginTemplate

插件是**唯一能改船体属性**的装配件。设计上它和武器共用插槽系统，但不分尺寸、不参与开火。

### 4.1 字段表

```js
{
  id:        "plugin.shellplate",   // string  唯一键
  name:      "附加装甲",             // string  显示名
  desc:      "焊接上去的一层装甲板", // string  一句话说明（UI 悬浮）
  icon:      "p_shellplate",         // string  图标 key（可选）

  // ---- 三个手填值 ----
  command:   0,                     // int     附加指挥值（默认 0，见 D1）
  buildTime: 1.2,                   // float   附加工时（秒）
  capacity:  3,                     // int     承载占用

  mods:      { hp: 25, hullHitR: 1.5 },   // 属性加成，键名同船体 armor
  abilities: [{ id: "ability.repair_drone", count: 1 }],  // 可空；支援能力，见 支援能力设计.md
  limits:    { maxPerShip: 1 },           // 可选：同一艘船最多装几个
  tags:      ["装甲"]                     // 可选：UI 分类
}
```

| 字段                  | 说明                                                                                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mods`              | 键名**与船体 `armor` 块同名**（`hp` / `hpRegen` / `shield` / `shieldRegen` / `hullHitR` / `shieldHitR`），这样结算就是一句 `for (k in mods) armor[k] += mods[k]`，不需要映射表 |
| `mods.capacity`     | **特例**：加到承载量上限，不是加到 armor                                                                                                                            |
| `mods.fireRate`     | **特例**：开火冷却乘数，多个插件**相乘**，`0.85` = 快 15%                                                                                                              |
| `abilities`         | **支援能力引用**（护盾充能 / 维修）。一个插件可以只带能力、只带 `mods`、或两者都带。字段与规则见 `支援能力设计.md`                                                                                  |
| `limits.maxPerShip` | 缺省无限制；扩容类插件必须限 1，原因见 §6.4                                                                                                                            |
| `tags`              | 纯 UI 筛选，不参与计算                                                                                                                                        |

### 4.2 阶段一插件清单（占位，正式插件系统另做）

| id | 名称 | capacity | buildTime | command | mods | limits |
|---|---|---|---|---|---|---|
| `plugin.capacitor` | 扩容电容 | 5 | 2.0 | 0 | `{ capacity: +6 }` | `maxPerShip: 1` |
| `plugin.shellplate` | 附加装甲 | 3 | 1.2 | 0 | `{ hp: +25, hullHitR: +1.5 }` | — |
| `plugin.deflector` | 偏导护盾 | 4 | 1.6 | 0 | `{ shield: +40, shieldRegen: +2 }` | — |
| `plugin.autoloader` | 自动装填机 | 2 | 0.8 | 0 | `{ fireRate: 0.85 }` | — |

> 支援类插件（护盾充能器 / 维修无人机）不在这张表里，它们带的是 `abilities` 而不是 `mods`，见 `支援能力设计.md`。

### 4.3 一条硬规则：扩容类插件的返还率必须 ≤ 125%

`plugin.capacitor` 花 5 点承载，换 6 点上限，净赚 1 点（20%）。如果哪个插件能做到「给的上限远超它的占用」，玩家就会无限叠它，承载力上限形同虚设。所以：

```
对任何带 mods.capacity 的插件：  capacity（占用） ≥ mods.capacity × 0.8
                                 即 换来的上限 ≤ 花掉占用的 1.25 倍
```

§6.4 的推荐算法直接把这个约束编进去，单测里断言。

## 6. 推荐值算法

### 6.1 设计目标

算法**不是**用来决定最终数值的，而是给出「如果只按这几个可测量的属性来定价，它应该是多少」。所以：

- 每个值有**独立的物理含义**，不共用一个公式硬凑；
- 常数（分母、权重、档位表）集中在一个文件顶部，改常数 = 重新平衡全表；
- 算出的值必须和 §3.4 / §4.2 / §5 的手填值**一致**（否则审计一开始就全是警告，没人看了）。

### 6.2 船体：承载量 → 指挥值 → 建造时间（单向链）

```
① capacity_rec = round( Σ SLOT_VOLUME[槽] × FILL_RATIO )
     SLOT_VOLUME = { weaponS: 5, weaponM: 8, weaponL: 12, plugin: 4 }
     FILL_RATIO  = 0.80      // 留 20% 余量，让玩家必须取舍

② command_rec  = max(1, round( hp/15 + shield/30 + capacity/40 ))
     // 注意 capacity 用**手填值**，不回读 capacity_rec
     // class === "mothership" 时直接返回 0

③ buildTime_rec = round1( command × CLASS_TIME_MUL[class] )
     CLASS_TIME_MUL = { frigate: 2.0, destroyer: 2.6, cruiser: 2.9, mothership: 0 }
```

**为什么链条单向**：承载量是「船有多大」的直接体现，指挥值是「它值多少人口」，工时是「造它多久」。后者依赖前者，前者不依赖后者，所以不会有循环。

验算：

| 船体 | 槽位容积和 | ×0.8 | capacity 手填 | hp/15+shield/30+cap/40 | command | ×系数 | buildTime |
|---|---|---|---|---|---|---|---|
| 矛隼级 | 5+5+4+4=18 | 14.4 → **14** | 14 ✅ | 4.000+0+0.350 = 4.35 | **4** ✅ | 2.0 | **8.0** ✅ |
| 壁垒级 | 8+5+4+4=21 | 16.8 → **17** | 17 ✅ | 5.000+1.000+0.425 = 6.43 | **6** ✅ | 2.0 | **12.0** ✅ |
| 重锤级 | 8+5+5+4×3=30 | 24.0 → **24** | 24 ✅ | 8.667+1.000+0.600 = 10.27 | **10** ✅ | 2.6 | **26.0** ✅ |
| 堡垒级 | 8+8+5+5+4×4=42 | 33.6 → **34** | 34 ✅ | 18.667+2.000+0.850 = 21.52 | **22** ✅ | 2.9 | **63.8** ✅ |
| 方舟级 | 5+4+4=13 | 10.4 → **10** | 10 ✅ | — | **0** ✅ | — | **0** ✅ |

**为什么承载量由槽位布局推**：槽位是「我这条船想装几件东西」的设计声明，承载量是「内部空间够不够」。反过来推（先定 60 点空间，再切 8 个槽）会出现「8 个槽最多装满 40 点，60 点永远用不到」的死值——v1 就有这个 bug。

### 6.3 武器：承载量看体积，工时看效能

**capacity** 取「单发投送能量」，因为装填速度不占空间，口径才占：

```
power   = dmg × (1 + 0.25×(burst−1)) + 0.5×(blastDmg + blastR)
caliber = power ^ 0.6                      // 亚线性：体积不随能量线性涨
capacity_rec = max( SIZE_FLOOR[size], round( 3 × caliber / caliber_laser ) )
     SIZE_FLOOR = { S: 2, M: 5, L: 9 }
     caliber_laser = 24^0.6 = 6.73          // 以激光为 3 点基准
```

**buildTime** 取「综合效能」，因为工时反映的是加工难度：

```
buildTime_rec = round1( capacity × 0.34 × EFFORT )
EFFORT = 1 + 0.10×(maxHits−1) + 0.15×pierceShield
           + 0.10×跟踪 + 0.05×(射程 > 350)
```

验算：

| 武器 | power | caliber | capacity 算 | 手填 | EFFORT | buildTime 算 | 手填 |
|---|---|---|---|---|---|---|---|
| 激光 | 24 | 6.73 | 3.00 → 3 | 3 ✅ | 1.00 | 1.02 → 1.0 | 1.0 ✅ |
| 链炮 | 35 | 8.44 | 3.76 → 4 | 4 ✅ | 1.05 | 1.43 → 1.4 | 1.4 ✅ |
| 导弹 | 64 | 12.13 | 5.40 → 5 | 5 ✅ | 1.15 | 1.96 → 2.0 | 2.0 ✅ |
| 鱼雷 | 54.5 | 11.01 | 4.91 → **5**（M 下限 5） | 5 ✅ | 1.05 | 1.79 → 1.8 | 1.8 ✅ |
| 轨道炮 | 20 | 6.03 | 2.69 → **5**（M 下限 5） | 5 ✅ | 1.35 | 2.30 → 2.3 | 2.3 ✅ |

**这里有个值得注意的地方**：轨道炮按口径算只有 2.7 点，接近激光；它的强度全在「穿盾 + 打 3 个 + 250 射程」上，所以承载量被尺寸下限抬到 5，靠工时（2.3s，全表最高）和后续可能的指挥值加成来体现代价。**这说明承载量只该管「多大」，不管「多强」**——这两件事分开，正好避免"一门好炮占半个船"。

### 6.4 插件：按属性加成定价，并强制扩容返还率

```
modScore = Σ |value| × MOD_WEIGHT[键]
     MOD_WEIGHT = { hp: 0.10,   hpRegen: 0.50,
                    shield: 0.10, shieldRegen: 0.50,
                    hullHitR: 0.65, shieldHitR: 0.65,
                    capacity: 1.00,          // 承载力本身就是货币，按 1:1
                    fireRate: 12.0 }         // |1−v| × 12

capacity_rec  = max(1, round(modScore / 1.2))
buildTime_rec = round1(capacity_rec × 0.4)
command_rec   = 0

// 硬约束：带 mods.capacity 的插件
capacity_rec = max( capacity_rec, ceil(mods.capacity × 0.8) )
```

验算：

| 插件 | modScore | /1.2 | capacity 手填 | buildTime 算 | 手填 |
|---|---|---|---|---|---|
| 扩容电容 | 6×1.00 = 6.00 | 5.00 → 5（返还率 6/5 = 120%，靠 `maxPerShip: 1` 拦） | **5** ✅ | 2.0 | 2.0 ✅ |
| 附加装甲 | 25×0.10 + 1.5×0.65 = 3.475 | 2.90 → 3 | 3 ✅ | 1.2 | 1.2 ✅ |
| 偏导护盾 | 40×0.10 + 2×0.50 = 5.00 | 4.17 → 4 | 4 ✅ | 1.6 | 1.6 ✅ |
| 自动装填机 | 0.15×12 = 1.80 | 1.50 → 2 | 2 ✅ | 0.8 | 0.8 ✅ |

> 扩容电容的账：花 **5** 点占用换 **+6** 点上限，净 +1。这是刻意的「小赚」，因为它同时被 `maxPerShip: 1` 限死，一艘船只能赚一次。如果没有这条限制，返还率 >100% 的插件会被无限叠，承载力上限直接失效——这是整套算法里**唯一必须硬性拦截**的地方。

### 6.5 偏离审计

```js
balanceReport(templates) → [
  { id: "hull.citadel", field: "command",
    value: 22, recommended: 22, drift: 0.00, level: "ok" },
  { id: "railgun", field: "buildTime",
    value: 3.0, recommended: 2.3, drift: +0.30, level: "warn" },
  ...
]

drift = (value − recommended) / recommended
level = |drift| ≤ 0.20 → "ok"
      ≤ 0.50           → "warn"
      否则              → "alert"
```

用途：

| 场景 | 谁看 |
|---|---|
| 新增/修改模板后跑一次 | 写数值的人 |
| 单测断言 `alert` 数量为 0（或显式白名单） | CI |
| 构筑界面里显示 `22 (+0)` / `3.0 (+0.7 ⚠)` 角标 | 玩家看不到，开发期调试面板 |
| 改完 `MOD_WEIGHT` 常数后一键复核全表 | 平衡调整时 |

阈值和「alert 是否阻断」是待定项，见 D9。

### 6.6 初始值 = 推荐值

§3.4 / §4.2 / §5 的表里所有手填值都等于算法输出，所以初始审计是**全绿**。之后手改任何一条，审计会立刻告诉你偏离了多少——这就是「硬编码 + 推荐算法」的完整闭环。

## 7. 舰船模板 ShipTemplate

### 7.1 字段表

```js
{
  id:   "ship.usr_0001",          // string  玩家方案 id
  name: "矛隼-截击型",             // string  玩家可改
  hull: "hull.falcon",            // string  船体模板 id
  fit:  { w1: "missile", w2: null, p1: "plugin.capacitor", p2: null },
  meta: { createdAt, updatedAt, favorite: false, note: "", tags: [] },
  derived: { ... }                // 只读缓存，永远由 computeShip() 重算
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 玩家侧唯一键；建议 `ship.usr_<自增>`，不用时间戳（避免同毫秒碰撞） |
| `name` | string | 允许重名，UI 上靠 id 区分 |
| `hull` | string | 必须是存在的 `hull.*` |
| `fit` | object | **插槽 id → 模板 id**；空槽 `null`；键集合必须与船体槽位集合完全一致 |
| `meta` | object | 纯展示，不参与计算 |
| `derived` | object | 缓存，不进存档（读档后重算一次） |

**`fit` 为什么是对象而不是数组**

`fit: { w1: "missile", w2: null }` 而不是 `[{slot:"w1", item:"missile"}, ...]`：

1. 天然去重：一个槽位不可能塞两件；
2. 改装配就是一次赋值，草稿 diff 极简（与 `setLoadout` 的事务式校验天然契合）；
3. JSON 序列化后人类可读，方便手改存档调试。

风险：槽位被删/改 id 时旧存档会留孤儿键。对策——`computeShip()` 忽略不存在的槽位键，并报一条 `未知插槽 w9`。

### 7.2 `derived` 结构

```js
derived: {
  ok: true, reasons: [],
  capacity:     20,      // 上限（含插件 mods.capacity 加成）
  capacityUsed: 17,      // 占用
  capacityFree:  3,      // 余量（负数 = 超载，ok=false）
  command:       4,      // 占总人口 = hull.command + Σ item.command
  buildTime:    14.8,    // 未除生产线效率
  fireRate:      0.85,   // 开火冷却乘数（多插件相乘）
  armor: { hp, hpRegen, shield, shieldRegen, hullHitR, shieldHitR },  // 含插件加成
  weapons: [ { slot:"w1", id:"missile", name:"导弹", size:"S", capacity:5 } ],
  plugins: [ { slot:"p1", id:"plugin.capacitor", name:"扩容电容", capacity:5 } ]
}
```

**`ok=false` 时 `derived` 仍然要给全**。这样玩家拖进一件装不下的东西时，UI 能立刻用红字显示「承载量 17 / 20」，而不是只弹一句"装不下"。`reasons` 同时给人话原因。

### 7.3 完整算例

```js
{
  id: "ship.usr_0001", name: "矛隼-截击型", hull: "hull.falcon",
  fit: { w1: "missile", w2: "missile", p1: "plugin.capacitor", p2: "plugin.autoloader" },
  derived: {
    ok: true, reasons: [],
    capacity: 20, capacityUsed: 17, capacityFree: 3,
    command: 4,
    buildTime: 14.8,
    fireRate: 0.85,
    armor: { hp: 60, hpRegen: 2.0, shield: 0, shieldRegen: 0, hullHitR: 6, shieldHitR: 10 },
    ...
  }
}
```

逐步核对：
- 上限 `14(船体) + 6(电容) = 20`
- 占用 `5(导弹) + 5(导弹) + 5(电容) + 2(装填机) = 17`，余 3
- 工时 `8.0 + 2.0 + 2.0 + 2.0 + 0.8 = 14.8`
- 指挥值 `4 + 0 + 0 = 4`，**装了两枚导弹也不涨价**（D1 的直接后果，评审时对照感受一下）

## 8. 校验规则清单

`computeShip()` 一次跑完所有规则，**不短路**，这样玩家能一次看到所有问题。

| # | 规则 | 触发条件 | reasons 文案 |
|---|---|---|---|

## 9. 计算流程

```js
function computeShip(tpl, unlocked?) {
  hull = HULL_TEMPLATES[tpl.hull]
  if (!hull) return { ok:false, reasons:["未知船体"], derived: emptyDerived() }

  // ① 逐槽收集，同时校验 V4~V11
  weapons = []; plugins = []; used = 0
  for (slot of hull.slots.weapon) { ...校验...; used += w.capacity }
  for (slot of hull.slots.plugin) { ...校验...; used += p.capacity }

  // ② 先算上限（插件加成），再比对 —— 顺序不可换
  //    否则「扩容电容」会因为自己占 5 点而装不上
  capacity = hull.capacity + Σ plugin.mods.capacity
  free     = capacity - used
  if (free < 0) reasons.push("超出承载量…")

  // ③ 属性结算：船体基础 + 插件 mods
  armor = { ...hull.armor }
  for (p of plugins)
    for (k in p.mods)
      if (k !== "capacity" && k !== "fireRate") armor[k] += p.mods[k]

  // ④ 三个手填值的合成
  command   = hull.command   + Σ item.command
  buildTime = hull.buildTime + Σ item.buildTime

  return { ok: reasons.length === 0, reasons, derived: {...} }
}
```

**幂等性**：`computeShip()` 不改入参、不读时间、不读随机数，同一输入永远同一输出。这条保证「UI 里预览的数字」和「实际造出来的船」必然一致。

## 12. 与蓝图/解锁的关系

解锁记录是**存档状态**，不是模板：

```js
{
  hulls:   Set<string>,   // 已解锁的 hull.* id
  weapons: Set<string>,   // 已解锁的武器 id
  plugins: Set<string>,   // 已解锁的 plugin.* id
}
```

`computeShip(tpl, { unlocked: catalog })` 只在传了 catalog 时才校验 V2/V7/V9。已存的舰船模板如果引用了未解锁装备，校验失败但**不删模板**，只是不允许下单。

占领建筑 → 给蓝图 → 写进 catalog 的流程不在本文范围。
