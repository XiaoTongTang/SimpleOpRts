# 支援能力设计：护盾充能 / 维修（评审稿）

> 关联：`战舰构筑数据结构.md`（模板体系）、`构筑机制设计.md`（防御系统）
> 本文解决两件事：① 把「给友军充护盾」「给友军维修」做成可构筑的模块；② 顺带定掉主文档里悬着的 **D7（护盾来源）**。

---

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 做成插件还是装备？ | **做成插件**，但插件通过一个 `abilities` 字段**引用第三种预设表** `AbilityTemplate` |
| 两种能力要分开设计吗？ | **不分开**。它们是同一个机制的两个参数：`resource: "shield" \| "hull"` |
| 为什么单拉一张表 | 母舰的维修无人机是**船体自带**的（需求原文），必须能挂在船体上；插件只是载体之一 |
| 原来的能量/冷却模型 | **删掉**。改成纯速率模型（`rate` 点/秒） |
| 原来的 `sq.p.chargers` 计数 | **删掉**。改成编译期展开成每艘船的能力实例 |
| D7（护盾来源） | 用「自回 vs 他回」矩阵解决，两套并存但不打架 |

一句话：**支援能力 = 一个作用在友军身上的持续性资源恢复光环，按目标上限封顶。**

## 1. 为什么这两种能力应该统一

「充护盾」和「修血」在实现上是**同一个循环**：

```
找到半径内的友军 → 按某种优先级挑出 N 个 → 每个每秒 +rate 点某资源 → 不超过上限
```

只有三处参数不同：

| 差异 | 护盾充能 | 维修 |
|---|---|---|
| 恢复哪个资源 | `shield` | `hp` |
| 目标有效性判据 | `shield < 护盾上限` | `hp < maxHp` |
| 能否抬高目标上限 | **能**（临时护盾上限，见 §8） | 不能（血量不能超上限） |

所以合成一张表 + 一个 `resource` 枚举，而不是两套代码。好处：

1. **写一遍逻辑**，以后加「修护盾电容」「修能量」之类只加枚举值；
2. **定价模型统一**（都是吞吐量 = rate × 目标数）；
3. **UI 统一**：一个「支援模块」面板，只有「恢复什么」不同；
4. 玩家认知成本低：「支援模块 = 恢复光环」。

## 2. 顺带解决 D7：自回 vs 他回

主文档 D7 卡在「船体护盾回充」和「充能器套盾」两套机制打架。把它们按**作用域**切开就没事了：

| 资源 | **自回**（船体自带，被动，只作用自己） | **他回**（能力模块，主动，只作用友军） |
|---|---|---|
| 血量 | `armor.hpRegen` | 维修能力 |
| 护盾 | `armor.shieldRegen` | 护盾充能能力 |

- 自回**慢**、只对自己、永远生效 → 体现「船体属性」；
- 他回**快**、范围性、必须有模块 → 体现「构筑选择」。

两者作用域完全不同（自己 vs 范围内其他人），不存在同一个盾有两个来源打架的问题。
默认 `includeSelf: true` 时充能器也会照顾自己，那是**两个独立来源叠加**，数值上合法且容易解释。

> 结论：D7 选「A + 拆分作用域」，**不删功能**，只是把全局常量 `G.shieldHp` 那一套换成模块参数。

## 3. AbilityTemplate（能力模板）

### 3.1 字段表

```js
{
  id:          "ability.shield_charger_s",
  name:        "护盾充能器",
  desc:        "给半径内的友军补充护盾并临时抬高护盾上限",

  resource:    "shield",       // enum   shield | hull
  radius:      140,            // number 作用半径（像素）
  rate:        10,             // number 每秒恢复量（**每个目标**，见 D13）
  maxTargets:  2,              // int    单台设备同时照顾几个目标
  grant:       30,             // int    仅 shield：临时提高目标护盾上限（取 max 不叠加）

  includeSelf: true,           // bool   是否也能作用于自己
  select:      "lowestRatio",  // enum   lowestRatio | nearest
  fx:          "shieldlink"    // string 表现层样式 key
}
```

| 字段 | 说明 |
|---|---|
| `resource` | 唯一区分两种能力的字段 |
| `rate` | 纯速率，**没有能量、没有冷却、没有充能次数**。数值直接可读（10 血/秒） |
| `maxTargets` | 单台设备的并行目标数；载体上的 `count` 会乘上去（§4.3） |
| `grant` | 只对 `shield` 有意义。为 0 表示「只回充，不给容量」 |
| `select` | 目标优先级。**默认按血量百分比**，不是绝对血量——否则残血巡洋舰会被满编护卫舰抢光名额 |
| `fx` | 表现层 key，sim 不认识内容，只把它塞进 fx 事件 |

### 3.2 三个示例（阶段一）

| id | 名称 | resource | radius | rate | maxTargets | grant | 定价 capacity | buildTime |
|---|---|---|---|---|---|---|---|---|
| `ability.shield_charger_s` | 护盾充能器·小 | shield | 140 | 10 | 2 | 30 | 4 | 1.8 |
| `ability.shield_charger_l` | 护盾充能器·大 | shield | 200 | 24 | 4 | 60 | 16 | 7.2 |
| `ability.repair_drone` | 维修无人机 | hull | 180 | 8 | 1 | 0 | 3 | 1.4 |

> 维修无人机的 `maxTargets: 1` 是刻意的：**1 架无人机照顾 1 艘船**，母舰的「4 架无人机」就变成 `count: 4`，语义直观（§4.3）。

## 4. 谁携带能力

### 4.1 插件

在插件模板上加一个 `abilities` 数组（可与 `mods` 并存）：

```js
{
  id: "plugin.charger_s", name: "护盾充能器",
  command: 0, buildTime: 1.8, capacity: 4,
  mods: {},                                  // 可空
  abilities: [{ id: "ability.shield_charger_s", count: 1 }],
  limits: { maxPerShip: 2 },                 // 允许装两台（速率叠加）
  tags: ["支援"]
}
```

一个插件可以同时有 `mods` 和 `abilities`：比如「护盾发生器」既给自己 +20 护盾上限，又给友军回充。

### 4.2 船体自带

母舰的维修无人机不再写成 `repairDrones: { count, rate, radius }` 这种一次性字段，而是引用同一张能力表：

```js
// 方舟级 hull.ark
mothership: { ... },
abilities: [{ id: "ability.repair_drone", count: 4 }]
```

这样「母舰的维修无人机」和「插件装的维修模块」**走同一套代码、同一套数值模型**，以后想让母舰也能装充能器，加一行就行。

### 4.3 `count` 的语义

```
生效目标数 = ability.maxTargets × count
生效速率   = ability.rate          （每目标不变，不乘 count）
```

即**多装一台 = 能同时照顾更多目标，而不是把同一艘船修得更快**。
理由：这样「数量」这个旋钮有独立含义，且不会出现「4 架无人机全砸在一艘船上，每秒 32 血」的怪值。

如果要「更快」，换更大的能力模板（`_l` 版本），那是另一条设计轴。

## 5. 叠加与覆盖规则

| 项 | 规则 | 理由 |
|---|---|---|
| 护盾 `grant`（上限加成） | 同帧所有覆盖源**取最大值，不叠加** | 防止 5 台充能器把上限顶到 200 |
| 护盾 `rate` | **相加** | 多台一起回得更快，合理且鼓励集火式保障 |
| 维修 `rate` | **相加** | 同上 |
| 目标名额 | 每台设备**独立**选目标，不共用名额 | 简单，且小设备不会抢大设备的名额 |
| 自己给自己 | `includeSelf` 控制，不受名额限制地多算一个 | 避免「充能器占了自己的名额」这种反直觉 |

## 6. 目标选择规则

```
候选 = 同阵营 && 存活 && 半径内
     && (resource === "hull"   ? hp < maxHp
                              : shield < effectiveCap)     ← 满的不修，浪费
排序 = select === "lowestRatio" ? (hp/maxHp 升序, 距离升序, 单位索引升序)
                                : (距离升序, 单位索引升序)
取前 maxTargets 个
```

**必须带单位索引作为最终 tiebreak**：否则两个血量完全相同的目标会在不同帧之间来回抢名额，护盾量会来回抖。这是纯表现 bug，但很难查。

## 7. 每秒推进

```js
function stepSupport(units, grid, dt, fx) {
  dt = Math.min(dt, 0.05)                     // 掉帧保护，防止一次修复过量

  // ① 清空本帧缓存（护盾上限每帧重算，不缓存，所以没有状态残留）
  for (const u of units) {
    u.gainHp = 0; u.gainShield = 0; u.grantMax = 0
  }

  // ② 收集：先全部累加，不立刻改 hp/shield
  for (const u of units) {
    if (u.hp <= 0 || !u.abilities?.length) continue

    for (const ab of u.abilities) {
      const cand = grid.queryCircle(u.x, u.y, ab.radius)
      // ...按 §6 过滤排序，取前 ab.maxTargets 个（includeSelf 另算）
      for (const t of picked) {
        if (ab.resource === "shield") {
          t.grantMax = Math.max(t.grantMax, ab.grant)
          t.gainShield += ab.rate * dt
        } else {
          t.gainHp += ab.rate * dt
        }
        maybeFx(fx, u, t, ab)                 // 5Hz 节流，见 §10
      }
    }
  }

  // ③ 应用：先算上限，再回充，最后夹紧
  for (const u of units) {
    u.effShieldCap = u.baseShieldCap + u.grantMax
    if (u.gainShield) u.shield = Math.min(u.effShieldCap, u.shield + u.gainShield)
    if (u.gainHp)     u.hp     = Math.min(u.maxHp,        u.hp     + u.gainHp)
    if (u.shield > u.effShieldCap) u.shield = u.effShieldCap     // 光环离开后回落
  }
}
```

三个关键点：

1. **两遍遍历（先累加后应用）**：否则结果依赖 `units` 数组顺序，同一个局面跑两次血量不同——这是最难复现的一类 bug。
2. **`effShieldCap` 每帧从零重算**，不存「我现在被几个充能器照着」这种状态。充能器死了/飞走了，下一帧自动回落。
3. **`dt` 上限 0.05**：否则切标签页回来时一帧跑 5 秒，能瞬间奶满全场。

## 8. 临时护盾上限的生命周期

`grant` 带来的上限是**跟着光环走的**，需要定清楚离开光环时怎么处理：

| 方案 | 行为 | 评价 |
|---|---|---|
| **A（建议）** | 立即 clamp：`shield = min(shield, 新上限)` | 实现最简单，无残留状态。代价是护盾艇一飞走，友军盾条瞬间掉一截 |
| B | 超出部分按固定速率衰减（如 20/s） | 观感好，但要多存一个「衰减中」状态 |
| C | 充能器不 `grant`，只回充 | 模型最简，但「纯护盾艇」这个构筑流派就做不出来（目标没护盾容量时充能器无效） |

我建议 **A**：护盾艇必须跟着舰队，这本身是合理的战术约束，而且实现上没有状态残留。
如果后面觉得视觉太突兀，再换成 B，只是加一个字段的事。

## 9. 定价

沿用主文档「硬编码 + 推荐值」的框架，能力模板本身不挂载，所以 `capacity` / `buildTime` 记在**载体（插件）**上，但由能力的吞吐量算出推荐值。

```
grantTerm   = grant × 0.5                    // 仅 shield，纯回充时为 0
throughput  = rate × maxTargets + grantTerm
capacity_rec  = max(1, round(throughput / 8))
buildTime_rec = round1(capacity_rec × 0.45)   // 比同容量武器略贵：持续收益没有 CD 空窗
command_rec   = 0
```

验算：

| 能力 | rate×目标 | grantTerm | throughput | capacity | buildTime |
|---|---|---|---|---|---|
| 充能器·小 | 10×2 = 20 | 15 | 35 | 4.4 → **4** | 1.8 |
| 充能器·大 | 24×4 = 96 | 30 | 126 | 15.8 → **16** | 7.2 |
| 维修无人机 | 8×1 = 8 | 0 | 8 | 1.0 → **1** | 0.5 |

> 维修无人机单台只有 1 点承载，看着很便宜——但母舰装 4 架就是 4 点，而且 `count` 不计入船体的装配承载（船体自带的模块不占插件槽，这也是母舰强度的一部分）。

载体（插件）的推荐值：

```js
capacity_rec  = max(能力 capacity_rec, mods 算出的 capacity)   // 两者取大，不叠加
buildTime_rec = 能力 buildTime_rec + mods buildTime_rec         // 工时相加
```

因为 `mods` 和 `abilities` 是两类不同的收益（静态属性 vs 持续支援），**承载取大是为了不让「双修」插件变成性价比之王**，工时可加则是合理的加工成本。

## 10. 表现层

现在的实现是「套盾瞬间发一对 `shieldlink` + `shieldup`」，改成持续恢复后不能每帧发，否则 fx 列表会被打爆。

| 场景 | 样式 | 频率 |
|---|---|---|
| 充能中 | 从充能器到目标一条低透明度青色弧线 + 目标护盾环内侧缓慢收拢 | 每对（源→目标）**最多 0.4s 一次** |
| 维修中 | 绿色短线 + 目标身上小十字微光 | 同上 |
| 目标已满 | **完全不发** | — |

「目标已满不发」很重要：一支 24 艘编队全程被照射，如果不管这个，屏幕上会永远飘着线。

## 11. 与现有代码的差异

| 现状 | 目标 |
|---|---|
| `G.shieldHp / chargerRange / chargerCd / energyMax / energyCost / energyRegen` 7 个全局常量 | **删除**，进能力模板 |
| `sq.p.chargers`（小队面板滑块）+ `u.charger = idx < p.chargers` 按索引分配 | **删除**，编译期展开成 `u.abilities[]` |
| `u.energy / u.castCd` | **删除**，纯速率模型 |
| `stepChargers(units, squads, G, dt, fx)` | 换成 `stepSupport(units, grid, dt, fx)` |
| 套盾 = `best.shield = G.shieldHp` 瞬时满 | 按 `rate×dt` 累积，上限由 `baseShieldCap + grantMax` 决定 |
| `defense-system.js` 里 `initCombat` 用 `idx` 分配充能器 | 删除，能力来自 `compileShip()` 的编译结果 |
| `render-units.js` 的 `if (u.charger)` 画环 | 改成 `if (u.abilities.some(a => a.resource === "shield"))` |
| `templates.js` 里每个模板的 `chargers: n` | 删除，改成模板级的舰船模板引用 |

**迁移建议**：这次改造可以和数据模板一起做，因为 `stepChargers` 本来就要重写。但注意它是**会改变战场表现**的（原来是「每 2.5 秒给一个人套满 80 盾」，现在是「10/s 持续回」），建议先在一份可回滚的分支上跑，用 fix 的随机种子对比两份录像。

## 12. 需要拍板的决策点

| # | 决策点 | 本文建议 | 备选 |
|---|---|---|---|
| **D11** | 充能器是否 `grant` 临时护盾上限 | **是**（能做纯护盾艇流派） | 只回充，要求目标本身有护盾容量 |
| **D12** | 光环离开后超出的护盾怎么处理 | **立即 clamp** | 按 20/s 衰减 |
| **D13** | `rate` 是「每目标」还是「总量分摊」 | **每目标**（数值直观） | 总量分摊（更真实，但玩家算不清） |
| **D14** | `count` 影响目标数还是速率 | **目标数**（一架无人机照顾一艘船） | 影响速率（4 架全砸一艘船） |
| **D15** | 要不要独立的「系统槽」 | **不要**，共用插件槽 | 独立槽位，支援舰不能同时堆武器 |
| **D16** | 是否保留能量/冷却模型 | **不要**，纯速率 | 保留电量，模块有使用窗口 |
| **D17** | 支援模块是否也吃指挥值 | **不吃**（`command: 0`） | 吃，防止支援舰满编不吃人口 |

## 13. 这套设计为什么符合项目原则

项目的核心是「增强单位与小队的自主性，靠涌现行为减少操作量」。支援能力正好是这个原则的典型：

- **玩家只决定「带几艘支援舰、带哪种」**，不决定「什么时候治疗谁」；
- 目标选择（血量百分比最低优先）由系统自动完成，且规则单一可预期；
- 多艘支援舰之间的覆盖是**空间关系自然产生**的：舰队越密集保障越强，散开就照顾不到——不需要任何额外的"阵型"机制；
- 「护盾艇贴着舰队走」这种战术，是从 `radius` 和移动系统**涌现**出来的，不是写死的规则。

所以这类能力适合做成**被动光环**，而不是需要点技能（那会增加微操）。

## 14. 不做的事

1. **建筑维修**：目前没有建筑，`targetKind` 字段先不加。
2. **护盾过载 / 弹幕拦截 / 加速光环**：schema 留了 `fx` 和 `resource` 两个扩展点，但这次不设计。
3. **能量系统**：整套删掉（D16）。
4. **支援能力的蓝图解锁链路**：和武器/插件一致，走 `PlayerCatalog.plugins`。
5. **多能力叠加的 UI 优先级**：先不做，等真有多模块船再说。
