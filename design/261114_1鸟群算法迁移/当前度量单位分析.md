## 0. 一句话结论

**是同一个单位（世界像素），但不是同一个尺。**

模拟里只有一套坐标：`x / y` 单位是**世界像素**，没有任何比例因子、没有 DPR、没有视口尺寸参与运算。
真正的问题不是"单位不同"，而是**三层数据之间换算关系不自洽**：

| 层         | 成员                                        | 是否必须自洽                        |
| --------- | ----------------------------------------- | ----------------------------- |
| **物理层**   | 单位半径、分离间隙、对齐区、凝聚区、威胁/感知区、武器射程、弹丸接触半径、速度、力 | **必须**（目前基本自洽）                |
| **空间离散层** | 地图格子、空间索引格子                               | 只与精度有关，与物理无关                  |
| **表现层**   | 贴图展示尺寸、血条、护盾环                             | 只需"看着合理" —— **本次决定把它收到与物理一致** |

## 3. 唯一的尺度换算点：相机

```
世界坐标 ──cameraView()──▶ 屏幕坐标
            ox / oy / zoom
屏幕坐标 ──renderer──▶ 设备像素（× devicePixelRatio）
```

`cameraView()` 返回的 `{ ox, oy, zoom }` 是**全项目唯一**把世界像素映射到屏幕的地方，且它是纯观察状态：
不参与模拟、不进快照、不落盘（见 `core.js` 注释「相机是观察状态」）。渲染器把 `world.scale = zoom` 一设，
之后所有绘制都用世界坐标。

所以：**物理层内部没有隐式缩放，表现层通过同一个 `zoom` 缩放。**

## 4. 三处「同单位、不同尺」

### 4.1 贴图宽度 vs 碰撞直径（已决，见 §5）

`sizeOf(u) = 14 + hitR × 2.6`（夹 22–64），而碰撞直径是 `2 × hitR`。两者比值不是常数：

| 舰型 | `hitR` | 碰撞直径 | 旧 `sizeOf` | 比值 | 贴图半宽 − 半径 |
|---|---:|---:|---:|---:|---:|
| 矛隼 | 6 | 12 | 29.6 | **2.47×** | 8.8 px |
| 壁垒 | 6.5 | 13 | 30.9 | 2.38× | 8.95 px |
| 重锤 | 9 | 18 | 37.4 | 2.08× | 9.7 px |
| 堡垒 | 13 | 26 | 47.8 | 1.84× | 10.9 px |
| 母舰 | 40 | 80 | 64（夹顶） | 0.80× | −8 px |

**后果分两种，严重程度差一个量级：**

- **船 vs 船**：视觉重叠，但玩家会读成"贴得紧"，可接受；
- **船 vs 墙**：贴图有 8.8–10.9 px 插进墙里，是**肉眼可见的穿模**，不可接受。

### 4.2 同一参数组里混着两种度量

```
sepRadius       = 表面间隙   gap = d − (r_i + r_j)
alignRadius     = 圆心距
cohRadius       = 圆心距
r4 / r5         = 圆心距
武器射程         = 圆心距（代码里是 d² < range²）
```

这是「每鸟半径」功能的必然代价（分离必须按间隙，否则两个大个体永远在分离区里），
但**同一张参数表里两种度量并存**是调参错误的高发点。

**决定：保留现状，但把恒等式写进代码注释与调参面板：**

```
分离触发的圆心距 = r_i + r_j + sepRadius      // 两个 6 号船 = 12 + 8 = 20
其余所有半径      = 圆心距，不减去半径和
```

### 4.3 地图格子（8 px）比单位半径（6–13 px）还小

对**碰撞**无害：8 px 是几何离散化的精度，倒角多边形按精确几何求解、不按格心，不会出现"格比船小就穿"。

对**流场**有一个已知缺陷：Dijkstra 只知道格子通/不通，不知道**宽度**。
一条 1 格宽（8 px）的缝在流场里是「可通行」，而 r = 6 的船要 12 px 宽才过得去 ——
理论上船会被引到窄口顶着墙。

**决定 D3：流场照做，但建场时不膨胀墙体 —— 寻路不感知船宽。**
本次不做的是「按船宽修正可通行性」这一层，不是流场本身。具体不做三件事：

1. 不对 `walls` 做膨胀（`k` 格方形膨胀）；
2. 不在地图规范里写走廊宽度约束；
3. 不加运行时"卡住/顶着墙"检测。

理由：

1. 现阶段**没有一张带墙的地图**。默认地图是空图，唯一的墙是世界边框；空图上的流场与「直线指信标」等价，
   这个问题**不会显现**。
2. 膨胀是**有代价的**：8 px 格膨胀 1 格会把所有走廊吞掉 16 px，等于强制地图至少 3 格宽。
   在地图设计还没开始的时候先定死这条，可能反过来限制关卡表达。
3. 它是**纯几何问题**，与 Couzin 力模型、每鸟半径、IIR 滤波都不耦合。
   等真出现窄走廊地图、并且实测到"顶着墙"之后再加，改动范围只在一个函数里，不会返工。

**已知后果（记录在案，不当 bug 处理）：**

| 场景 | 表现 |
|---|---|
| 地图里出现 1–2 格宽（8–16 px）的缝 | 流场认为可通行，船挤到窄口顶着墙，靠分离力散开，再到别处去（不会死锁，但会绕远） |
| 地图里出现 < 1 格宽（不可通行）的缝 | 正常，流场本来就不会选 |

**将来要补的时候，位置是**：`flow-field.js` 里建场前对 `walls` 做一次膨胀
（`k = ceil(minRadius / cellSize)` 格的方形膨胀），只影响寻路用的那张位图，**不动碰撞用的原图**。
膨胀之外的部分（Dijkstra、方向回填、每队一张场、共享缓存）都不受影响。

## 5. 决策 D1：表现层向物理层对齐

### 5.1 决策内容

**`sizeOf` 不再是 `14 + r × 2.6`，而是让「贴图里船体的横向可见宽度」正好等于 `2 × radius`。**

这样：

- 横向半宽 == 碰撞半径 ⇒ **墙边穿模归零**；
- 船与船的视觉间隙 == `sepRadius`，看到的和算到的一致；
- 玩家不需要在两套尺度之间换算。

### 5.2 为什么不能字面写 `sizeOf = 2 × radius`

量了素材（`frigate.png`，8×8 格、每格 32×32、**不透明像素包围盒**）：

```
包围盒宽度: min 14  中位 18  max 20   （分布 {14, 16, 18, 20}）
包围盒高度: min 26  中位 27  max 28   （分布 {26, 27, 28}）
填充率:     中位 32.8%（最大 37.1%）
水平居中偏移 |cx|: 全部 0.00（精确居中）
垂直居中偏移  cy : +0.50（整体低半像素）
PNG 头: 256×256, bitDepth 8, colorType 6 (RGBA), 非交错
```

**素材有透明边距**：船体只占格子的 18/32 = 56%。所以字面 `sizeOf = 2r` 得到的是：

| 舰型 | `radius` | 字面 `2r` | **实际可见船体** |
|---|---:|---:|---|
| 矛隼 | 6 | 12.0 | **6.8 × 10.1** |
| 壁垒 | 6.5 | 13.0 | 7.3 × 11.0 |
| 重锤 | 9 | 18.0 | 10.1 × 15.2 |
| 堡垒 | 13 | 26.0 | 14.6 × 21.9 |

6.8 px 的船在铺满全图时约为 **3.7 屏幕像素** —— 那不是船，是一个点。

### 5.3 正确公式

把透明边距除回去：

```js
sizeOf(u) = 2 * u.radius * (cellW / bboxW)      // 矛隼: 12 × 32/18 = 21.3 px
```

验证：横向半宽 = `(bboxW / cellW) × sizeOf / 2 = radius` ✔

最终尺寸：

| 舰型 | `radius` | 旧 `sizeOf` | 新 `sizeOf` | 可见船体 | 变化 |
|---|---:|---:|---:|---|---:|
| 矛隼 | 6 | 29.6 | **21.3** | 12 × 18 | −28% |
| 壁垒 | 6.5 | 30.9 | 23.1 | 13 × 19.5 | −25% |
| 重锤 | 9 | 37.4 | 32.0 | 18 × 27 | −14% |
| 堡垒 | 13 | 47.8 | 46.2 | 26 × 39 | −3% |
| 母舰 | 40 | 64（夹顶） | 142 | 80 × 120 | +122% ⚠️ |

**注意变化集中在小船**（−28%），堡垒几乎不动。所以整体队形观感不会缩水。
船长（`bboxH`）仍是宽度的 1.5 倍，会沿航向伸出碰撞圆 —— 这是对的：撞墙的是圆，只包横向宽度。

## 6. 决策 D2：贴图度量数据外置为 JSON

### 6.1 决策内容

**不在游戏的 `loadShipAtlas()` 里量像素**，而是**离线用工具统一量好，写进每张图旁边的 JSON**；
运行时只读 JSON。

理由：

1. 运行时量 64 格 × 1024 像素要逐像素读 `getImageData`，在 `loadShipAtlas()` 里是一次额外的
   离屏 canvas 往返，且和 `brighten()` 那个提亮拷贝混在一起，逻辑变脏；
2. 度量是**素材的属性**，不是运行时的行为。素材改了重跑工具即可，游戏代码不用动；
3. JSON 可以被美术/工具链/校验脚本共用（例如"这格是不是空帧"、"这格是不是偏心"）；
4. 运行时零成本：直接读一个字段。

### 6.2 文件位置与命名

```
public/imgs/frigate.png        ← 素材
public/imgs/frigate.json       ← 同名 sidecar
```

命名规则：**同目录、同主名、扩展名换成 `.json`**。`loadShipAtlas()` 由图片 URL 推出 JSON URL，
所以以后加第二张图集不用改代码。

### 6.3 Schema（`sprite-atlas/1`）

```json
{
  "schema": "sprite-atlas/1",
  "image": "frigate.png",
  "width": 256,
  "height": 256,
  "cell": { "w": 32, "h": 32, "cols": 8, "rows": 8 },
  "alphaThreshold": 24,
  "frames": [
    { "bbox": [7, 3, 24, 29], "w": 18, "h": 27, "cx": 0, "cy": 0.5 },
    { "bbox": [8, 3, 23, 29], "w": 16, "h": 27, "cx": 0, "cy": 0.5 }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `schema` | 版本号，运行时校验，不匹配就回退兜底 |
| `image` | 源文件名，用于校验读到的 JSON 是不是配错图 |
| `width` / `height` | 图片像素尺寸，必须等于 `cell.w × cols` |
| `cell` | 网格切分参数（`ship-sprites.js` 的 `CELL / COLS / ROWS` 改为从这里读） |
| `alphaThreshold` | 判定"不透明"的 alpha 阈值（24） |
| `frames[i].bbox` | 该格内的不透明包围盒，`[minX, minY, maxX, maxY]`，**相对格子左上角、含端点** |
| `frames[i].w` / `h` | 包围盒宽高（预计算，运行时不做减法） |
| `frames[i].cx` / `cy` | 包围盒中心相对格中心的偏移，未来做"视觉中心对齐物理中心"用（当前全部 ≤ 0.5 px，可以先忽略） |

空帧写成 `{ "bbox": null, "w": 0, "h": 0 }`，加载时跳过（当前 `frigate.png` 64 格全有内容）。

### 6.4 工具

```
node tools/measure-sprites.mjs public/imgs/frigate.png
node tools/measure-sprites.mjs public/imgs        # 目录形式，批量处理 *.png
```

- **零依赖**：PNG 解码用 Node 内置 `zlib` 手写（本项目 `colorType = 6`、8 bit、非交错，
  只需 `IHDR` 解析 + `IDAT` inflate + 五类 filter 反滤波，约 80 行）；
  遇到不支持的格式（调色板、16 bit、交错）直接报错并说明原因。
- 输出与源文件同目录、同主名。
- 建议加进 `package.json`：`"sprites": "node tools/measure-sprites.mjs public/imgs"`，
  素材更新后跑一次。

### 6.5 运行时用法

```js
// ship-sprites.js
const meta = await fetch(jsonUrl).then(r => r.json());   // 失败 → null，走兜底
// ...
frames.push(Object.assign(texture, {
  cellW: meta.cell.w,
  bboxW: meta.frames[i].w,
  bboxH: meta.frames[i].h
}));

// 一艘船画多大（世界像素）
export function sizeOf(u, tex) {
  const r = u.hitR === undefined ? 6 : u.hitR;
  const k = tex?.bboxW > 0 ? tex.cellW / tex.bboxW : FALLBACK_K;  // FALLBACK_K = 32/18 ≈ 1.78
  return 2 * r * k;
}
```

- 调 `sizeOf` 的两处：`drawUnits()`（有 `v`）与 `drawBars()`（没有 `v`，重算一次 `variantOf`，
  那是一段十几字符的 FNV，200 艘船的开销可忽略）。
- **JSON 缺失时**回退到中位系数 `1.78` 并打一条警告：游戏必须能跑，但墙边会残余 ±11% 的宽度误差。

## 7. 连带影响清单

### 7.1 代码要改的

| 文件 | 改动 |
|---|---|
| `src/render/ship-sprites.js` | `sizeOf()` 换公式；`loadShipAtlas()` 读 sidecar JSON；`CELL/COLS/ROWS` 从 JSON 取；删掉 22–64 的 clamp |

| `tools/measure-sprites.mjs` | 新建 |
| `public/imgs/frigate.json` | 新建（工具产出） |

### 7.2 数值要改的

| 位置 | 旧 | 新 | 原因 |
|---|---|---|---|
| `form.standard` 的 `sepRadius` | 8 | **5** | 当初抬到 8 的唯一理由是「30 px 贴图显得挤」；现在贴图 21 px、半径 6，5 px 间隙正好等于分离间隙。**换算表里唯一的手调值消失，四套阵型全部回到机械换算值** |
| 血条 `BAR_W = 14` | — | 不动 | `max(14, 21.3 × 0.72) = 15.3`，与旧值基本一致 |
| 血条 `BAR_DY = -5` | — | 不动 | 船半高仍 > 5 |

### 7.3 不受影响的

- **物理层全部**：分离、对齐、凝聚、威胁、寻敌、命令、墙体碰撞、武器射程、弹速 —— 一个数字都不变；
- **确定性**：`sizeOf` 只被渲染层调用，`core/` 里搜不到它；
- `variantOf()` 的哈希口径（`maxHp | hitR | 武器数`）。

## 8. 未决

### 8.1 母舰（`hull.ark`，`hullHitR = 40`）

新公式给出 `sizeOf = 142 px`，是地图宽的 7%，且要把 32 px 的素材放大 4.4 倍，会很糊。三条路：

| 方案 | 结果 | 代价 |
|---|---|---|
| A. 保留 clamp（如 96 px） | 贴图缩到 96 px，可见半宽 = `96 × 18/32 / 2` = **27 px** | 碰撞半径 40 > 可见半宽 27 ⇒ 碰撞圆比船大 13 px，玩家会觉得「还没碰到就被弹开」，是反向穿模 |
| B. 把 `hull.ark.hullHitR` 降到 ~20 | `sizeOf = 71 px`，自洽 | 母舰的命中盒变小，武器更容易打偏；但它现在**根本没上场** |
| C. 母舰走独立规则（不参与群体力场、贴图不按半径推） | 干净 | 需要一层"母舰特例"，本次不引入 |

**建议 B**：`hullHitR` 本来就是"一个够用的命中盒"，不是船体尺寸；母舰 3000 血的体积感靠贴图尺寸表达就够了。
但这件事等母舰真要上场时再定，现在只在文档里记账。

### 8.2 地图走廊宽度 —— 已按 D3 关闭，不是未决项

按 §4.3 的 D3，本次不膨胀、不做走廊规范，但**流场照做**。
留一句提醒：将来补膨胀时，`k = ceil(minRadius / cellSize)` 依赖"最小半径"这个量，
当前最小 `hitR = 6`（`cellSize = 8` ⇒ `k = 1`）；如果以后出现 `hitR < 4` 的小艇，`k` 仍是 1，
但那时要重新核算"多少格宽才算可通行"。
