### 1.1 逐项边界

**M1 质量速度模型力场** —— 迁的是**力的语义与积分方式**，不是参数值。
沙盒是 1200×1200 的空场、60 只鸟、无战斗；项目是 2000×1200、约 184 艘船、有武器系统。
所以 `sepForce = 60` 这种数字**不能照抄**，必须按第一段的换算公式重新标定（见 §3.1.2）。

**M2 每鸟半径** —— 半径来源唯一：`hull.armor.hullHitR`（受击半径）。
这一个数同时喂给：分离力的间隙判据、墙体硬碰撞、出生点检查、武器命中判定（本来就在用）、贴图尺寸。
**不迁**沙盒里的「体型分布面板」（按份额配置半径档位）—— 项目的半径由舰船方案决定，不需要人工配份额。

**M3 IIR 低通** —— 只迁滤波**算法与接入点**。沙盒里是双滤波器对照（1€ / IIR + 监视器 + FFT 频谱图），
1€ 部分**按你的结论直接废弃，不迁**。

**M4 流场** —— 迁「每队一张场」的数据结构与调度。沙盒是全局单信标单张场，项目要改成每小队一份，
且必须解决 10 支小队各要一张场时的构建耗时（实测见 §3.4.4）。

**M5 地图导入** —— 迁 JSON 格式与校验规则（`0` 空地 / `-1` 墙 / 可选 `width` `height`），
保证沙盒里做过的地图能直接复用。**不迁**沙盒的贴图重建（`rebuildMapTexture`，那是 canvas2d 的离屏纹理），
项目用 Pixi，墙用 Graphics 画。

**M6 墙体硬碰撞** —— 圆 × 倒角多边形（chamfer）的推出 + 去法向速度 + 子步进。
这是整套东西里**唯一有数学推导**的部分。倒角（地图平滑）单独成节见 §3.6.4 ——
它既是手感问题（90° 台阶会让船"顿一下"），也是视觉问题（方格边缘不像墙），
沙盒的实现有两个缺陷需要一起修。

### 2.2 现有移动模型到底哪里「不是质量速度」

这是本次迁移的**唯一实质**。逐项对照：

| 维度 | 现状（`group-layer.js`） | 沙盒（质量速度模型） |
|---|---|---|
| 力的语义 | 每个力写成 `w · (v_目标 − v)`，即**速度配平**；`w` 的量纲是 1/s | 每个力写成 `F`，量纲是 px/s²；彼此**直接相加** |
| 分离 | `F = wSep · (SPD·û − v)`，强度 `w = (1 − d/rRep)²` | `F = sepForce · Σ (sepRadius/g)² · (−û)`，**无目标速度** |
| 对齐 | 邻居**速度**的加权平均，再和 `v` 配平 | 邻居**朝向单位向量**之和，再和**自身朝向**配平 |
| 凝聚 | 质心方向 · `SPD`，再和 `v` 配平 | `cohForce · normalize(Σ dx)`，**方向归一、幅值固定** |
| 积分 | `v += F·dt`，然后 `v *= exp(−drag·dt)`，再把速度模长夹到 `SPD` | `v += (F/mass)·dt`，然后 `v *= exp(−damping·dt)`，**不夹速度** |
| 加速度上限 | `MAX_ACCEL = 430` 硬夹 | **无**（靠 `SEP_MAX_WEIGHT` 与阻尼兜） |
| 停滞 | `stallSpeed = 60` 以下沿当前朝向补 `stallAccel = 100` | 同构（`boostSpeed` / `boostForce`） |
| 边界 | 软推（70px 缓冲、`BK = 7`）+ `core.step` 硬夹到 `[8, W−8]` + 速度翻转 | 圆 × 多边形硬碰撞，推出 + **只去法向速度**（切向保留，所以会沿墙滑） |

**关键洞察：`w` 与 `F` 不能一一对等。**
老模型里 `wSep/wAli/wCoh/wCmd` 本身**就是速度弛豫增益**（单位 1/s），它让速度快速收敛到目标；
新模型里没有这种内禀增益，收敛全靠 `damping`。所以换算时必须同时定 **`damping`（定响应快慢）**
和 **各力幅值（定稳态速度与力的比例）**，两者不能独立选。推导见 §3.1.2。

### 2.3 现有的分组结构（迁移必须原样保住）

`stepUnits` 里今天已经实现了你要的「小队内对齐凝聚、其余只分离」，代码只有三行：

```js
const same = sq.loose
  ? (oFaction === myFaction && !o.obstacle)   // 散兵：认同阵营
  : (mine === o.squad);                        // 正规小队：只认自己队

if (d < rRep) { /* 分离：全局，不分小队不分阵营 */ }
if (enemy) { /* 威胁 r4 / 寻敌 r5，只对敌方 */ continue; }
if (!same) continue;                           // 友军但不亲和 → 到此为止
/* 对齐 rOri / 凝聚 rAtt */
```

外加两条**小队级**的通道：

- `computeSquadTargets()`：正规小队每帧算一个 `r5` 内敌人的 `1/d²` 加权质心，全队朝**同一个点**推进
  （不这么做队头队尾会分叉，凝聚力救不回来 —— 见 `design/己方与敌方Couzin算法设计.md` §三）；
- `sq.goal`：命令信标，走 `omega × wCmd`。

**这四组结构（分离全局 / 亲和分阵营或分队 / 战斗只对敌 / 全队共享目标点）是项目已经调通的手感，
M1 只换"力怎么算怎么积分"，这四组判定原样保留。**

## 三、怎么和现有机制兼容

### 3.0 总原则

1. **一次只换一层，每层能单独回退。** 每阶段结束跑全套 `pnpm test`，任何一项红就停下来。
2. **不动对外契约。** `core.step / getView / snapshot / command` 四个方法签名不变（`command` 只加新 type）。
   渲染层继续"只读 view"。
3. **判定逻辑不重写，只换力的算式。** `same` 判定、统一寻敌、`alpha` 统计、`fx` 推送全部原样保留。
4. **确定性优先于性能。** 所有"每帧做多少活"的调度都必须是**定数**（第 N 张场 / 第 N 个单位），
   不许按毫秒决定 —— 否则 `determinism.smoke` 立刻红。
5. **迁移期间只验逻辑，不验数字。** 每一步的验收都是"力算得对不对、加得对不对、谁对谁算"，
   **不是**"速度和旧模型像不像"。旧的参数基线一律不对齐；新模型的参数调优在迁移完成之后
   **整体重做**（见 §3.1.2 的方框说明）。`behavior.bench` 只记录、不判定。

### 3.1 M1：力模型怎么换

#### 3.1.1 新参数组

`sq.p` 的移动参数从 12 个键换成 13 个键。**半径类参数沿用原名**（`r4 / r5` 不动），
**权重类参数全部换成"力"**（改名，杜绝"这两个 w 是一回事"的误读），
**另有两个原本属于全局的键下沉进小队**：

| 新键 | 单位 | 含义 | 旧键 / 来源 |
|---|---|---|---|
| `sepRadius` | px | 分离区阈值 —— **表面间隙**，不是圆心距 | `rRep` |
| `alignRadius` | px | 对齐区（圆心距） | `rOri` |
| `cohRadius` | px | 凝聚区上限（圆心距） | `rAtt` |
| `sepForce` | px/s² | 分离合力系数 | `wSep` |
| `alignForce` | px/s² | 对齐力 | `wAli` |
| `cohForce` | px/s² | 凝聚力 | `wCoh` |
| `threatForce` | px/s² | 威胁力（躲远） | `wThreat` |
| `seekForce` | px/s² | 寻敌力（靠近） | `wSeek` |
| `commandForce` | px/s² | 命令力 | `omega × wCmd` |
| `arriveR` | px | 命令力的到达衰减半径 | **原 `G.arriveR`（全局）** |
| `smallPushShare` | % | 大个体受小个体分离力的比例（0–100） | **沙盒的全局参数** |
| `r4` | px | 威胁区半径 | 不变 |
| `r5` | px | 感知 / 寻敌区半径 | 不变 |

`omega / wCmd` 合并成 `commandForce`：现有 4 套阵型和 7 套模板里 `omega = 1.10`、`wCmd = 1.20` 是**常量**，
两个键从来没有单独调过，留着只是多两个自由度。

**为什么 `arriveR` 和 `smallPushShare` 必须在小队里** —— 这两个都是**战术决策**，不是物理常数：

- `arriveR`：冲锋队要"一头扎进去"（小），驻守队要"提前收油、在区域边缘停住"（大）。
  它是"这支队伍怎么收尾"的问题，全局一个值等于所有队伍用同一种停车方式。
- `smallPushShare`：它在回答"**是大船围绕小船，还是小船围绕大船**"。
  `100` = 互相推，队形按尺寸自然分层；`30` = 大船压阵、小船绕着大船散开；`0` = 大船完全不理会小船。
  这是编队战术，不是船体物理 —— 一支护卫队和一支突击队就该有不同取值。

全局参数（`core.G`）：

| 键 | 值 | 含义 |
|---|---|---|
| `damping` | **1.5**（起点） | 粘性阻尼 λ（1/s），替代旧的 `drag = 0.30` |
| `mass` | **1**（起点） | **全局质量**：`a = F / mass`，所有单位共用（见 §3.2.5） |
| `boostSpeed` | 60 | 低速助推阈值（沿用 `stallSpeed`） |
| `boostForce` | 100 | 低速助推力（沿用 `stallAccel`） |
| `maxSpeedFactor` | 1.8 | 安全阀，速度上限 = `1.8 × 巡航速度` |
| `radiusAffectsWalls` | true | 半径是否参与墙碰撞（对照开关，见 M2/M6） |

> `mass` 在量纲上是"力的总缩放"，与把所有 `*Force` 同乘一个系数等价。
> 它单独存在的价值有两个：① 调手感时只拧一个总闸，不用改 6 个力；② 它是
> **将来做每船质量时的落点** —— 那时 `u.mass = f(radius)`，`G.mass` 退化成全局基准值。
> 起点取 1，**意味着迁移本身不改变任何东西**。

#### 3.1.2 从旧参数换算（一次性，用完即删）

第一性的换算是：**要让稳态速度对上，力的幅值必须等于"旧增益 × 巡航速度"**。

新模型单通道稳态：`v* = F / (mass · λ)`（由 `v ← (v + F/mass·dt)·e^{−λ·dt}` 得，一阶近似；`mass = 1` 时即 `F / λ`）。
老模型单通道稳态：`v* = w · SPD / (w + drag)`。

两式相等、并令 `SPD = 96`、`λ = drag + w` 时，解出 `F = w · SPD`。所以：

```
sepForce   = wSep   × SPD
alignForce = wAli   × SPD
cohForce   = wCoh   × SPD
threatForce= wThreat× SPD
seekForce  = wSeek  × SPD
commandForce = omega × wCmd × SPD
sepRadius  = rRep − 2 × r_ref        （r_ref = 6，场上的主力半径，占 166/208）
alignRadius = rOri                   （判据没变，直接沿用）
cohRadius   = rAtt                   （同上）
damping     = 1.5                    （见下）
mass        = 1                      （全局，迁移不改任何东西）
arriveR     = 46                     （原全局值，逐队沿用）
smallPushShare = 30                  （沙盒默认值）
```

照此换算 4 套阵型（`arriveR` 全部 46、`smallPushShare` 全部 30，这两列是战术旋钮，
先按原值铺平，阶段 7 再按兵种分化）：

| 阵型 | sepRadius | alignRadius | cohRadius | sepForce | alignForce | cohForce | threatForce | seekForce | commandForce | r4 | r5 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `form.standard` | 5 → **8** | 46 | 86 | 144 | 91 | 110 | 144 | 144 | 127 | 80 | 300 |
| `form.guerrilla` | 22 | 64 | 120 | 96 | 48 | 43 | 115 | 82 | 127 | 200 | 350 |
| `form.dense` | 23 | 60 | 104 | 101 | 48 | 139 | 192 | 96 | 127 | 55 | 270 |
| `form.wide` | 18 | 58 | 200 | 134 | 67 | 67 | 163 | 154 | 127 | 60 | 280 |

`form.standard` 的 5 被手动抬到 8：`17 − 12 = 5` 意味着两只矛隼表面只隔 5px 就触发分离，
而 `sizeOf()` 给矛隼画的贴图宽约 30px —— 换算值在**机制上等价**，在**视觉上明显偏挤**。
这一格是纯手感值，阶段 2 实测后再定。

**`damping = 1.5` 的来历**：老模型里命令通道的响应时间常数是 `1/(wCmd·omega + drag) = 1/1.62 ≈ 0.62 s`。
新模型里唯一的弛豫就是阻尼，所以 `λ ≈ 1.62`；取整到 **1.5**（τ = 0.67 s）。
沙盒的 `damping = 0.8`（τ = 1.25 s）**太软**，是 1200px 空场无战斗的产物，不要照搬。

> ### ⚠ 换算值只是起点，**迁移期间不对齐旧模型的数字**
>
> 上面这张表是把旧参数"翻译"过来的**起点**，不是验收标准。
>
> **迁移阶段只保证算法逻辑正确**（力怎么算、怎么加、怎么积分、谁对谁算）。
> 参数什么时候"手感对"是**迁移完成之后单独做**的一件事，那时可以推倒重来。
>
> 一个具体的例子，说明为什么不能强行对齐：
>
> ```
> 旧模型：寻敌是 wSeek · (SPD·û − v)      —— 速度配平，永远不超过 SPD
>         命令是 omega·wCmd · (SPD·û − v) —— 同上
>         两者**同时作用于同一个目标速度**，不会叠加超过 96 px/s
>
> 新模型：寻敌是 seekForce · û              —— 力
>         命令是 commandForce · û           —— 力
>         两者**直接相加**（127 + 144 = 271），稳态速度 ≈ 271 / damping
> ```
>
> 于是新模型的实测平均速度是 61.6 px/s、信标到达 4.8 s，而旧模型是 45.8 px/s / 10.1 s。
> **这不是 bug，是"力相加"这个性质的自然结果** —— 相关决策：**保留该性质，不为对齐旧数字去削弱寻敌力或命令力**。
>
> 同理，`maxSpeedFactor = 1.8` 是**安全阀**（防爆），不是"把这 271 削回 96"的配平旋钮。
> 如果以后觉得太快，调 `damping` / 各力幅值，那是调参阶段的事。

**实施方式（重要）**：写一个临时的 `deriveMassParams(oldP)`，跑一遍把所有模板的输出打印出来，
人工核对后**粘贴成字面量**写进 `formation-templates.js` / `templates.js`，然后删掉换算函数。
不要在运行时保留"旧键存在就换算"的兼容分支 —— 那会让"到底生效的是哪个数"永远说不清。

#### 3.1.3 积分与力的合成（新 `stepUnits` 骨架）

```js
// ---- 0. 每帧一次的准备量 ----
const sepRadius = P.sepRadius;
const smallPushShare = P.smallPushShare / 100;          // 0–1，**每队一份**
let maxR = 0;
for (const b of units) if (b.radius > maxR) maxR = b.radius;
const maxReach = Math.max(sepRadius + 2 * maxR, P.alignRadius, P.cohRadius);
// cmdX / cmdY / cmdPull：本队流场给出的方向与到达衰减（P.arriveR），见 §3.4.5

// ---- 1. 社交力：分离全局，对齐/凝聚只对亲和邻居 ----
if (gap <= sepRadius) {
  const safeGap = gap >= SEP_MIN_GAP ? gap : SEP_MIN_GAP;
  let w = (sepRadius * sepRadius) / (safeGap * safeGap);
  if (w > SEP_MAX_WEIGHT) w = SEP_MAX_WEIGHT;
  if (other.radius < u.radius) w *= smallPushShare;   // 大受小于小
  sepX -= (dx / d) * w;
  sepY -= (dy / d) * w;
} else if (same && d <= alignRadius) {
  aliX += other.hx; aliY += other.hy;                // 朝向单位向量，不是速度
  aliCount++;
} else if (same && d <= cohRadius) {
  cohX += dx; cohY += dy;                            // 指向质心，不归一
  cohCount++;
}

// ---- 2. 合成（全部是 px/s²；归一化只在"方向"上用）----
let fx = 0, fy = 0;

// 分离：Σ 已经是加权向量和，方向与强度都在里面，不归一
if (sepCount) { fx += P.sepForce * sepX; fy += P.sepForce * sepY; }

// 对齐：目标是"邻居平均朝向"，再和自身朝向配平（注意是朝向，不是速度）
if (aliCount) {
  const L = Math.hypot(aliX, aliY);
  if (L > 1e-9) { fx += P.alignForce * (aliX / L - u.hx); fy += P.alignForce * (aliY / L - u.hy); }
}

// 凝聚：方向归一，幅值恒为 cohForce（这就是"凝聚力与距离无关"的来源）
if (cohCount) {
  const L = Math.hypot(cohX, cohY);
  if (L > 1e-9) { fx += P.cohForce * (cohX / L); fy += P.cohForce * (cohY / L); }
}

// 威胁 / 寻敌：方向归一、强度取"最近的那个" —— 与现状一致，只把 w×SPD 换成 force
if (thMax > 1e-6) {
  const L = Math.hypot(thX, thY) || 1;
  fx += P.threatForce * thMax * (thX / L); fy += P.threatForce * thMax * (thY / L);
}
if (skMax > 1e-6) {
  const L = Math.hypot(skX, skY) || 1;
  fx += P.seekForce * skMax * (skX / L); fy += P.seekForce * skMax * (skY / L);
}

// 命令力：方向读本队流场（M4），强度带到达衰减
if (cmdPull > 0) { fx += P.commandForce * cmdPull * cmdX; fy += P.commandForce * cmdPull * cmdY; }

// 低速助推：沿当前朝向（没有朝向时用上一次的 u.hx, u.hy）
if (speed < G.boostSpeed) { fx += G.boostForce * u.hx; fy += G.boostForce * u.hy; }

// ---- 3. 积分 ----
vx += (fx / u.mass) * dt;                            // u.mass = G.mass，默认 1，见 §3.2.5
vy += (fy / u.mass) * dt;
const damp = Math.exp(-G.damping * dt);
vx *= damp; vy *= damp;
const cap = SPD * G.maxSpeedFactor;                   // 安全阀，不是行为参数
if (speed > cap) { ... 夹到 cap ... }
moveUnitWithWalls(map, u, u.radius, dt);              // M6

// ---- 4. 朝向（新增字段，供下一步的对齐与助推使用）----
const sp = Math.hypot(u.vx, u.vy);
if (sp > 1e-9) { u.hx = u.vx / sp; u.hy = u.vy / sp; }   // 速度为 0 时保留上一次的朝向
```

**`u.hx / u.hy` 是本层新增的唯一单位字段**，必须在 `initUnit()` 里初始化（`hx = 1, hy = 0`）。
它有两个用途：对齐（新模型配平的是朝向而不是速度）与低速助推（速度趋零时 `atan2` 是噪声）。
渲染层也可以直接读它，省掉每帧两次 `atan2`。

#### 3.1.4 要删掉的三样东西

| 删掉 | 原因 |
|---|---|
| `MAX_ACCEL = 430` 硬夹 | 新模型靠阻尼稳定；再夹一次会把"分离力突然变大"这件事吃掉，等于白换 |
| 速度硬夹（`\|v\| ≤ SPD`） | 换成 `1.8 × SPD` 的安全阀。原来的 `SPD` 既是巡航速度又是硬上限，两个语义混在一个常量里；新模型需要"巡航速度"这个概念但不能再拿它当上限 |
| 软边界推（`BM = 70`, `BK = 7`） | 有硬碰撞之后它只会把船按进墙里再被推出来，制造抖动。**推迟到阶段 4**：阶段 2 时还没有墙体碰撞，现在删掉就没有任何东西管世界边界了。它作为"环境力"暂时保留，不参与服从度统计；阶段 4 落地硬碰撞时一并删除 |

#### 3.1.5 三区判据：照搬沙盒的互斥链

**决定：直接用沙盒的 `if / else if / else if`，不设开关、不做 A/B。**

```js
if (gap <= sepRadius)              { /* 分离 */ }
else if (same && d <= alignRadius) { /* 对齐 */ }
else if (same && d <= cohRadius)   { /* 凝聚 */ }
```

一共只有三条分支，相邻两区**严格不相交**：进了分离区就既不对齐也不凝聚。

跟现状比，这个决定带来两处真实的行为变化，都是**有意的**：

| 变化 | 现状 | 迁移后 | 为什么可以接受 |
|---|---|---|---|
| 凝聚的邻居判据 | 钟形窗 `cohW(d, rOri, rAtt)`：`rOri` 附近最弱、中间最强、`rAtt` 附近再归零 | 硬阈值 `d <= cohRadius`：区内**一律**参与 | 凝聚的幅值本来就是归一化的（`cohForce` 恒定），钟形窗只影响"谁被算作邻居"。硬阈值让边缘个体也参与，队形边缘更不容易脱落 |
| 拥挤时是否还凝聚 | 分离区内的邻居**同时**贡献分离和凝聚，两股力对冲 | 分离区内直接静音凝聚 | 拥挤时最不需要的就是"再往人堆里按一把"，静音是对的 |

代价是**凝聚力不能再靠"距离加权"来做分层**，只剩 `cohForce`（幅度）和 `cohRadius`（范围）两个旋钮。
如果阶段 2 发现队形收不拢，调这两个，**不要**回头加钟形窗。

> 附带一个几何后果：大个体的半径会把对齐区吃掉（见 §3.2.2 推论 2），
> 这是 `gap` 判据 + 互斥链的直接推论，靠 `sepRadius < alignRadius − 2 × r_max` 这条不变量兜住。

#### 3.1.6 稳定性保障

新模型没有加速度上限，理论上存在"一堆船挤在一起 → 分离力叠加到几千 px/s² → 弹射"的风险。
沙盒 60 只鸟没暴露，项目 184 艘船必须防。三道保险：

1. `SEP_MAX_WEIGHT = 25`：单邻居分离权重封顶（贴脸时也不过 `25 × sepForce`）；
2. `maxSpeedFactor = 1.8`：速度安全阀（184 艘船时 `1.8 × 96 = 173 px/s`）；
3. 硬碰撞子步进（M6）：单子步位移 ≤ `0.45 × cellSize`，保证不会一帧穿过墙。

阶段 2 的验收里要专门有一条：**"把一支小队塞进 200×200 的角落，跑 600 帧，最大单步 Δv < 400 px/s"**
（沙盒里贴墙处的实测基线是 456 px/s，远离墙 719 px/s）。

#### 3.1.7 无命令时集群自己游走是**设计**，不是缺陷

低速助推是**无条件**的（只要速度低于 `boostSpeed`）：

```js
if (G.boostSpeed > 0 && speed < G.boostSpeed) {
  wx += G.boostForce * u.hx;
  wy += G.boostForce * u.hy;
}
```

于是在没有命令信标时，每艘船都会沿各自朝向维持 ~`boostSpeed`（60 px/s）的巡航，
**集群会自己随机游走、慢慢散开**。

**这是刻意的设计**：部队闲着不该钉死在原地。它带来的后果——队形会慢慢摊开、
在纸上看起来"队伍散了"——**不需要任何处理**。

> ⚠ 给后来的人：这条力**不要**加"有命令才助推"之类的门。
> 迁移过程中曾经试过加门（理由是"助推变成了方向棘轮"），实测把散布半径从 977 px 压回 39–173 px，
> 但那恰恰把"集群自主游走"这个设计意图一起删掉了，已撤回。
> `force-model.smoke.mjs` 里有一条用例守着这个行为：**无命令信标时也必须自己走起来**。

### 3.2 M2：每鸟半径

#### 3.2.1 唯一数据源

```js
// defense-system.js · initUnit()
u.radius = u.hitR;        // 就是 hull.armor.hullHitR，一个数，不再有第二个来源
u.mass   = G.mass;        // 全局质量，默认 1；逐单位质量是将来才做的事（见 §3.2.5）
```

`hitR` 现在同时服务五件事，全部一致：

| 用途 | 代码 | 变化 |
|---|---|---|
| 武器命中判定 | `weapon-system.js` `hitROf()` | 不变（本来就用它） |
| 分离力间隙 `gap = d − (r_i + r_j)` | 新增 | **新** |
| 墙体硬碰撞 | 新增 | **新** |
| 出生点是否在墙里 | 新增 | **新** |
| 贴图尺寸 | `ship-sprites.js` `sizeOf()` | 不变 |

**`shieldHitR` 不要混进来**：船体模板里还有一个 `shieldHitR`（矛隼 10、堡垒 19、母舰 40），
现在**没有任何代码读它**。它是"护盾层的外扩半径"这个概念，留着等以后做护盾命中判定。
拿它当船半径会让有盾的船凭空变大（壁垒 6.5 → 10.5），错的不是一点。

#### 3.2.2 分离力

```js
const gap = d - (u.radius + other.radius);   // 表面间隙，不是圆心距
```

必读的三条推论（沙盒 `每鸟半径-分离力几何分析.html` 已推导并验证）：

1. **触发圆心距 = r_i + r_j + sepRadius**。两只 6 号船是 `12 + 8 = 20`；一只 13 号对一只 6 号是 `19 + 8 = 27`。
   所以「每鸟半径」不是"给每只鸟加个 buzz"，它**改变的是整个队形几何**。
2. **大个体吃掉对齐区**。因为三区互斥，`if (gap <= sepRadius) ... else if (d <= alignRadius)`，
   当 `r_i + r_j + sepRadius > alignRadius` 时对齐区**完全消失**。
   以 `form.standard` 为例：`13 + 13 + 8 = 34 < 46` 尚可；一旦 `sepRadius` 抬到 20，
   `13 + 13 + 20 = 46 = alignRadius`，两只堡垒级之间就再也无法对齐了（重锤 9 号的上界是 28）。
   **这是调整 `sepRadius` 时必须盯住的上界**：`sepRadius < alignRadius − 2 × r_max`。
3. **pruning 半径必须含半径和**：

```js
let maxR = 0;
for (const b of units) if (b.radius > maxR) maxR = b.radius;
const maxReach = Math.max(sepRadius + 2 * maxR, alignRadius, cohRadius);
```

#### 3.2.3 `smallPushShare`（小队参数）

```js
if (other.radius < u.radius) w *= P.smallPushShare / 100;
```

它在回答**"是大船围绕小船，还是小船围绕大船"**，所以是编队的战术决策，进 `sq.p`：

- `100` = 完全双向，队形按尺寸自然分层
- `30` = 默认：大船只挨小船 30% 的推力 → 大船压阵、小船绕着大船散开
- `0` = 大船完全不理会小船 —— **沙盒实测这个会把小船抖到 1.85°/step（基线 0.9°），所以默认不用 0**

同尺寸之间永远 100%（它只作用在"邻居比自己小"这一侧）。实测的三档质心间距（100 只、2/4/7 三档，9 秒）：

| N | 小-小 | 小-大 | 大-大 |
|---:|---:|---:|---:|
| 0 | 105 | 84 | 57 |
| 25 | 90 | 83 | 73 |
| 50 | 86 | 82 | 87 |
| 75 | 84 | 90 | 91 |
| 100 | 81 | 92 | 100 |

交叉点 ≈ 45%。项目里半径差没那么大（6 到 13），所以 30% 会更接近"温和不对称"，是合理的起点。

#### 3.2.4 需要审计的调用点

| 调用点 | 必须做的检查 |
|---|---|
| `collectCircleWallContacts(x, y, radius)` | 搜格窗口 `ceil(radius / cellSize)`，**不能写死 3×3** |
| `findFreeSpawnPoint` / `findRandomFloorPoint` | 兜底分支也必须带半径（沙盒里这行是已知缺口） |
| `resizeSquad()` 新增单位 | 落在 `sq.cx/cy` 附近，可能正好在墙里 → 生成后要 `isBlockedCircle` 检查并推开 |
| `completeJob()` 出厂的船 | 同上 |
| `Grid.insert()` | 索引按**圆心**放格，不变；但 `queryCircle` 的半径要含 `maxRadius` |
| `weapon-system` 的 `BIG` 名单 | `hitR > UNIT_PAD(8)` 已经涵盖堡垒 13 与母舰 40，**不用改** |

#### 3.2.5 全局「质量」参数

沙盒的 `mass` **是全局单值（默认 1）**，不是每鸟质量：`syncMasses()` 会把它刷到所有鸟身上。
项目照搬这个语义，放进 `core.G`，并保留 `u.mass` 字段（值 = `G.mass`），积分时走 `/ u.mass`。

**它做什么、不做什么：**

```
v += (F / mass) · dt        ⇒  mass 是力的总缩放，等价于所有 *Force 同乘 1/mass
v *= e^(−damping·dt)        ⇒  damping 才是"失去动力后多快停下来"
```

- `mass ↑` → 同样的力给更小的加速度，整体更"肉"、更钝；
- `damping ↑` → 速度衰减更快，松油门后停得更快、抖动衰减更快；
- 两者不重复：`mass` 调"推动有多难"，`damping` 调"滑行有多远"。

**它不会带来"大船更重"**：所有单位共用同一个值，尺寸之间没有任何差异。
"大船不容易被小船推动"这件事**由 `smallPushShare`（小队参数）表达**，它更直接、只有一个旋钮、已经实测过。

**为什么不给每艘船按半径算质量**（`mass ∝ radius²`）：两个代价太大 ——
① 所有 6 个力参数全部失效重标（大船的分离力要乘 1/4.7 才等价）；
② 大船会明显迟钝，而现状"缓慢硬墙"的手感是靠 `threatForce` 大 + `sepRadius` 大表达的，再加一层质量会过头。

**决策：`G.mass = 1`（迁移本身零行为变化），每单位的 `u.mass` 一律等于 `G.mass`。**
将来真要按尺寸分级，只改 `initUnit()` 里那一行赋值，`stepUnits` 的 `/ u.mass` 已经在位，全部力参数不用重标
—— 因为 `G.mass = 1` 时它们已经是"单位质量下的加速度"。

#### 3.2.6 尺度重标

项目的半径是 6–13（默认局），沙盒是 2–7。后果：

- 分离区**圆心距**整体变大：`2 × 6 + 8 = 20`（沙盒 `2 × 2 + 22 = 26`，比例接近）；
- 贴图与碰撞的比例失衡：矛隼贴图宽 ≈ 30px，碰撞直径 12px。**这会让人误以为"贴图重叠 = 碰撞失效"**。
  阶段 3 验收时要专门截一张图说明：贴图能叠，圆心不能叠。
- 母舰（40）如果上场：`sepRadius + 2×40 = 88` 的分离圈，几乎是一支小队的直径。
  它应当走「不参与群体力场」的特例（现状它也没上场），本次不处理。

### 3.3 M3：IIR 低通滤波

#### 3.3.1 为什么是 IIR 而不是接着调 1€

| | 1€（已废弃） | IIR（本次） |
|---|---|---|
| 参数 | 3 个（`fc_min / β / fc_d`），互相耦合 | 1 个（`fc`） |
| 行为 | 截止频率随 \|ω\| 自适应：小抖动强平滑、大转向放开 | 恒定截止：平滑度与延迟都是常数 |
| 可预测性 | 延迟随运动状态变化，没法预先说"掉头会慢多少" | 延迟 = `1/(2π·fc)`，可解析算出 |
| 实测 | 「效果不行」（2026-11-08 回退） | 沙盒里作为对照项保留，默认 `filterType = 'iir'` |

1€ 理论上更优（自适应），但它引入的"自激"风险在鸟群这种低频大幅信号上反而更明显：
`β·|ω|` 一上来把截止抬高，平滑就消失了，抖动原样透出；而把 `β` 调小又退化成固定低通——那就直接用它。
**结论：用 IIR，把 1 个参数调到位。**

#### 3.3.2 公式与状态

```js
// render/angle-filter.js
const TAU = Math.PI * 2;

export class IirAngle {
  constructor(cutoffHz = 3) { this.init = false; this.last = 0; this.unwrapped = 0; this.out = 0; this.setCutoff(cutoffHz); }
  setCutoff(hz) { this.k = TAU * Math.max(1e-3, hz); }
  update(angle, dt) {
    if (!this.init) { this.init = true; this.last = angle; this.unwrapped = angle; this.out = angle; return angle; }
    // 先解卷绕（跨 ±π 必须处理，否则 179° → −179° 会被当成转了 358°）
    let d = angle - this.last;
    d = Math.atan2(Math.sin(d), Math.cos(d));
    this.unwrapped += d;
    this.last = angle;
    // 一阶低通：alpha 用指数形式，天然与帧率无关
    const a = 1 - Math.exp(-this.k * dt);
    this.out += (this.unwrapped - this.out) * a;
    return this.out;
  }
}
```

三个要点：

1. **解卷绕是必须的**。直接对 `atan2` 的结果做 EMA，跨 ±π 时会产生一整圈的错误旋转。
2. **`alpha` 用 `1 − e^{−k·dt}`**，不用固定系数。这样 60Hz / 144Hz / 掉帧到 30Hz 的平滑强度一致。
   沙盒里写的是 `1 - Math.exp(-TAU * fc * dt)`，同一个式子。
3. **状态挂单位对象**，用 `WeakMap<unit, IirAngle>`。挂精灵上就是现状那个 bug（精灵池复用串朝向）。

#### 3.3.3 接入点

```js
// render-pixi.js
const CUTOFF_HZ = 3;
this.filters = new WeakMap();                  // 构造时一次；精灵创建时 s.rotation = Math.PI / 2

filterOf(u) {
  let f = this.filters.get(u);
  if (!f) { f = new IirAngle(CUTOFF_HZ); this.filters.set(u, f); }
  return f;
}

drawUnits(view, dt) {
  ...
  // 速度 ≤ 2 时干脆不喂新样本 —— 滤波器保持上一次输出，
  // 于是"静止船保持朝向"这件事不需要额外的锁角字段（现状的 s._ang 就是那个字段）
  if (Math.hypot(u.vx, u.vy) > 2) {
    s.rotation = this.filterOf(u).update(Math.atan2(u.vy, u.vx), dt) + Math.PI / 2;
  }

```

`draw(view, dt)` 要多一个 `dt` 参数（`main.js` 主循环里本来就有 `dt`）。
`WorldRenderer` 抽象基类同步改签名。

#### 3.3.4 截止频率

|     `fc` | 时间常数 `1/(2πfc)` | 以 180°/s 转向时的滞后角 | 适用            |
| -------: | --------------: | ---------------: | ------------- |
|   1.5 Hz |          106 ms |              19° | 太平滑，转向发肉      |
|     2 Hz |           80 ms |              14° | 保守            |
| **3 Hz** |       **53 ms** |         **9.5°** | **默认（沙盒实测值）** |
|     5 Hz |           32 ms |             5.7° | 抖动压不住时往上调     |
|     8 Hz |           20 ms |             3.6° | 基本等于不滤        |

验收口径：**朝向的二阶差分标准差（抖动量）下降 ≥ 60%，同时"命令信标急转"的可见延迟 ≤ 0.15 s**。
量测方法沿用沙盒的监视器思路，在 `render-pixi.js` 里加一个 `?angle=probe` 开关打印指标。

#### 3.4.2 共享缓存（关键优化）

10 支小队同时被选中下一个信标时，**目标格往往是同一个**。所以场按**目标格**做缓存，不按小队：

```js
// core.flowCache: Map<string, { field, refs }>  —— key = `${map.rev}:${cx}:${cy}`
// LRU 上限 8 张
```

于是"给全部 8 支正规小队下同一个点"只算 **1** 张场。这是把每次点击的卡顿从 8 张压到 1 张的关键。

#### 3.4.3 确定性预算（这一条不能省）

`test/determinism.smoke.mjs` 要求同种子同指纹。**按毫秒预算决定"这帧算几张场"会让不同机器跑出不同的战斗**。
唯一安全的调度是定数：

```js
// core.step() 里，在 stepUnits 之前
stepFlowQueue() {
  let budget = FLOW_PER_FRAME;              // 定数 1，不是毫秒
  while (budget-- > 0 && this.flowQueue.length) {
    const id = this.flowQueue.shift();      // 按 squadId 升序入队 → 顺序确定
    this.buildFlow(id);
  }
}
```

场没算好的那几帧，该小队**退化为直线指信标**（`u.flowFallback = true`）。
退化最多持续 `N/FLOW_PER_FRAME` 帧（N = 队列长度），是确定性的。

按实测（§3.4.4），1 张场 ≈ 2.9 ms，一帧 16.7 ms 有余量；设 `FLOW_PER_FRAME = 1` 即可。

#### 3.4.4 网格尺寸怎么选（实测数据）

`node 鸟群算法抖动研究/_bench-flowfield.mjs`（2000×1200，3% 散墙 + 一条 U 形墙，即"几乎全图可达"的最坏情况）：

| 单元 | 格数 | 单场耗时（中位/最大） | 单场内存 | 结论 |
|---:|---:|---:|---:|---|
| 4 px | 150 000 | **17.0 / 18.3 ms** | 1.72 MB | ✗ 一帧都不够 |
| **8 px** | **37 500** | **≈7 / 16 ms**（实现了之后实测） | 0.43 MB | **✓ 推荐** |
| 16 px | 9 375 | 1.0 / 1.1 ms | 0.11 MB | 墙太粗，会切角 |

> **⚠ 这张表第一次填的时候 8px 那格写的是 2.9 ms，那个数是错的。**
> 早期的独立基准用的是 `Float32Array` 存代价，`√2` 之类的代价被舍入后，
> `nodeCost > cost[i]` 会误判成"该节点已过时"，于是它永久不出队 ——
> 空图上只有 **13%** 的格子可达（4916 / 37 500）。基准跑得快是因为它只做了 13% 的活。
>
> 换成 `Float64Array` 之后可达率 100%，耗时 ≈9 ms；再把内层循环里的
> `map.isWall()` 方法调用换成"补一圈实心边"的查表、并把除法/开方提到循环外，
> 才降到 **≈7 ms**。`FLOW_PER_FRAME = 1` 的结论不变（一帧 16.7 ms 仍然够），
> 但余量比原先以为的小。

对照沙盒原样（1200×1200 @ 4px = 90 000 格）：9.2 ms。沙盒能接受是因为它**单张场、点击时才重算**。

**决定：默认 `cellSize = 8`，写进地图 JSON 可覆盖。上限 `MAX_MAP_CELLS = 200 000`。**

#### 3.4.5 方向的读法与已知风险

```js
// group-layer.js：命令通道
const idx = flowCellIndexAt(map, u.x, u.y);
let cmdX = field.dirX[idx], cmdY = field.dirY[idx];

if (cmdX === 0 && cmdY === 0) {
  // 场上没有方向（该格不可达 / 没算好 / 没墙的退化）→ 直线指信标
  const dx = sq.goal.x - u.x, dy = sq.goal.y - u.y;
  const L = Math.hypot(dx, dy) || 1e-9;
  cmdX = dx / L; cmdY = dy / L;
}

// 到达衰减：每队自己的 P.arriveR（远处满幅，近处线性收）
const dist = Math.hypot(sq.goal.x - u.x, sq.goal.y - u.y);
const cmdPull = dist < P.arriveR ? dist / P.arriveR : 1;
```

**已知风险：8 邻域流场在空地上是锯齿的。** 相邻两格的最优方向可能差 22.5°，船会走"阶梯"。
沙盒靠 `damping` 抹掉了大半，项目里 `alignForce` 还会帮着拉直。若仍然可见，两个后手（阶段 5 备选）：

1. **双线性插值方向**：读 4 个相邻格的方向做插值（`dirX/dirY` 是 Float32，插值合法）；
2. **直线可视时优先直线**：在算场的方向回填那一趟，对每个格做一次到信标的可视检查（只测"该格是否与信标同在一个连通直线上"，
   用一次 DDA，37 500 次射线 ≈ 几毫秒，超预算）；更省的做法是只对**信标周围 32 格内的走廊**做，其余仍然用场。

先做原样，实测再决定。

#### 3.4.6 建场时不按船宽膨胀地图（M4 照做，只省掉这一步）

流场本身按 §3.4.1–§3.4.5 全量实现。这里只划清**建场时的一个明确不做的步骤**：

Dijkstra 只知道格子「通/不通」，不知道宽度。`cellSize = 8 px`，而最小半径是 6 px（舰船要 12 px 宽才过得去），
所以一条 1 格宽的缝会被流场当成可通行，船挤到窄口顶着墙。

**决定：本次不膨胀墙体** —— 寻路不感知船宽。具体不做三件事：

1. 不对 `walls` 做 `k = ceil(minRadius / cellSize)` 的方形膨胀；
2. 不在地图规范里写走廊宽度约束；
3. 不加运行时"卡住/顶着墙"检测。

理由：

1. 现阶段**没有一张带墙的地图**（默认是空图，唯一的墙是世界边框），空图上的流场与「直线指信标」等价，问题不会显现；
2. 膨胀会吞掉 16 px 走廊宽度，等于在地图设计开始之前先把关卡表达定死；
3. 它是纯几何问题，与力模型 / 每鸟半径 / IIR 都不耦合。将来要补时，在 `flow-field.js` 建场前加一次膨胀即可
   （只作用于寻路用的位图，**不动碰撞用的原图**），Dijkstra / 方向回填 / 共享缓存都不用改。

**唯一约束落到测试上**：阶段 5 的绕障测试用图，走廊宽度**自选为 ≥ 24 px（3 格）**。
这不是地图规范，只是让"绕障失败"这个结论可以被正确归因——
如果测试图里出现 1 格宽的缝，失败就不是流场的问题，而是本次明确不处理的已知缺陷。

#### 3.6.2 算法与那个必须记住的坑

```js
function moveUnitWithWalls(map, u, radius, dt) {
  let remaining = dt, iter = 0;
  while (remaining > 1e-9 && iter++ < 48) {
    const speed = Math.hypot(u.vx, u.vy);
    const stepDt = speed > 1e-9
      ? Math.min(remaining, (map.cellSize * 0.45) / speed)   // 单子步位移 ≤ 0.45 格
      : remaining;
    u.x += u.vx * stepDt; u.y += u.vy * stepDt;
    resolveUnitWall(map, u, radius);
    remaining -= stepDt;
  }
}
```

| `resolveUnitWall`：取所有接触 → 最深的一个 → 沿法线推出 `depth` → **只去掉法向速度**（切向保留，于是沿墙滑）
→ 再复查 2 遍（凹角里可能同时压两面墙）。

墙格的多边形不是方格，而是**倒角后的多边形**（地图平滑处理），几何见 §3.6.4。

**搜格窗口必须由半径推出来**（这是上一轮修掉的那个 bug）：

```js
const reachCells = Math.max(1, Math.ceil(radius / map.cellSize));
// r = 6 @ cell 8 → 1 → 3×3；r = 13 → 2 → 5×5；r = 40（母舰）→ 5 → 11×11
```

写死 3×3 的后果实测过：半径 8 的圆能压进墙 4px 而检测不到，随后某个此前在窗口外的邻格滑进来，
突然给出一个 `depth = radius + distance` 的深接触，一次性把船弹出去（单步速度跳变 1018 px/s），
表现就是"穿入墙体快速穿出"的抖动。修复后穿透 4.00px/596 帧 → **0px/0 帧**。

#### 3.6.4 地图平滑处理（格角倒角）

##### 是什么

墙由 8 px 的方格拼成，凸角是**直角**。船贴着墙角滑过去时，会先撞上这个 90° 台阶再被推开——
表现为"顿一下"，密集时看得很明显。而且直角在视觉上就是"像素方块的边缘"，不像墙。

**做法**：把每个「暴露在外」的方格角切掉一个 45° 等腰三角形，墙角从 90° 变成 135° 斜面，
等价于用多边形近似圆角。这正是 `getChamferedCellPolygon()` 干的事。

##### 「暴露」怎么判定

一个角只有**它的两条正交邻格都是空地**时才算暴露（否则墙体连续延伸过去，那个角在墙里，不该切）。

```js
// 4 个 bit 对应 4 个角：TL=1, TR=2, BR=4, BL=8
function getWallChamferMask(x, y) {
  const L = isCellWall(x - 1, y), R = isCellWall(x + 1, y);
  const T = isCellWall(x, y - 1), B = isCellWall(x, y + 1);
  let m = 0;
  if (!L && !T) m |= 1;   // 左上角暴露
  if (!R && !T) m |= 2;   // 右上角
  if (!R && !B) m |= 4;   // 右下角
  if (!L && !B) m |= 8;   // 左下角
  return m;
}
```

注意它只看**正交**邻格，不看对角——这是刻意的近似，对角是墙时说明那里是凹口，切了会把凹口填平。

##### 怎么切

半平面裁剪（Sutherland–Hodgman），每置位一个 bit 就裁掉那条 45° 线外侧的三角形：

```js
// 局部坐标以格左上角为原点，C = cellSize，t = 切进深度
// TL: 保留 (X-l) + (Y-t) >= t          // 线从 (t,0) 到 (0,t)
// TR: 保留 (r-X) + (Y-t) >= t          // 线从 (C-t,0) 到 (C,t)
// BR: 保留 (r-X) + (b-Y) >= t
// BL: 保留 (X-l) + (b-Y) >= t
```

四次裁剪后仍 ≥ 3 个顶点才算有效多边形（`clipPolygonHalfPlane` 逐边插值求交点，
退化成线或点时返回 `null`）。

##### 关键约束一：渲染与碰撞必须用同一份多边形

这是 D1（表现层向物理层对齐）的直接延伸。如果墙按原始方格画、碰撞却按倒角多边形算，
玩家会看到"船离墙角还有半个格就被弹开"，或者反过来"船插进了画出来的墙角"。

所以：**`getChamferedCellPolygon()` 是唯一几何来源**，碰撞（`collectCircleWallContacts`）与
渲染（画墙）都调它。渲染可以按 `map.rev` 缓存成一张静态 Graphics，重画时只画一次。

##### 关键约束二：倒角没有"深度"这个参数（2026-11 定案）

**一格只要触发倒角，就固定切掉一半** —— 切线正好是格子的对角线，没有可调项：

```js
const t = map.cellSize;   // 半平面 (x-left)+(y-top) >= t，切线从角连到对角
```

暴露在外的角被完整切掉，墙角就是沙盒里那个 45° 斜面。
因为以**格**为单位表达，整张地图等比放大（格长 8 → 24）时斜面也跟着等比变长
（物理长度 11.3 px → 33.9 px）；这是"世界尺寸 = 格数 × 格长"的自然结果，
详见 `design/261115_1地图相关测试复盘/05-技术设计-格长即比例尺.md` §5。

**这条只负责"角切了"，不负责"墙还剩多少面积"。** 薄墙（2×2 方块、1 格厚墙、L 拐角）会被削细，
但那属于**地图设计工具**的职责 —— 工具该提示"这堵墙太薄"，游戏运行时不判定、不报警、不做任何面积约束。

唯一必须兜住的是**孤立单格**：四个角全是暴露角，切完多边形就没了（`null`）→ 该格对船完全无碰撞 →
船直接穿墙。这是碰撞缺陷，不是面积问题，所以保留两行特判：

```js
if (!L && !R && !T && !B) return 0;   // 孤立柱：四面开阔，切了就没东西了
```

`test/wall.smoke.mjs` 的 [1][1b][2] 只断言**语义**：暴露角被切、内部角不切、
"切掉一半"（切线过格心）、孤立格不切；再用 [3] 验"孤立单格仍然挡船"。不写任何面积/顶点数断言。

##### 参数与代价

| 项 | 值 |
|---|---|
| 每次接触检测的多边形 | ≤ 8 顶点（4 次裁剪，最多切出 8 边） |
| 每条边的距离计算 | 1 次投影 + 1 次 `sqrt` |
| 是否需要缓存 | 碰撞侧**不缓存**（每次现算，一个格几条边，代价低于查表）；渲染侧按 `map.rev` 缓存整图 |

`collectCircleWallContacts` 的搜格窗口已经在 §3.6.2 按半径推过，倒角不改变窗口大小。
