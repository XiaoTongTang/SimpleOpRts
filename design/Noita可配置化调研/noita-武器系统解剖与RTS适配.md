## 文档定位

本篇只做两件事：

1. 拆开 **Noita**（你写作 "Notia"）的法杖系统，讲清它由哪几层构成、每层为什么这么切；
2. 指出哪些结构能搬进"RTS 大群单位"的语境，哪些必须改、为什么。

**这不是 Noita 攻略，也不是最终的武器配表。** 配表是下一篇的事。

## 一句话结论

Noita 的武器不是"一把枪 + 一套数值"，而是一台**极小的解释器**：

> 牌是数据，顺序是程序，修饰是前缀高阶函数，一切写入同一个共享累加器。

它的深度不来自武器数量，而来自 422 张牌 × 一条抽牌规则。

---

## 一、四层结构

| 层 | 是什么 | 关键字段 | 谁改它 |
|---|---|---|---|
| L0 载体 | 法杖/枪身 | shuffle、actions_per_round、cast_delay、recharge、mana_max、mana_charge、capacity、spread、speed_mul、always_cast | 掉落时随机生成 |
| L1 牌 | 单张法术 | type、mana(drain)、**draws**、max_uses、各类 delta、action() | 玩家装填 |
| L2 解释器 | 抽牌机 | Deck / Hand / Discard、wrap、作用域 | 引擎，玩家不可见 |
| L3 组合子 | 语义算子 | 修饰、多重、触发、希腊字母 | 涌现，无显式配置 |

L0 是"容器与预算"，L1 是"内容"，L2 是"规则"，L3 是"语法"。**玩家只在 L0 和 L1 上操作，却在 L3 上获得表达力**——这是整套设计最值钱的地方。

## 二、执行模型（心脏）

三堆：`Deck`（牌库）、`Hand`（本次施法抽到的牌）、`Discard`（弃牌）。

抽牌规则：

- 一次 cast 从 Deck 顶抽 `actions_per_round` 个**根表达式**；**根抽永不 wrap**。
- 抽到之后，每张牌按自己的 `draws` 继续抽：
  - 投射物 `draws = 0`（自己就是叶子）
  - 修饰符 `draws = 1`（抓下一张，把 delta 挂上去）
  - 多重施法 `draws = N`（抓 N 张，同时发射）
  - 触发器 `draws = 1`，但开一个**新的 payload 栈**，命中时才展开
- 任何**由牌引起的**抽牌遇到空 Deck → 把 Discard 按槽位顺序灌回 Deck（wrap 绕回），本次 cast 结束时强制装填。
- cast 收尾：Hand → Discard。

**最关键的一句话：连不连接由牌的 `draws` 数字决定，不由牌的类别决定。** 代码里没有 `if type == MODIFIER` 这种分支。整个解释器核心大概二十行，却能表达修饰、多重、触发、嵌套、循环五种语法。

### 三层作用域

这是设计者唯一需要精心决定的边界：

| 作用域 | 内容 | 生命周期 |
|---|---|---|
| **cast** | shot state：伤害加成、散布、弹速、追踪、穿盾…… | 每次 cast 重置 |
| **payload** | 触发体内部**另起一份** shot state | 触发时创建，执行完销毁 |
| **global** | mana、recharge、recoil | 穿透一切隔离，全杖共享 |

注意那个"故意漏"：触发体里的修饰符不会污染外面，但触发体里的**减装填**照样算到整把杖头上。否则触发器就变成了一个免费 buff 仓库。

## 三、组合子清单

| 组合子 | Lisp 类比 | Noita 实现 |
|---|---|---|
| 投射物 | 原子 | `draws = 0` |
| 修饰符 | 前缀函数 `(dmg+ bolt)` | `draws = 1`，写 shot state |
| 多重施法 | N 元 gather `(cast3 a b c)` | `draws = N` |
| 触发器 | 惰性闭包 `(bolt (payload ...))` | `draws = 1` + 新 payload 栈 |
| 希腊字母 | **反射**：把牌库当数据来查询 | Alpha=第一张、Gamma=最后一张、Tau=后两张、Mu=所有修饰符、Phi=所有投射物、Omega=全部 |
| wrap | 循环 / 尾递归 | 空 Deck 自动回灌 |

希腊字母是系统里唯一的元编程，也是唯一会失控的东西。它对单机是浪漫，对 RTS 是灾难（见第六节）。

## 四、四重预算

| 预算 | 结算点 | 性质 |
|---|---|---|
| `mana` | 每张牌 | 唯一的硬闸门。不够就跳过该牌，并可能顺势 wrap |
| `cast delay` | 每次 cast | 杖底值 + 所有牌的 delta 求和，60 发/秒封顶 |
| `recharge` | 抽空 / wrap 后 | 同上，但只在牌库干涸时结算 |
| `capacity` | 槽位数 | 硬上限，决定你能塞几张 |
| `max_uses` | 单张牌 | 消耗品，靠 Spell Refresher 补充 |

四条正交的取舍轴。**只有一条轴（DPS）的配装游戏，最优解是唯一的。**

## 五、九个可以直接抄的设计决策

**D1 牌是数据，不是分支**
422 张牌共用一份 schema，`action()` 只写共享状态、不调用别的牌。
→ 加一张新牌不需要改任何旧牌，也不存在"兼容性表"。N 张牌产出 N 种效果，而不是 N² 种冲突。
→ 代价：没有专属 combo，所有 combo 都是涌现的，作者也控制不了强度。

**D2 抽牌数是数据（`draws`）**
一条规则解释所有连接行为，不需要给"修饰符"和"多重施法"各写一套特例。
→ 系统小到能讲清楚，复杂到玩不完。

**D3 修饰符是前缀、上下文敏感**
不是"选中投射物 → 添加属性"，而是"这张牌占住下一个被抽出的槽位"。
→ 用**一维顺序**代替二维绑定。UI 成本为零，表达力极高。
→ 代价：心理模型只能靠试错建立，且"顺序"天然难解释。

**D4 一切写入共享累加器**
`c.damage += 0.1`、`c.spread += 2`、`c.speed *= 1.4`——所有修饰都是对同一个数值包做加减乘。
→ 零耦合：修饰符不需要知道自己修饰的是谁，因此任意两张牌都能共存，422 张不需要一张兼容表。
→ 注意一处常见误读：因为都写同一张表、且字段多为独立加减，**修饰符之间的先后顺序通常不改变结果**。"顺序是程序"指的是顺序决定**分组**（哪几张被同一发弹吃掉、wrap 落在哪），不是决定算术次序。
→ 如果想要顺序也产生算术意义（先 `+10` 再 `×2` ≠ 先 `×2` 再 `+10`），需要额外规定"修饰符依次作用于已生成的弹"。这是 Noita 没有、但 RTS 版可以加的一条小规则。

**D5 作用域三分**
cast / payload / global。共享什么、隔离什么，是唯一的架构决策。做对了组合自动成立，做错了要么全串味、要么组合失效。

**D6 多维稀缺**
五条预算，每条都是独立的取舍轴。稀缺维度的数量，决定取舍的丰富度。

**D7 乱序杖作为价格歧视**
`shuffle` 把确定性换成随机性，给低容量杖一个"便宜但不可控"的生态位。
→ 用不确定性定价：**想要确定性，就得花槽位或稀有度去买。**

**D8 检查免费、编辑收费（不对称）**
拿起新法杖对比时游戏**暂停**；打开背包编辑时游戏**不**暂停；圣山是唯一的安全编辑点，但一次性。
→ 把"配置"这个动作本身设计成玩法：思考有安全区，执行有风险。

**D9 不解释**
游戏从不告诉你 wrap 会发生什么，社区自己发现，"发现"的所有权归玩家。
→ 代价：入门墙极高。Noita 用"死得快、重开快"消化这个成本。**RTS 一局三十分钟，玩家没有一百次试错的机会，这条不能照搬**（见第七节）。

## 六、不能照搬的六条

**1. 编辑粒度**
Noita 一个持有者一棵树，玩家能承担"读一棵解析树"的认知成本。RTS 是 20 个战斗群 × 200 单位，每单位一棵树 = 认知爆炸。
→ **必须把编辑锁在小队层，单位只做执行者。**

**2. 编辑时机**
Noita 可以边挨打边进背包（这是它故意设计的风险）。RTS 战斗中不能编辑。
→ **配装只能发生在战斗外**。我的游戏里"圣山"就是准备阶段。

**3. 视觉可读性**
Noita 里"我的杖在干什么"是玩家自己造的，他懂。RTS 里同屏 200 单位，必须一眼看出"这群在放什么"。
→ **程序必须有稳定的视觉签名**。推论：VFX 数量 = 弹卡数量，修饰符只能改参数、不能新增特效类型。否则特效数按组合数爆炸。

**4. 随机性**
RTS 需要可规划的战斗结果，否则战略无从谈起。
→ `shuffle` 最多只能作为少数战斗群的**标签**，不能是全局默认。

**5. 平衡**
Noita 不需要平衡（单机，超模就是爽点）。RTS 必须平衡，而且必须**可解析地算出来**，不能"跑起来看看"。
→ 成本模型要能闭式算出 DPM / 有效血量 / 能量曲线。

**6. 性能**
Noita 一帧只有一个施法者。RTS 一帧可能 200 个单位同时施法。
→ **必须编译，不能解释。** 好消息：非乱序杖的抽牌结构是**纯静态可推导的**——给定牌序和 `actions_per_round`，不运行也能算出每一发打什么、什么时候 wrap。编译期把整棵树展开成扁平指令序列，运行时只做 `u.cd -= dt` 和数组下标。

## 七、适配骨架（建议，不是定稿）

### 7.1 载体换位

> **单位 = 执行者，小队 = 法杖，玩家只配小队。**

一次"施法"= 小队的一次齐射，`actions_per_round` = 这次齐射参与的单位数。

### 7.2 卡的语义重划

照搬 Noita 的八类会崩。RTS 只需要五类：

| 类 | 作用 | 对应现有 |
|---|---|---|
| 弹 | 产生伤害事件 | ray / laser / torpedo |
| 修饰 | 改下一发弹的参数（穿盾、增程、溅射、追踪、延迟引爆） | 无 |
| 齐射 | 一次打 N 发 / 分 N 个目标 | 无 |
| 触发 | 命中或爆炸后追加效果（二次爆炸、破盾连锁、标记） | 无 |
| 载荷 | 作用于友军（套盾、修复、加速） | 护盾充能器 |

载荷这一类是 RTS 特有、Noita 没有的（Noita 的治疗是投射物）。它很可能是这套系统在 RTS 里**最出彩的一格**：让"火力"和"支援"共用同一套语法。

### 7.3 移植清单

| 抄 | 砍 |
|---|---|
| `draws` 驱动连接（D2） | 希腊字母（元编程） |
| 共享累加器 + 顺序有意义（D4） | 任意 wrap / 递归 |
| 作用域三分（D5） | 卡牌收集、稀有度、抽卡 |
| 多维预算（D6） | 战斗中编辑 |
| 检查免费 / 编辑收费（D8） | 默认乱序 |
| | `max_uses`（或改成"过载"：超频后进入长冷却） |

### 7.4 编译而不是解释

```
compile(program) -> {
  cycle,          // 一轮总时长
  steps: [ {t, slot, dmg, pierce, ...} ],   // 已展开的扁平序列
  energy,         // 每轮能量消耗
  dpm, ehp        // 可直接展示给玩家的解析值
}
```

运行期只剩查表和倒计时。这一步不做，200 单位 × 表达式树必炸。

### 7.5 一个算例

把现有的"要塞战术群"（`laser`，10 人口，300 血，5 充能器）写成程序：

```
槽 0 [弹]   激光
槽 1 [修饰] 校准：+射程，-伤害
槽 2 [齐射] 双联：同轮打 2 发
槽 3 [载荷] 护盾投射：命中后给最近友军套盾
```

编译后：`cycle = 2s`，每轮 2 发、耗能 E、DPM = 2 × dmg × 30，并给玩家一行"每轮 2 发 / 每发 X 伤害 / 每秒 Y 能量"的白话摘要。

**注意这里没有任何新机制**——只是把已经写在 `weapon-system.js` 里的三种弹，加上三个"改参数"的槽位。这就是这套系统最诱人的地方：**它不增加游戏内容，它增加内容的排列数**。

### 7.6 数值必须可解析

这是 RTS 与 Noita 最大的分歧点。要给玩家的不是"试试看"，而是一张能算的表：

- 每轮伤害 = Σ(弹伤害 × 修饰累加器结果)
- 每轮周期 = 基础周期 × (1 + 齐射惩罚)
- 能量曲线 = 每轮耗能 / 每秒回复 → 决定"能连续打几轮"
- 有效血量 = 血量 + 载荷提供的护盾

玩家的战略决策发生在这些数字之间，而不是在"我发现了一个 bug 组合"上。

## 八、反模式清单

1. **别给完全自由的组合。** Noita 有 422 张牌、单机、可以重开一万次。RTS 应该是 20 张牌、4 槽位、且槽位有类型限制（1 弹 + 1 修饰 + 1 齐射/触发 + 1 载荷）。**限制槽位类型不是懒，是让组合可读。**
2. **别暴露 wrap。** RTS 里的无限循环 = 不平衡，且玩家看不懂。
3. **别做抽卡。** 这里的"可配置"应该是**配装**，不是**收藏**。卡应该全部可见、可买，靠预算限制，不靠掉落限制。
4. **别在战斗中编辑。**
5. **别让修饰符产生新特效。** 参数变了，颜色/形状不变。
6. **别只留一条预算轴。** 只有 DPS 的配装 = 唯一解。
