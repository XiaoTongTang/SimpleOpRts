> 状态：**设计稿（v2，待实现）**
> 日期：2026-11-15
> 归属：`design/261115_3母舰舰船生产机制设计/`
> 前序讨论：母舰 = 出兵点；口 = 有状态；分批出厂；rally 成型

## 0. 摘要

五件事一起变：

1. **母舰变成一条真正的船，而且是一条有「方案」的船**：`hull.ark` 进舰船方案库（`ship.std_ark`），
   舰船设计界面里能选它、配它的 1 个武器槽 + 2 个插件槽。它在 `units` 里，`mass = 1`、`radius = 40`，
   移动、被瞄准、被分离力推、被击毁 —— **全部不做例外**。
   「完全停船」通过**它自己那套小队参数**表达（助推 0 + 社交力 0），不是代码例外。
2. **生产与出货解耦**：产线造完 → 待发区 → 由「出兵建筑」把船一艘一艘放进战场。
   **口只有位置、没有方向**，状态（占用）挂在单位实例上。
3. **一个出兵建筑同一时间只服务一支小队**：从建队那一刻起，该建筑的**全部出口被这支队伍保留**
   （排他，别的队一艘也别想用），出货时按顺序轮转着用；整支出完才允许下一支。
   所以「出口」不需要和「小队」互相绑定，反而是**建筑**上记一个 `producing`（当前正在出厂的队）。
4. **不靠初速度、不靠一次性生成**：船从口上错开冒出，靠一个 **rally 点**汇成一支队。
5. **一个阵营可以有 N 艘母舰、N 支母舰小队**：母舰就是船，母舰小队就是"编制里含母舰的普通小队"
   （内置编制模板 `squad.ark`）。**每艘母舰各带一套产能**（3 条产线 + 效率总和 + 待发区 + 出兵口），
   所以多造一艘母舰 = +3 产线 +12 个泊位 +4 个口 + 一层战损冗余。

一句话记法：**线是造多快，口是放多快，坞是囤多少；建筑一次只放飞一支队；一艘母舰一套产能。**

已拍板的决策：

| # | 决策 | 影响 |
|---|---|---|
| D1 | 口是有状态的「口」，状态绑在**单位实例**上 | 模板只存位置；占用/释放是运行时字段 |
| D2 | **不做**出口插件、**不做**「能不能出大船」的尺寸分级 | 口没有 `size`；大船只是出生点沿径向多挪几像素 |
| D3 | **口没有 `dir`，只有 `pos`**；不指定出厂朝向 | `pos` 语义 = 武器挂点；船朝向由速度派生（见 §6.1） |
| D4 | 自然凝聚 = 设置 **rally** 点 | 复用 seek 力的形状，不新增系统 |
| D5 | 出兵点**只做手动指定**，不做自动就近 | 一条命令 + 默认值（自己的母舰） |
| D6 | 母舰是 `units` 里的一员，`mass = 1`，无行为例外 | 它会漂、会被打、会被推开 |
| D7 | 母舰小队 = **编制里含母舰的普通小队**（不是无编制小队） | `entries` 有内容（`ship.std_ark × 1`）；`motherShipSquad` 变成**派生缓存**的判据 |
| D8 | **助推力 / 助推阈值下沉为小队参数** | 母舰小队 `boostForce = 0` ⇒ 完全停船；全局参数只剩 4 项 |
| D9 | 母舰有**专属编制模板 `squad.ark`** + **专属阵型 `form.mothership`** | 不新增任何"母舰专用代码分支" |
| D10 | 一个建筑同一时间只放飞**一支**小队 | 建筑上记 `producing`；其余队伍的船在待发区排队 |
| D11 | 删掉**服从度 α** 统计 | 见 §10：它从来没有人读过 |
| D12 | **母舰有自己的舰船方案**（`ship.std_ark`），舰船设计界面可见、可装配 | 去掉 `ship-design.js:19` 的 mothership 过滤；母舰走完整的"方案 → 运行时"链路 |
| D13 | 一个阵营可有 **N 艘母舰 / N 支母舰小队**，**每艘母舰各带一套产能设施** | `this.production` 从"按阵营 2 个"变成"按母舰 1:1"；命令改用 `facilityId` 寻址 |

## 1. 背景：现状与问题

### 1.1 现状（三个事实）

- **母舰是虚拟的**：`core.js:175` 的注释写着「阶段一没有母舰实体，直接用方舟级的产能参数虚拟一个」。
  `this.production = [createFacility(0, …), createFacility(1, …)]`，参数抄自 `hull.ark.mothership`。
  战场上根本没有这条船，`getView().bases` 也一直是空数组。
- **一键建队是"凭空生成"**：`cmdBuildFromTemplate` 在 `(width×0.26 / 0.74, height×0.5)` 这个**硬编码圆心**
  周围 `SPAWN_SPREAD = 55` 的圆盘里，一次撒出全部 N 艘，`vx = vy = 0`。
- **排队建造也是"凭空生成"**：`completeJob` 把船直接撒在散兵池重心附近的 55 圆盘里。

### 1.2 为什么现在会"挤在一起然后瞬间爆开"

不是"密度不够"，是**分离力的邻居叠加**。手算一遍量级（建议实测复核）：

| 量 | 值 | 出处 |
|---|---|---|
| 生成圆盘半径 | 55 px | `core.js:57 SPAWN_SPREAD` |
| 矛隼受击/船体半径 | 6 px | `hull.falcon.armor.hullHitR` |
| 分离间隙 `sepRadius` | 12 px | `form.default.p.sepRadius` |
| 分离触发圆心距 | `2r + sepRadius` = **24 px** | `group-layer.js` `gap = d − (rᵢ+rⱼ)` |
| 6 点在 55 圆盘内的典型最近邻距 | ≈ **20 px** | 均布估算 |
| 单邻居权重上限 | 25（**每邻居**封顶，不是每艘船） | `SEP_MAX_WEIGHT` |
| 5 个邻居的合力量级 | `5 × 25 × 50 = 6250 px/s²` | `sepForce = 50` |

结论：出厂瞬间**几乎每一对都在分离区里**，而权重上限是"每个邻居"各算一次，
所以邻居数一多，合力**线性叠加到失控**（阻尼 1.1 下的稳态速度上千 px/s）→ 十几帧内满速四散。

**因此分批出厂不是"为了好看"，它是根因治疗**：把出场密度降到 1，这个力就永远不会被叠起来。
初速度不解决问题（它只是把爆炸美化成一束），所以 D3 直接把它砍掉是对的。

## 2. 概念模型

### 2.1 五个概念，各归各位

| 概念 | 回答的问题 | 归属 |
|---|---|---|
| **产能** facility | 能造多快（产线数、效率） | **每艘母舰一份** |
| **生产** job | 在造什么、还要多久 | 设施，**不是**母舰 |
| **待发** staging | 造好了、还没上场的船排在哪 | 设施（泊位，有容量） |
| **出货** port | 从哪个位置、什么节奏进战场 | **建筑实例**上的口 |
| **成型** rally | 出来的船在哪汇合、什么时候算成型 | 小队 |

母舰同时是四样东西：**一条船**（有血、会动、能开火、**有方案**）、
**产能载体**（它自己那一份设施的 `owner`）、**口的宿主**（`u.ports`）、**一支小队**（`squad.ark`）。
它**不是**"生产"本身 —— 队列和待发区都在设施上，
所以"别的建筑也能出兵"只需要让 `facility.outlet` 指向另一个单位。

### 2.2 关系图

```
 产线 queue ──(效率 × 时间)──► job 完成
                                  │ 交付（待发区满则暂不交付，卡在队首）
                                  ▼
                    staging  [ {squadId, shipId}, … ]   FIFO，容量 12
                                  │ 出货（一帧一艘，轮转口，间隔 LAUNCH_GAP）
                                  ▼
        出兵建筑 u.outlet ──► u.producing（当前小队）─► 口 ─► 单位 ─► 飞向 rally
                                  │
                                  └─ 该队出完 → producing = null → 下一支
```

### 2.3 为什么「小队不绑出口，建筑记 producing」

- 一支队要**占满**建筑的所有口才好看（船从四周错开冒出），所以出口不是"被哪支队预订"，而是
  "某段时间只能服务一支队"。
- 反过来，如果小队绑出口，会出现"这支队锁了口，但另一支队从同一个口出"的歧义，
  以及"一队一口 ⇒ 单队出得慢"的问题。
- 记在建筑上的另一个好处：**"这个建筑正忙"是一个可以被玩家看见、被命令拒绝的状态**
  （`cmdBuildFromTemplate` 直接拒），不需要额外的小队状态机。

## 3. 数据结构

### 3.1 船体模板：口的**几何**（不可变）

`core/data/hull-templates.js`，加在 `hull.ark` 上：

```js
"hull.ark": {
  …,
  // 出货口：只有位置，没有方向。
  // 坐标与武器挂点同一套：舰体局部坐标，+x = 舰首，+y = 左舷。
  ports: [
    { id: "p1", pos: [36,  32] },   // 左前  |pos| = 48.2
    { id: "p2", pos: [36, -32] },   // 右前  |pos| = 48.2
    { id: "p3", pos: [-2,  44] },   // 左后  |pos| = 44.0
    { id: "p4", pos: [-2, -44] }    // 右后  |pos| = 44.0
  ]
}
```

**为什么没有 `dir`**（D3）：船的朝向是"当时速度的方向"（`updateHeading`），
出厂那一瞬指定了也立刻被改掉，所以方向不该是数据。
`pos` 只回答一个问题：**船从哪儿冒出来**。

**布局约束**（三条，都要写进测试）：

| 约束 | 这条数据 | 理由 |
|---|---|---|
| `\|pos\| > hullHitR` | 44~48.2 > 40 | 口在船体**外**，船不会生在船体里 |
| 任意两口的**出生点**间距 ≥ `2×最大船半径 + 8`（≈34） | 最小是 p1↔p3 = 39.8 | 两个口先后出兵时，前一艘已经走开、后一艘也不会贴着它 |
| 口**贴着船体**、并沿舰轴**错开** | 前后错开 38 px | "错开"比"正四向"好：正四向的两个侧口在同一横剖面上，前脚出、后脚紧跟着出时距离最短 |

> 口特意**不放在正四向**：`p1/p2` 靠前、`p3/p4` 靠后，任意两个相邻口都不在同一横剖面上。
> 这样即使两艘船前后脚从相邻口出来，它们也在舰轴方向错开了 38 px。
> 口也**不布置在舰尾**，因为 rally 在舰首方向（§6.3），舰尾口要绕舰半圈。

`compileShip()` 增加一行 `ports: hull.ports || null`，于是**任何有 `ports` 的船体都自动拥有口**，
不需要为母舰写任何特例（未来给"船坞舰 / 无人机母舰"加口只是加数据）。

### 3.2 单位实例：口的**状态**（运行时，跟实例走）

`initUnit()` 末尾按模板复制一份状态：

```js
// 只在这艘船身上存在；两艘同型母舰的口互不影响（D1）
u.ports = [
  { id: "p1", ox: 36, oy: 32,   // 本地位置（模板抄来，永不改）
    hold: 0,                    // > 0 = 占用中（秒）；每帧递减
    last: null }                // 上一艘从这口出去的船（用于"已离口"判据）
]

// 出兵建筑上的另外三个字段（也在实例上）
u.producing = null;   // 当前正在出厂的 squadId；null = 空闲
u.launchCd  = 0;      // 距下次允许出货还剩多少秒（全局节奏，不是单口）
u.nextPort  = 0;      // 下一个使用的口下标（轮转，确定性）
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `ox, oy` | number | 口的本地位置；世界位置 = `中心 + 按朝向旋转(ox, oy)` |
| `hold` | number | 剩余占用时间；`0` = 空闲。上限 `PORT_HOLD_CAP` |
| `last` | unit \| null | 上一艘船；死掉/离口/被打爆都会让它提前释放 |

世界位置与出生点：

```js
// 左向量 = (−hy, hx)
wx = b.x + ox * b.hx - oy * b.hy;
wy = b.y + ox * b.hy + oy * b.hx;

// 出生点在「口 → 舰心」这条射线的延长线上，按**这艘船的大小**外推
d  = hypot(wx - b.x, wy - b.y);          // = |pos|
ux = (wx - b.x) / d,  uy = (wy - b.y) / d;
r  = max(d, b.radius + shipR + EXIT_GAP);
spawn = { x: b.x + ux * r, y: b.y + uy * r };
```

`max(...)` 的作用：口的位置是按"贴船体"设计的（44~48），而最大的堡垒半径 13，
`40 + 13 + 6 = 59`；所以**大船自动出得远一点**，小船则几乎正好在口上。
这也是"暂不做尺寸分级"（D2）的兜底 —— 大船不会生在船体里。

### 3.3 单位需要稳定 id

"指定一栋出兵建筑"要能寻址。`units` 是普通对象数组、会被 `splice` 重排，**数组下标不能当 id**。

```js
this.uidSeq = 1;
u.uid = this.uidSeq++;      // makeUnit / spawnAll / 出货处统一
```

新增字段，不改变任何现有语义（现有选择/命令全部按 `squad`，不按单位）。

### 3.4 设施：从"阵营的产能"变成"有主、有口、有坞"

`core/sim/production.js` 的 `createFacility` 扩展：

```js
{
  ownerUid,                   // 母舰单位的 uid —— 设施的主键
  owner: <unit>,              // 同一艘母舰的引用
  faction: 0,
  efficiencyTotal: 30,
  lines: [{ alloc: 10, queue: [job] }],

  outlet: <unit>,             // 出兵建筑，**默认 = owner 自己**
  staging: [],                // [{ squadId, shipId }]，FIFO
  stagingCap: 12,             // 泊位数
}
```

`job` 结构不变：`{ id, faction, shipId, buildTime, progress }`。

**一艘母舰一份设施（D13）**，所以 `this.production` 从"按阵营固定 2 个"变成
"按 `units` 里的母舰 1:1 建立"，随母舰生灭：
母舰一出生就建一份设施，母舰被击毁就**连设施一起消失**（它的队列和待发区一起没）。

**模组与指挥值仍是阵营级**（`build.modules` / `build.commandCap`，沿用现有代码）：
它们更像"国家后勤储备"，不随母舰数变。母舰级的是：产线数、效率总和、待发区、出货口。

**注意 `producing / launchCd / nextPort` 不在设施上，在 `outlet` 那个单位上**（D10）：
"这个建筑正忙着放一支队"是建筑的状态，换出兵点就该跟着建筑走/被拒绝（§7.3）。

### 3.5 母舰小队 = 含母舰的普通小队（D7 + D12 + D13）

母舰现在有方案了，所以它不再需要"无编制"的特权。内置一条**编制模板**：

```js
// squad-templates.js —— 和另外 4 条内置模板并列
"squad.ark": {
  id: "squad.ark",
  name: "母舰编队",
  desc: "一艘母舰 + 它自带的一套产能",
  entries: [{ ship: "ship.std_ark", n: 1 }],
  formations: ["form.mothership"]      // 唯一可选阵型：停船
}
```

`createBuild` 末尾每阵营追加一条引用它的队（`id` 必须等于数组下标）：

```js
// state.js createBuild() 的 squads 末尾
{ id: 10, key: "母舰", name: "母舰", faction: 0,
  loose: false,                          // 它不是"一团船"，走的是一支小队的群体行为
  motherShipSquad: true,                 // 【派生缓存】见 §3.5.1
  template: "squad.ark",
  entries: [{ ship: "ship.std_ark", n: 1 }],
  formations: ["form.mothership"], form: "form.mothership",
  ship: "ship.std_ark",                  // 主方案 = 母舰方案
  count: 1 }
```

这一步把上一版里所有"母舰没有方案"的特例**一次性消掉**：

| 上一版（母舰无方案） | 现在（母舰有方案） |
|---|---|
| `entries: []`，`spawnAll` 要单独分支按船体造 | `entries: [{ship, n:1}]`，**走通用路径**（`runtimeOf("ship.std_ark")`） |
| `b.count` 只能手写 1（推出来是 0） | `count = entriesCount(entries)` = 1 |
| 快照 `1/0`，要靠 `isEditable` 回落 | 天然 `1/1` |
| `b.ship: null`，`applyShipToSquadParams` 会 `compileShip(undefined)` 炸 | `b.ship = "ship.std_ark"`，一切正常 |

```js
// squad-layer.js makeSquad() 追加字段
sq.motherShipSquad = !!def.motherShipSquad;   // 【必须也在 sq 上】removeSquad 判的是运行时对象
sq.rally = null;          // 出厂集合点 {x,y}；null = 无
sq.rallyAt = 0;           // 写入时刻（超时判据）
```

为什么**必须有**小队：`stepUnits` 的主循环第一件事是 `const sq = squads[u.squad]; if (!sq) continue;`。
没有小队的单位在 L1 里**完全不动**（连墙都不撞）。所以"母舰在 units 里" ⇔ "母舰必须有一个小队"。

#### 3.5.1 `motherShipSquad` 是派生缓存，不是手写常量

判据 = **该队编制里有没有 `hull.class === "mothership"` 的船**：

```js
function computeMothershipFlag(b, ships) {
  for (const e of squadEntries(b)) {
    if (!(e.n > 0)) continue;
    if (getHull(ships?.[e.ship]?.hull)?.class === "mothership") return true;
  }
  return false;
}
```

必须在**编制变化的入口**统一重算，否则会漂：`createBuild` / `cmdBuildFromTemplate` /
`applySquadTemplate`（模板一改，引用它的队跟着变）/ 任何改 `entries` 的命令。
`sq` 上也要同步一份（`removeSquad` 判的是 `this.squads[id]`，不是构筑项）。

它决定三件事：

1. 该队的默认/推荐阵型是 `form.mothership`（停船）——
   模板里已经写了，但玩家自建模板时要能"发现我这队里塞了母舰"；
2. 这支队里的母舰**各自获得一套产能设施**（§3.4）；
3. UI 不显示"解散 / 吸收"，出货时不发 rally（§5.3）。

**为什么不做成手写布尔**：多母舰之后，"含母舰"是随编制变化的属性（改模板、改编制都会变），
存一份纯手写常量就等于存两份真相。派生 + 缓存 = 一份真相。

**多母舰 / 多母舰小队（D13）**：再建一支引用 `squad.ark` 的队，就多一支母舰小队；
队伍里那艘母舰**出生时自动拿到一套产能设施**（§3.4）。所以"造第二条母舰"的收益是：

**+3 条产线、+3×10 效率、+12 个泊位、+4 个出货口、+1 条命。**

**单队母舰数上限 = 1**（`MAX_ARK_PER_SQUAD = 1`）：编制层面 `n: 2` 虽然合法，
但两艘 40 半径的船同队会互相挤，且 UI 会冒出两组产线卡片。将来要做"母舰战斗群"再放开。

#### 3.5.2 必须补的闸门

现有"挡住散兵池"的判断都是 `b.loose`；母舰队是 `loose: false`，会从它们中间穿过去：

| 位置 | 现状判据 | 不补的后果 |
|---|---|---|
| `cmdDisband` `core.js:1754` | `if (b.loose) reject` | 母舰被解散，单位扔进散兵池 ⇒ 阵营少一份产能与出兵点 |
| `removeSquad` `core.js:1784` | `if (this.squads[id].loose) return false` | 两张表各删一项 + 全体重编号 ⇒ 母舰的 `u.squad` 指到别人身上 |
| `cmdSetSquadCount` `core.js:960` | `if (b.loose) reject` | 编制能被改成 N 艘 ⇒ 凭空造船 / 把母舰改没 |
| `cmdSetFormation` `core.js:1173` | `if (b.loose) reject` | 换上普通阵型 ⇒ `boostForce` 不再是 0 ⇒ **母舰开始自航** |
| `snapshot` `core.js:693` | `count: b.loose ? alive : entriesCount()` | 现在两者都是 1，只是兜底 |
| UI 小队卡片 `ui.js:557/571/574` | `s.loose` 决定"alive 口径"和三个按钮 | 母舰会带着"解散 / 吸收"两个它不能用的按钮 |

统一成一个判据，别散着写：

```js
/** 玩家能不能动这支队的"编制层"东西（阵型 / 舰数 / 解散 / 吸收） */
function isEditable(b, ships) {
  return !!b && !b.loose && !computeMothershipFlag(b, ships);
}
```

- 上表里 `if (b.loose) return reject(...)` → `if (!isEditable(b, this.ships)) return reject(...)`（文案按身份分开写）
- `removeSquad` → `if (!isEditable(b, this.ships)) return false`
- `snapshot` → `count: isEditable(b) ? entriesCount(entries) : alive`（留作兜底）
- UI → **照常显示这张卡**，只把"解散 / 吸收散兵"两处按钮按 `motherShipSquad` 去掉（见 §3.5.3）

## 4. 口的状态机

### 4.1 状态机（只有两个状态，每个口一份）

```
        出货成功
  空闲 ───────────► 占用 (hold = PORT_HOLD_CAP)
   ▲                    │
   └────────────────────┘
     释放（满足任一）：
       a) last 已死 (hp ≤ 0)
       b) last 离出生点 ≥ 2×last.radius + PORT_CLEAR
       c) hold 递减到 0（PORT_HOLD_CAP 兜底）
```

`hold` 是**上限**而不是"固定占多久"：正常情况下 (b) 会在 ~0.2 s 内释放，
(c) 只在"船卡住了/被敌人贴住/被墙挡住"时兜底。

**注意：`hold` 是"安全"，不是"节奏"。** 节奏由建筑级的 `LAUNCH_GAP` 管（§4.3）：
轮转四口意味着同一个口每 4 次出货才用一次（≈0.8 s），远大于它自己需要的 0.2 s，
所以 `hold` 几乎永远不成为瓶颈 —— 它是"万一"的保险。

### 4.2 为什么"口占用"就能根除爆开

一次只有一艘船在口上，**下一个船出生时上一艘已经离开 ≥ 2r + PORT_CLEAR**，
所以新船与它最近的同伴之间至少隔了一个船身。§1.2 里那个"5 个邻居各 25 权重"的前提不存在了。
不需要"出生保护期"、不需要"分离力淡入"、也不需要给初速度（D3）。

### 4.3 轮转与节奏（**没有"选口规则"了**）

一支队出厂期间，建筑的全部口都被它**排他占用**；出货时按固定顺序轮转：

```
从 u.nextPort 开始，找第一个 hold === 0 的口 → 出一艘 → u.nextPort = (该口 + 1) % n
```

- **不做**"挑离目标最近的口""按队伍绑定口"之类的选择（那些规则已删除）。
- 唯一的门是 `u.launchCd`（建筑级），出货后置为 `LAUNCH_GAP`；它没到就整帧不出。
- 一个口都不空闲（极端情况：三艘船同时压在同一口附近）→ 本帧不出，不消耗待发区。

轮转 + `LAUNCH_GAP` 带来的观感就是"从四周错开着、一艘一艘地冒出来"：

```
t=0.0  p1（左前）
t=0.2  p2（右前）
t=0.4  p3（左后）
t=0.6  p4（右后）
t=0.8  p1 …
```

相邻两次出货的口间距 ≥ 40 px（§3.1 的布局约束），前后两艘船在 0.2 s 内各自离开 ~20 px，
所以它们既不会同点重叠，也不会贴着走。

## 5. 出货流程

### 5.1 常量（可调，先给一组起手值）

`core/sim/production.js`：

```js
export const EXIT_GAP        = 6;     // 出生点在「舰体表面 + 船半径」之外再留多少（px）
export const PORT_CLEAR      = 6;     // 口释放距离 = 2×r + 它
export const PORT_HOLD_CAP   = 1.2;   // 口占用上限（s）
export const LAUNCH_GAP      = 0.20;  // 同一个建筑两次出货的最小间隔（s）—— 真正的节奏
export const STAGING_CAP     = 12;    // 待发区泊位数
export const RALLY_DIST      = 90;    // rally 在舰心之外多远（沿舰首方向）
export const RALLY_ARRIVE    = 40;    // 全队到这个距离算"到齐"
export const RALLY_TIMEOUT   = 3.0;   // 到不齐也解散（s）
```

### 5.2 每帧三步（`core.stepProduction`）

> `this.production` 现在**一艘母舰一项**（D13），随母舰生灭。

```
1. 模组自然恢复（不变）
2. stepFacility：推进产线；job 造完 → 尝试交付到 staging
      交付失败（staging 满）→ job 留在队首，progress 保持在 buildTime，下帧重试
3. stepLaunch：每个设施最多出一艘
```

```js
stepLaunch(dt) {
  for (const fac of this.production) {
    const b = fac.outlet;
    if (!b || !(b.hp > 0) || !b.ports || !b.ports.length) continue;   // 没口 = 停产

    // 口的时间推进（含快速释放）
    stepPorts(b, dt);

    b.launchCd = Math.max(0, b.launchCd - dt);
    if (b.launchCd > 0) continue;

    // 正在出厂的队优先；没有就按 FIFO 取队首（可能是散兵池的单艘船）
    const want = b.producing;
    const idx = fac.staging.findIndex(s => want === null || s.squadId === want);
    if (idx < 0) {
      if (want !== null) b.producing = null;    // 这支队伍已经全出完了
      continue;
    }

    const item = fac.staging[idx];
    const rt = this.runtimeOf(item.shipId);
    if (!rt) { fac.staging.splice(idx, 1); continue; }      // 方案已不可建造，丢弃

    // 兜底：取到的是某支编制小队的船而 producing 还是空的（例如迁移后），顺手补上标记
    if (b.producing === null && item.squadId !== this.poolOf(fac.faction)) {
      b.producing = item.squadId;
    }

    // 轮转选口：从 nextPort 起找第一个空闲的
    const n = b.ports.length;
    let port = null, pi = -1;
    for (let k = 0; k < n; k++) {
      const i = (b.nextPort + k) % n;
      if (b.ports[i].hold <= 0) { port = b.ports[i]; pi = i; break; }
    }
    if (!port) continue;                                     // 口都还没清空

    let spawn = exitPointOf(b, port, rt.hitR);
    if (isBlockedCircle(this.map, spawn.x, spawn.y, rt.hitR)) {
      const free = findFreeSpawnPoint(this.map, spawn.x, spawn.y, 0, rt.hitR, rand);
      if (!free) { port.hold = 0.3; continue; }              // 这个口压墙，短暂跳过
      spawn = free;
    }

    this.spawnFromPort(item, rt, spawn, b, port);
    fac.staging.splice(idx, 1);
    b.launchCd = LAUNCH_GAP;
    b.nextPort = (pi + 1) % n;
    if (b.producing !== null && !fac.staging.some(s => s.squadId === b.producing)) {
      b.producing = null;                                    // 整支出完，建筑空出来
    }
  }
}
```

### 5.3 生成一艘船

```js
spawnFromPort(item, rt, spawn, b, port) {
  const u = {
    uid: this.uidSeq++,
    squad: item.squadId,
    x: spawn.x, y: spawn.y, vx: 0, vy: 0,      // 【D3】速度真的是 0，没有初速度
    cAll: 0                                     // alpha 已删（§10）
  };
  initUnit(u, rt);            // 填 u.ports / hitR / radius / mass / 武器 / 能力
  this.settleUnit(u);         // 出墙（不消耗随机数）
  this.units.push(u);

  port.hold = PORT_HOLD_CAP;
  port.last = u;

  const sq = this.squads[item.squadId];
  // rally 只发给"成编制、且不含母舰"的新队：
  //   · 散兵池是 loose，多一艘船不该把整个池子拉到一个点上
  //   · 母舰小队只有 1 艘、而且它就是出生点，rally 没有意义
  if (sq && !sq.loose && !sq.motherShipSquad && !sq.rally && !sq.goal) {
    // rally：沿母舰**当前朝向**的前方（不是口的方向）
    sq.rally = { x: b.x + b.hx * (b.radius + RALLY_DIST),
                 y: b.y + b.hy * (b.radius + RALLY_DIST) };
    sq.rallyAt = this.time;
  }
  computeCenters(this.units, this.squads);
}
```

**朝向初始化（一次性，不是数据）**：`initUnit` 之后补一行

```js
const dx = spawn.x - b.x, dy = spawn.y - b.y, dd = Math.hypot(dx, dy) || 1;
u.hx = dx / dd; u.hy = dy / dd;      // 出生这一刻朝"外"
```

理由不是"想让它朝哪"，而是**规避一个退化值**：`updateHeading` 在速度 ≈ 0 且 `hx === undefined`
时兜底成 `(1, 0)`；而低速助推是沿 `hx/hy` 推的，于是**每艘新船都会被沿世界 +x 推一把**。
对右/左舷口来说这一把是侧向的，会和母舰的径向分离力拧着来。
设成径向只是把"第一帧的朝向"定成物理上唯一合理的那个，之后立刻由速度接管（D3 的意思不变）。

## 6. 出厂观感：不初速、rally、成型

### 6.1 船怎么离开口（不用初速度、不用口方向）

起手值下的量级（矛隼 r = 6，出生点 = 40+6+6 = 52）：

- 出生点相对舰体的表面间隙 = `EXIT_GAP = 6` → 分离权重 `(12/6)² = 4`
  → 该方向加速度 `50×4 = 200 px/s²`（阻尼 1.1 → 稳态 ~180 px/s），而且**船越远力越小**，单调衰减；
- 即使某个阵型的 `sepRadius` 小于 `EXIT_GAP`（例如 `templates.js` 里有 `sepRadius: 5` 的预设），
  分离力为 0 也没关系：低速助推仍沿出生朝向把它推出去（~41 px/s）。

**关键性质**：这两个力都只随"距离"单调变化，且船在**持续远离**口 ——
不存在"力改速度 → 速度改力"的反馈环（这正是 §1.2 和避墙场设计里反复强调的抖动来源）。
所以"从口里滑出去"本身不会抖。

### 6.2 什么时候放下一艘

见 §4.2：`LAUNCH_GAP = 0.2 s` 是节奏，`hold` 是"上一艘真的走了"的保险。
**这个判据直接就是"不会重叠"的证明**，也是这套机制能替代"出生保护期"的原因。

### 6.3 rally：一个"定点"（D4）

小队的集合点：

```js
sq.rally = 舰心 + 舰首朝向 × (radius + RALLY_DIST)      // 首次出货时写入，之后不改
```

- 用**母舰朝向**，不是口的位置：四个口分布在两舷，没有"口的方向"可用（D3 已删 `dir`）；
  而母舰朝向是唯一的、稳定的、玩家能理解的"前方"（母舰出厂时就朝敌，且它完全停船，
  朝向不会自己变）。
- 因为口都布置在舰体两侧靠前的半段（§3.1），四股船流都不需要绕舰，都朝舰首前方汇聚。

**为什么不用现成的"统一寻敌目标"（`sq.target`）**：那条力是
`w = smoothstep(r4, r5, dT)`，`r4 = 190 / r5 = 500`；rally 距出生点只有 ~70 px，
`w = 0` —— 力根本不存在。而且 `sq.target` 每帧被 `computeSquadTargets` 覆盖，写进去会被冲掉。

所以 rally 用一条**新的项**，但形状是现成的"arrive seek"（与命令力同构）：

```js
// group-layer.js：进社交槽（sx/sy）
if (sq.rally && !sq.goal) {
  const rx = sq.rally.x - u.x, ry = sq.rally.y - u.y;
  const rd = Math.hypot(rx, ry);
  if (rd > 1) {
    const k = rd >= P.arriveR ? 1 : rd / P.arriveR;   // arrive 衰减：近了就松手
    sx += P.seekForce * k * (rx / rd);
    sy += P.seekForce * k * (ry / rd);
  }
}
```

- 幅值用现成的 `P.seekForce`（默认 50），**不新增参数**；
- `arrive` 衰减是**单调**的 → 不会围绕 rally 点打转；
- 与凝聚力/对齐/分离同时作用 ⇒ 观感是"几艘船汇到一处，然后自然站成一坨"。

**rally 什么时候结束**（清成 `null`，在 `stepProduction` 末尾统一扫一遍所有 `sq.rally !== null` 的队）：

1. 待发区里已没有本队的船（全出完了），**且**全队成员到 rally 的距离都 < `RALLY_ARRIVE`；或
2. 超时 `RALLY_TIMEOUT`。

### 6.4 出厂期间玩家下了命令

**直接生效，不排队。** 规则只有一句：

> `sq.goal` 存在时 rally 一律不生效（`&& !sq.goal`）；玩家下命令时顺手把 `sq.rally` 清掉。

于是：还没出厂的船照常一艘艘出（钱已经付了、编制也占着）；已经上场的船立刻朝目标走。
不需要"命令缓存""成型后才能指挥"这一层。

### 6.5 出厂期间的小队状态

- **扣费在入队那一刻**：模组立刻减、指挥值按编制立刻占满。
  否则玩家能在出厂途中取消建队白拿模组，或者拿一支半残队骗指挥值。
- UI 上 `alive / count` 天然显示 `3/8`，额外显示"出厂中 5"（`squads[i].pending`）。
  这不是 bug，是**信息**：玩家必须知道这支队还没准备好。

## 7. 出兵点（D5：只做手动指定）+ 一次一队（D10）

### 7.1 数据与命令

- 出兵点 = `facility.outlet`，类型是**单位引用**（带 `ports` 的同阵营建筑）。
- 默认值：每份设施建立时 = 它自己的 `owner`（那艘母舰）。
- 指定：`{ type: "setOutlet", facilityId, unitId }`，校验三条 ——
  1. 目标单位存在且 `hp > 0`；2. 同阵营；3. `ports.length > 0`。
- 不做"自动就近""按目标点推断"等任何自动逻辑（D5）。

### 7.2 一次一队（D10）

```js
cmdBuildFromTemplate(cmd):
  const b = fac.outlet;
  if (!b) return reject(["没有出兵点"]);
  if (b.producing !== null) return reject([`该建筑正在出厂第 ${b.producing} 号小队`]);
  …建队、扣模组、扣指挥值…
  b.producing = id;                       // 立刻标记，从这一刻起建筑被这支队伍占用
  for (每个编制的船) fac.staging.push({ squadId: id, shipId });
```

- 建队命令一成功，建筑就"忙"了：**第二支一键建队会被直接拒绝**，直到第一支全部出厂。
- 排队建造（散兵池的单艘船）**不占 `producing`**：它们照常进待发区，
  在 `producing === null` 的空档里一艘一艘出。
- 一支队"全部出厂"的判据 = 待发区里已经没有它的船（建队时整批 push，所以等价于"全出完了"）。

### 7.3 失效与兜底（都靠自然结果，不加特判）

| 情况 | 结果 |
|---|---|
| **母舰**被击毁 | **它那一份设施一起消失**（队列 + 待发区 + 出货口一起没）。该阵营其它母舰照常生产 —— 这就是"多母舰 = 冗余" |
| 出兵点（被指定的别的建筑）被打掉 | 设施还在，只是没口 → 只停"出货"，产线照常造，船堆在待发区（满 12 后产线卡住）。指定新出兵点后自动恢复 |
| 出兵点没有口 | 命令被拒（§7.1 校验） |
| 原建筑正在出厂，想改出兵点 | 命令被拒（避免半支队跨两个建筑出来）。**除非原建筑已经死了** —— 此时允许，并把 `producing` 迁移到新建筑，继续出同一支队 |
| 所有口都占用 | 本帧不出货，staging 不动，下一帧再试 |
| 出口压墙 | 先 `findFreeSpawnPoint` 找附近空地；找不到就给这个口一个短冷却，下一帧试别的口 |

"母舰死了就停产"这件事**不需要写代码**：设施与母舰 1:1，母舰没了设施就没了。
而"出兵点没了"也不需要：没有口 → 船出不去 → 待发区满 → 产线卡住。
这正是解耦带来的好处 —— 产能、生产、出货三个失效点是独立的。

## 8. 母舰本体（D6 + D7 + D8 + D9）

### 8.1 参数（船体数据 + 一条方案）

| 项 | 值 | 说明 |
|---|---|---|
| **方案** | `ship.std_ark` | `hull.ark` 的方案，舰船设计界面里可见、可配（D12） |
| `radius` / `hitR` | 40 | 与贴图可见宽度 2×40 对齐（既有约定） |
| `mass` | 1 | 与所有船相同，**不例外** |
| `hp` / `regen` | 3000 / 20 | |
| `command` | 0 | 不占指挥值 |
| 武器 | 1 个 S 槽 | 照常开火 |
| 插件 | 2 个槽 | 照常改装 |
| 能力 | 维修无人机 ×4 | 船体自带 |
| 口 | 4 个 | 见 §3.1 |
| `buildTime` | ⚠ **0 → 待定（建议 300~600）** | 现在是 0，产线会一帧造好一艘母舰 |
| `capacity` | ⚠ **10 → 建议 24** | 1 个 S 武器（3）+ 两个插件（4/5）就爆承载了 |

生成方式：和其它船完全一样 —— `runtimeOf("ship.std_ark")` → `initUnit` → `settleUnit`。
唯一的额外一步是：**放下它之后要建一份产能设施**（§3.4），参数取自 `hull.ark.mothership`
（`lines / efficiency / moduleCap / moduleRegen / commandCap / captureLimit`）。

### 8.2 落位与朝向

- 位置：阵营列 `width × (0.26 / 0.74)`；纵向按"该阵营第几艘母舰"错开
  （第 1 艘 `0.5h`，第 2 艘起 ±0.22h 往外排）。落点用 `findFreeSpawnPoint` 兜底跳出墙
  —— 母舰半径 40，落位必须真的空。
- 朝向：**朝敌方**（蓝 `hx = +1`，红 `hx = −1`），否则两艘母舰的口和 rally 都朝 +x。
  朝向只在出生时定一次；之后它不自航（`boostForce = 0`），所以朝向会一直保持
  （除非被撞动到有速度，那时朝向会跟着速度转 —— 这是 `updateHeading` 的既有行为，不特殊处理）。
- **没有特殊分支了**：母舰走 `spawnAll` 的通用路径（按 `entries` 造）。
  唯一需要"认出来"的地方是"放下它之后建设施"，判据是 `hull.class === "mothership"`。
- 母舰排在 `build.squads` 末尾 ⇒ `spawnAll` 前 10 队的随机数消耗顺序完全不变。

### 8.3 专属编制模板 + 专属阵型（D9）

母舰的超能力全部是**数据**，一条代码分支都没有：

| 数据 | 作用 |
|---|---|
| `hull.ark.ports` | 4 个出货口（§3.1） |
| `hull.ark.mothership` | 产能参数（每条产的线数、效率、模组上限…） |
| `ship.std_ark` | 方案：舰船设计界面可配（D12） |
| `squad.ark`（编制模板） | "一艘母舰"的编制，默认阵型 = `form.mothership`（§3.5） |
| `form.mothership`（阵型） | 不自航、不聚群、不追敌 |

"完全停船"就是这条阵型参数：

```js
// formation-templates.js
"form.mothership": {
  id: "form.mothership",
  name: "母舰（停泊）",
  desc: "母舰专用：不自航、不聚群、不追敌；仍会被撞动、仍会被打",
  builtin: true,
  p: {
    sepForce: 50, alignForce: 0, cohForce: 0,        // 社交：只保留"被推开"，不参与编队
    sepRadius: 12, alignRadius: 0, cohRadius: 0,
    commandForce: 50, arriveR: 135, smallPushShare: 25,
    threatForce: 0, seekForce: 0,                     // 不逃、不追
    r4: 190, r5: 500,
    boostSpeed: 0, boostForce: 0                      // 【停船】低速助推关掉
  }
}
```

参数表里真正**必须有**的是两个 0：

| 参数 | 为什么必须为 0 |
|---|---|
| `boostSpeed` / `boostForce` | 不自航。这是"完全停船"的唯一来源 |
| `seekForce` / `threatForce` | 母舰队是 `loose: false`，会走"统一寻敌"（`sq.target`）与威胁区；不归零它就会朝敌人挪 |

`alignForce / cohForce = 0` 其实是**多余的**（非 loose 的凝聚力只认同队，而本队只有 1 艘），
保留只是让这张表自解释 —— 顺带保证"哪天有人把母舰和护卫混编，它也不会突然开始编队"。

> 这个写法顺便回答了"为什么要把 boost 下沉到小队"：如果 boost 还是全局的，
> 要么母舰跟着舰队一起漂，要么只能在 `group-layer.js` 里写 `if (u.isMothership)` —— 后者正是 D6 禁止的。
> 下沉之后，母舰的"不动"和"不聚群"完全是**参数**，与代码路径无关。
> 想要"推都推不动"（像一堵墙）？把 `sepForce` 设 0 —— 又是一个参数。

### 8.4 多母舰（D13）

一个阵营可以有 N 艘母舰、N 支母舰小队、N 份产能。**没有"唯一母舰"的假设**：

| 玩法 | 现在怎么做 |
|---|---|
| 再要一艘母舰 | 再建一支引用 `squad.ark` 的队（同其它队一样的建队流程；扣模组/工时） |
| 它的产能 | 出生那一刻自动建一份设施，默认出兵点 = 它自己 |
| 它的口 | 来自 `hull.ark.ports`，4 个；新母舰同样可以给别的设施当出兵点 |
| 它被打掉 | 那一份设施消失，其它母舰不受影响 |

一艘新母舰必须从**某艘现存母舰的口**里出来（这是唯一有口的地方）。
出厂几何自动适配：出生点 = `40(父舰) + 40(自己) + 6 = 86`，口占用判据按 `2×40+6 = 86px`，
所以同一口要等这艘大船完全离开才放下一艘 —— 比放小船慢得多，这是应该的。

### 8.5 三个"后果"，全部接受

1. **它会漂一点**。`boostForce = 0` 之后它不再自航，但仍会被撞动（`sepForce = 50`，
   小船的推挤按 `smallPushShare` 只生效 25%）。位置漂了，口和 rally 就跟着漂 —— 这没问题。
2. **它会被人群推开**，也会被自己的船撞。这是 `mass = 1` 的必然结果（D6 接受）。
3. **它会死**。死了 = 那一份产能和出兵点一起没（§7.3），阶段一**不判负**，
   只要还有另一艘母舰，这个阵营就还能造。

### 8.6 不作为 `bases`

`getView().bases` 保持为空数组。母舰是 `units` 的一部分 ——
这样它自动获得：被瞄准、被分离推挤、走流场（如果玩家给它下命令）、渲染层的贴图与朝向、
以及将来"母舰也能移动"的自由。`renderer.js` 里那套 bases/towers 通道继续留给"静止建筑"。

## 9. 参数归位：助推从全局下沉到小队（D8）

### 9.1 改动

| 位置 | 改法 |
|---|---|
| `squad-layer.js` `P_DEFS` | **+2 项**：`["boostSpeed", 0, 60]`、`["boostForce", 0, 45]`（默认值取自现在 `G` 的 60/45） |
| `squad-layer.js` `GLOBAL_PARAM_DEFS` | **−2 项**，只剩 `damping / mass / maxSpeedFactor / wallAvoidForce` |
| `group-layer.js` | `G.boostSpeed / G.boostForce` → `P.boostSpeed / P.boostForce` |
| `formation-templates.js` `FORMATION_KEYS` | **+2 项**，阵型从此是 15 个键 |
| `form.default.p` | **+2 项**（60 / 45），保证"不改阵型时行为与今天完全一致" |
| `applyFormation` | 改成"缺失的键不覆盖"（`if (v !== undefined) p[k] = v`），否则旧阵型（localStorage 里的用户阵型）会把 boost 写成 `undefined` |
| UI 全局参数卡片 | 自动少两项（读 `GLOBAL_PARAM_DEFS`） |
| 阵型参数面板 | 自动多两项（读 `FORMATION_PARAM_GROUPS`），归到"助推"分组 |

### 9.2 为什么值得改

- **母舰需要 `boostForce = 0`**，而"全局参数"是所有队共用的 —— 全局里关掉，全舰队都不动了；
- 关不掉就只能写 `if (u.isMothership)`，违反 D6；
- 顺带一个更好的性质：**助推不再是"所有队一样"，而是一个战术参数**。
  比如"散兵池游走得更积极、正规队更沉稳"从此是两份阵型数据，不用改代码。

### 9.3 兼容性

- 用户存档里的自定义阵型**不需要迁移**：缺 `boostSpeed/boostForce` 时沿用 `P_DEFS` 默认值
  （`makeParams()` 已经填了 60/45），`applyFormation` 的"缺键不覆盖"保证不会被写成 `undefined`。
- `force-model.smoke.mjs` 里把 boost 塞在 `G` 里传的若干用例要改成写进 `sq.p`。

## 10. 删除服从度 α（D11）

### 10.1 现状

`group-layer.js` 每帧为每个单位算一个"命令力在合力里的份额"：

```js
const cMag = Math.hypot(cx, cy), sMag = Math.hypot(sx, sy), bMag = Math.hypot(bx, by);
const a = cMag / (cMag + sMag + bMag + 1e-6);
u.alpha = a; sumAlpha += a;
if (a > 0.5) sumCmd++;
if (bMag > 1) sumCombat++;
return { alpha, cmd, nb, spd, combat };
```

### 10.2 为什么可以整个删掉

- `core.js:490` 调 `stepUnits(...)` 时**丢弃了返回值** —— `alpha / cmd / nb / spd / combat` 没有任何消费者；
- `u.alpha` 也没有读者（全项目只有 `u.alpha = a` 这一处写，渲染层的 `s.alpha` 是 sprite 透明度，无关）；
- 即它每帧在算四个 `hypot`、除一次、写两次字段，只为丢弃。

### 10.3 删哪些

| 删 | 保留 |
|---|---|
| `u.alpha` 字段（`core.js` 4 处初始化 + `squad-layer.js:236` 1 处 + 单测 helper） | `u.cAll`（每单位邻居数，留着调试用；不进返回值） |
| `u.alpha = a`、`sumAlpha`、`sumCmd`、`sumCombat`、`sumNb`、`sumSpd` | `sx/sy/bx/by/cx/cy/wx/wy` 的累加（力本身要用） |
| `const cMag/sMag/bMag` 与整个 `return {...}`（`stepUnits` 变成无返回值的副作用函数） | 分槽累加的注释（说明"哪条力进哪一槽"仍然重要） |

> 如果以后真要做"指挥服从度"面板，重新加一次即可 —— 现在的版本没有任何人依赖它。

## 12. 不变量（写测试就照着这张表）

1. 开局 `units` 里恰好有 2 艘 `radius === 40` 的船（每阵营一艘），各属一个 `motherShipSquad` 小队；
   该队 `loose === false`、`entries === [{ ship: "ship.std_ark", n: 1 }]`、默认阵型是 `form.mothership`。
2. `poolOf(faction)` 永远返回一个 `loose === true` 的散兵池；母舰小队（`loose === false`）不可能被误认。
3. 口的状态只在实例上：同一模板生成的两艘母舰，`u.ports` 是不同对象。
4. 每帧每个设施**最多**出货 1 艘。
5. `producing !== null` 时，只有该队的船能出货；其他队 / 散兵池的船原地等待。
6. staging 里的船一定还不在 `units` 里；`units` 里的船一定不在 staging 里（不重复、不丢失）。
7. 出货位置：到母舰中心距离 ≥ `radius + shipR + EXIT_GAP`，且不压墙。
8. 出货链路**不消耗随机数**：同 seed、同输入，两次运行的 `units` 坐标完全一致。
9. 出厂顺序 = staging 的 FIFO 顺序，且轮转口顺序 = `nextPort` 递增。
10. 扣费在入队时刻：模组立刻减、指挥值立刻按编制占满。
11. 口释放后，`last` 一定是"已死"或"已离开 ≥ 2r + PORT_CLEAR"。
12. `sq.goal` 存在 ⇒ rally 不产生任何力。
13. 母舰死亡 ⇒ **它那一份设施一起消失**（队列/待发区/出兵口）；该阵营其它母舰的设施不受影响。
14. 母舰小队 `boostForce === 0 && boostSpeed === 0`，静置 300 帧位移 < 1 px。
15. `u.alpha === undefined`，`stepUnits(...) === undefined`（α 已删干净）。
16. 对母舰小队发 `disband / setSquadCount / setFormation` 一律被拒（`isEditable(b) === false`）。
17. 母舰小队**可以**被选中、可以收到 `cmdSetGoal`；下信标后会朝目标移动，取消后停下。
18. `this.production.length === 场上活着的母舰数`（每帧由 `syncFacilities()` 保证），且每条 `fac.ownerUid === fac.owner.uid`。
19. `b.motherShipSquad` / `sq.motherShipSquad` 永远等于"该队编制里含 `hull.class === "mothership"` 的船"（派生缓存不许漂）。

## 15. 风险与待定

| 风险 | 说明 | 缓解 |
|---|---|---|
| **出厂节奏** | 一队 8 艘 = 7×0.2 ≈ 1.4 s；30 艘 ≈ 5.8 s；且期间该建筑拒绝第二支队 | `LAUNCH_GAP` 一个旋钮；口径上这是"部署成本"，与建造时间并列 |
| **建筑忙时被拒** | 玩家连点两次一键建队，第二次被拒 | 快照里有 `producing/producingLeft`，UI 上把按钮变灰并显示"出厂中 5" |
| **舰尾没有口** | 全部四口都在前半段，rally 在舰首方向 | 这是刻意的（避免绕舰）；口是数据，以后想加舰尾口再加一条 |
| **母舰漂移导致口/ rally 偏移** | rally 写入后不再更新 | 观感上"这支队在它出生的地方集结"，可接受；若要跟随，改成每帧刷新（但会拖着队走） |
| **一口被压住** | 船的出生点被友军/敌人占住 | `PORT_HOLD_CAP` 兜底 + 轮转到别的口 |
| **出口压墙** | 母舰贴着墙 | `findFreeSpawnPoint` 兜底；静息避墙力本来就会让母舰离墙 |
| **UI 认知** | 玩家看到 `0/8` 以为没造出来 | 必须显示"出厂中 n"，列进 V3 必做 |
| **旧测试全崩** | 删 α、boost 下沉、出场不再消耗随机数 | 逐用例复核；"同 seed 同战斗"仍成立，但旧录像/存档不兼容 |

**待定（需要拍板）**：

1. `stagingCap = 12` 是否合适（太大 = 产能可以无限囤；太小 = 一键建队会被自己的口卡住）。
2. 一键建队在出厂途中是否允许取消（目前建议：不允许，钱不退）。
3. 母舰被击毁是否判负（阶段一建议：不判负，只是少一份产能）。
4. **母舰的 `buildTime` 与 `capacity`**：现在 `buildTime = 0`（产线一帧造好）、`capacity = 10`（装两个插件就爆）。
   建议 `buildTime ≈ 300~600`（工时）、`capacity ≈ 24`。
5. **模组到底算阵营级还是母舰级**：本稿按"阵营级"写（`build.modules` 不动，改动最小）。
   若要做成"每艘母舰一个货舱"，`moduleCap / moduleRegen` 要一起下沉到设施 —— 那样"多母舰"会更强。
6. **单队母舰上限 1** 是否成立（`MAX_ARK_PER_SQUAD`）。要"母舰战斗群"就放开，但 UI 与设施归属要重想。
4. 母舰的 `sepForce` 要不要设 0（"推得动"还是"推不动"）。

## 16. 附录：为什么"一次性生成"必然爆（推导）

设一批 `N` 艘船挤在半径 `S = 55` 的圆盘内，全部 `v = 0`。

1. 分离触发条件是**表面间隙** `gap = d − (rᵢ + rⱼ) ≤ sepRadius`，
   即圆心距 `d ≤ 2r + sepRadius = 24 px`（`r = 6`）。
2. `N = 6` 均布时典型最近邻距 ≈ `0.5 × sqrt(πS²/N)` ≈ `20 px` < 24 —— **大多数邻居对都在分离区内**。
3. 每对的权重 `w = (sepRadius / gap)²`，`gap → 0` 时封顶 25，**封顶是 per-neighbor 的**。
4. 于是单艘船的合力 = `sepForce × Σw ≈ 50 × 5 × 25 = 6250 px/s²`。
5. 阻尼 `λ = 1.1` 下的稳态速度 ≈ `6250 / 1.1 ≈ 5700 px/s`，被 `maxSpeedFactor` 夹住 → 十几帧内满速。

而**分批出厂**把这个乘积里的 `Σw` 从"5 个满权重"压到"0 个"（相距 ≥ 2r + PORT_CLEAR）。
所以这不是"调小 sepForce"能解决的（调小会毁掉正常战斗的分离手感），
唯一正确的解法是**别让它们在同一时刻出现在同一个点上** —— 也就是"口"。
