# 小队机制：基于 Couzin 力的实现方案

**版本** v1.0 · 评审通过并修正后的设计文档
**前提** 底层为「软化 Couzin」：`F = w_sep·F_sep + w_ali·F_ali + w_coh·F_coh + ω·w_cmd·F_cmd`

---
我已经想到了如何基于这套couzin模型改造出 小队机制，以及小队的 “驻守区域、按路线进攻” 等指令；couzin模型本质上就是“给单位施加力”来控制单位；

那么小队机制的实现方式为，加入了小队的同一队的单位才会互相受到“吸引力”与“定向力”，非同队单位之间不计算吸引力与定向力；

未加入小队单位会对所有其余单位计算吸引力与定向力；而“命令力”则是分小队设置的；A小队不会受到B小队的命令力；

接下来讲小队的驻守区域、按路线进攻的实现方式：这两个指令都基于“命令力”实现、驻守区域是划定一片矩形或圆形区域，一旦小队超出区域范围，则会受到命令力的约束，使其移动回区域内；若已经在区域内，则不会受到命令力；进攻则是划定一条直线、弧线或折线线，使得命令力的命令点在线上面缓慢移动，使得小队中的单位追随这个命令点，以达到推进的效果；请你评审我的设计思路并落实为一篇新的文档
## 0. 总评

**方向是对的，而且比之前的"任务契约系统"好得多。**

它的好处在结构上：**小队不是一个新的系统，而是"力的作用域"的一次重划。** 不新增状态机、不新增阶段、不新增授权等级——只是决定"谁跟谁算邻居"。这符合我们一直在说的原则：复杂度沉到局部规则里。

但有 **5 处会在落地时变成硬伤**，另有 1 处隐患。以下先列结论，再逐条展开。

| # | 原设计 | 问题 | 修正 |
|---|---|---|---|
| **1** | 同队才计算「吸引 + 定向」 | **没说分离力怎么办**。若分离也按队过滤，不同小队会互相穿透、堆叠 | 分离力**始终全局**，并让跨队分离更强 |
| **2** | 驻守：出界才施加命令力 | 边界上是**开关式**力，单位会在边界反复穿越 → **边界抖动** | 力随穿透深度渐变，边界处为 0 |
| **3** | 驻守：区域内不施加命令力 | 区域内只剩社交力 → 部队**坍缩成一个球**，而不是"占住这片区域" | 区域内加弱槽位/密度松弛（可选层） |
| **4** | 进攻：命令点沿线移动 | 全队 seek 同一个点 → 走成**纵队或球**，不是宽正面推进 | 命令从「点」升级为**推进线**（垂直于路线的线段） |
| **5** | 进攻：命令点缓慢移动 | 命令点速度与部队速度**没有耦合** → 命令点独自跑到终点 | 速度**反馈自适应**（落后就减速） |
| 隐患 | 未入队单位对所有人算吸引/定向 | 它们会形成一个隐形的"超级队"，被拉向**全场质心** | 改为"最近友军"或直接不聚合 |

## 1. 核心抽象：小队 = 力的作用域过滤器

这是整个设计的支点。一条力属于哪个作用域，决定了它表达什么：

| 力 | 作用域 | 它表达什么 | 若作用域搞错会怎样 |
|---|---|---|---|
| **分离** | **全局** | 体积、碰撞 | 队友可叠、跨队可穿模 |
| **对齐** | 同队 | 协同、齐步 | 全场合流、失去队形 |
| **凝聚** | 同队 | 归属、队形 | 全场合流、小队消失 |
| **命令** | 同队 | 意志 | 命令泄漏、A 队听 B 队的令 |
| 地形/边界 | 全局 | 物理 | 穿墙 |

### 1.1 为什么分离必须全局

原设计只规定了"吸引与定向同队"，没提分离。三种可能，只有一种对：

| 方案 | 后果 |
|---|---|
| 分离也按队过滤 | **两支队伍可以完全重叠**，视觉上糊成一坨。单位互相穿插，`-(dx/d)` 方向病态 → 抖动加剧 |
| 分离全局，权重一致 | 正确。两队互相推开，各自保持形状 |
| **分离全局，跨队更强**（推荐） | 自己人允许挤（紧密队形），外队保持距离（不纠缠）。 |

推荐实现：

```js
const w = sepW(d, rRep) * (o.squad === u.squad ? 0.85 : 1.35);
```

一个顺带的收益：这条规则让"不同小队不会混成一团"成为**物理结果**，不需要额外的排斥规则。

### 1.2 「未入队单位对所有人计算" → 建议修改

原规则会让所有散兵收敛到**全场质心**，形成一个隐形的超级小队。三个问题：

1. 有敌人时，散兵会被拉向**包含敌人**的质心；
2. 玩家看不出这支部队到底听谁的；
3. 散兵被拉向"大部队"而不是"最近的友军"，战术上不合理。

**建议**：未入队单位的凝聚/对齐作用域改为 **「最近的小队」**（动态继承），或干脆**不参与凝聚**，只保留分离与命令。

```js
const scope = u.squad ?? nearestSquadId(u.pos, 400);  // 400px 内最近的小队
```

这样"掉队单位会自动被最近的队伍吸走"，语义更好，也顺带实现了"残兵归队"。

## 2. 命令力按小队分发

原设计正确，无需修改。需要补的是**数据组织方式**：

```js
Squad {
  id:       int,
  color:    string,
  members:  Set<unitId>,
  order:    HoldOrder | AdvanceOrder | null,
  center:   Vec2,     // 每帧重算，供速度反馈与 UI 使用
}
```

每个单位每帧只问自己所属小队要一个 `(dir, strength)`：

```js
const o = squads[u.squad]?.order;
const { dir, strength } = o ? o.sample(u.pos) : { dir: 0, strength: 0 };
Cx += (ω * wCmd * strength) * (dir.x * SPD - u.vx);
Cy += (ω * wCmd * strength) * (dir.y * SPD - u.vy);
```

**关键点：`strength` 是 0~1 的连续量，不是"有/无"。** 上面第 2 条修正就落在这里。

## 3. 驻守区域

### 3.1 原设计的问题

> "一旦小队超出区域范围，则会受到命令力约束；若已在区域内，则不会受到命令力"

这是一个**开关式（bang-bang）力**：

- 单位越过边界 → 突然受到满幅拉回力；
- 被拉回 1px 进入区域 → 力瞬间归零；
- 但分离力仍在把它往外推 → 又出界 → 力再次出现。

结果：**一圈单位在边界上持续微抖**。这正是我们刚诊断过的极限环，只不过这次是命令力制造的。

### 3.2 修正：符号距离场 + 软墙

```js
// 区域内为负，区域外为正
d = sdf(pos)                     // sdf: signed distance field

if (d <= 0) {
  strength = 0;
} else {
  strength = smoothstep(0, MARGIN, d);   // 边界处 0，深出 MARGIN 后满幅
  dir = normalize(grad(sdf, pos));       // 指回区域内最近点
}
```

`MARGIN ≈ 0.5 × r₁ ~ 1.5 × r₁`（推荐从 `rRep` 起步）。

**几何的 sdf 都很便宜：**

| 形状 | sdf |
|---|---|
| 圆 `(c, r)` | `|p−c| − r` |
| 轴对齐矩形 | `max(|p−c|−half, 0)` 的长度（外）+ 内距离（内） |
| 有向矩形 | 先把 `p` 旋到局部坐标，再用上式 |

`grad` 对圆是 `(p−c)/|p−c|`，对矩形是"到最近边/角的单位向量"，都不需要数值微分。

### 3.3 必须解决的第二个问题：区域内坍缩成球

按原设计，进入区域后命令力归零，剩下的只有社交力 → **凝聚把所有人收到一个点上**。玩家看到的是"一坨球停在区域中央"，而不是"占据这片区域"。

两级方案，按需选用：

**Level 1（最小可用）** — 接受成球，把区域当作"集结区"。
配合"区域内提高 `w_sep`"可以让球松一点，但仍然是球。

**Level 2（面状覆盖）** — 引入**驻守槽位**：

```
1. 区域生成时，用泊松盘采样出 k 个哨位（k ≈ 兵力 / 3）
2. 每个单位分配最近哨位（每 0.5s 一次，带滞回）
3. 命令力 = 指向"自己的哨位"，但仍然只在区域外才生效
   —— 区域内也施加一个很弱的槽位力（strength ≤ 0.25）
```

这样才叫"驻守"，而不是"扎堆"。

> 注意：L2 的槽位力**必须弱**。一旦它足够强，就会出现我们之前讨论过的"结构固化"——部队变成钉子，永远不会因战斗而变形。

### 3.4 一个额外的好处

软墙方案自带"边界包容性"：**部队被打散出界后会自动慢慢游回来**，不需要"回归"指令。这比硬边界更耐打。

## 4. 路线进攻

### 4.1 原设计的最大问题：命令点是"点"

> "划定一条直线、弧线或折线，使得命令力的命令点在线上面缓慢移动，小队单位追随这个命令点"

全队 seek **同一个点**，结果必然是**纵队**（所有单位挤向一点，被分离力摊成一条线），或者到一个点上聚成球。

这不是"进攻"，这是"行军"。

**修正：命令不是点，是一条垂直于推进方向的线段。**

```
Front {
  center: Vec2,      // 推进线中点（沿路径前进）
  tangent: Vec2,     // 路径切线 = 推进方向
  normal:  Vec2,     // 垂直 = -tangent 旋转 90°
  width:   number    // 阵面宽度
}
```

每个单位追的不是 `center`，而是**自己在推进线上的投影点**：

```js
const off = clamp(dot(p - center, normal), -width/2, +width/2);
const goal = center + normal * off;      // 单位正前方的那一点
dir = normalize(goal - p);
```

效果：整个小队像一条**横扫的横线**向前压，宽度由 `width` 控制，单位不会互相挤到中间。

> **两种模式都要有，因为它们是两种战术：**

 | 模式 | 命令目标 | 产生的队形 | 用途 |
 |---|---|---|---|
 | **横线 Front** | 推进线上的投影点 | 宽正面 | 正面进攻、压线 |
 | **纵队 Column** | 单个命令点 | 纵队 / 长蛇 | 穿插、过窄口、行军 |

急转弯时 `normal` 会快速旋转 → 需要限制它的角速度（`≤ 2~3 rad/s`），或者允许它"切角"（内部弯道走弦而不是弧）。

### 4.2 第二个问题：命令点速度与部队速度没有耦合

如果命令点按固定速度走，部队一旦被地形、敌人、分离力拖慢，命令点会**独自跑到终点**，留下一支永远追不上的部队。

必须做**反馈调速**：

```js
gap  = dot(center - squad.center, tangent);   // 部队重心落后命令点多少
vCmd = vBase * clamp(1 - (gap - gapTarget) / gapWindow, 0.15, 1.6);
```

- `gap` 大（部队落后）→ 减速等它；
- `gap` 小甚至为负（部队追上了）→ 加速拉开。

`gapTarget ≈ 0.5 × width`，`gapWindow ≈ 2 × width`。

**更稳的替代方案**：命令点不自己走，而是"始终保持在部队重心前方 `gapTarget` 处"。这样永远不会脱节，但失去了"按计划速度推进"的语义。两者可以按键切换（`Auto` / `Fixed`）。

### 4.3 路径参数化

```
折线 → 弧长重采样（等距点）→ 切线表 → 曲率表
```

- **弧长重采样**是必需的，否则直线段的采样密度和弧线段不一致，速度会跳。
- **曲率**决定 `normal` 的最大旋转速率：`ω_max = v × κ`。
- **端点**：起点用 `smoothstep` 淡入命令力，终点前 `0.5×width` 距离开始减速，停下后自动转为驻守（或交给下一个 order）。

### 4.4 到终点之后做什么

要明确定义，否则部队会在终点原地聚团。

推荐：`AdvanceOrder` 自带一个可选的 `onArrive: HoldOrder | null`。
- 有 → 自动切驻守（"推进到这座桥然后守住"是一条完整的战术）；
- 无 → 命令力归零，部队自然散成球。

## 5. 统一抽象：命令 = 目标场

驻守和进攻看起来是两件事，但对单位层来说**只有一件事**：

```js
interface GoalField {
  sample(pos): { dir: Vec2, strength: number };   // strength ∈ [0, 1]
}
```

| 指令             | 场的构造                                                                               |
| -------------- | ---------------------------------------------------------------------------------- |
| **驻守圆/矩形**     | `d = sdf(pos)`；`strength = d > 0 ? smoothstep(0, MARGIN, d) : 0`；`dir = grad(sdf)` |
| **进攻（横线）**     | 路径投影得到 `Front`；`strength = 1`（或端点淡入淡出）；`dir = normalize(投影点 − pos)`                |
| **进攻（纵队）**     | 同上，但 `goal = center`                                                               |
| **集结 Regroup** | `dir = normalize(anchor − pos)`；`strength = min(1, dist / R)`                      |

**收益**：单位层的代码永远只有一段，新增指令 = 新增一个场。这与"命令是意图不是坐标"的原则一致。

## 6. 小队身份从哪来（待定）

原设计说"加入了小队的单位"，但没定义谁分配。三种来源，建议并存：

| 来源 | 做法 | 风险 |
|---|---|---|
| **玩家显式建队** | 框选 → 新建 Squad → 绑定数字键 | 无（推荐做主力） |
| **合并** | 框选多个单位加入现有 Squad | 无 |
| **自动识别（可选）** | DBSCAN + 锚点匹配 | **身份不稳定会放大抖动**（见下） |

**必须提醒的一点**：一旦"同队才受凝聚力"，小队身份就从"UI 标签"变成了**力场的边界**。身份抖动不再只是"徽章闪一下"，而是**单位在两种力场之间来回切换** → 直接表现为抖动。

> 所以：**自动识别只能作为「建议」，不能作为「事实」。**
> 玩家确认后才写入 `squadId`。这一步不能省。

## 8. 性能

| 项 | 代价 |
|---|---|
| 作用域过滤 | 邻居循环里多一次 `int` 比较，可忽略 |
| `GoalField.sample` | 圆形/矩形 O(1)；路径 O(log n) 或 O(1)（用弧长索引） |
| 小队重心 | 每队每帧一次遍历，O(总单位数) |
| 带宽 | 无（命令是广播常量，与"知情者机制"不冲突，可后加） |

结论：这套机制**不会带来可感知的性能成本**，因为它只是给现有的力加了几个条件。

## 9. 验收指标

### 驻守

| 指标 | 判据 |
|---|---|
| 进入时间 | 命令下达后 **< 3 s** 90% 单位入界 |
| 稳态越界率 | **< 5%** |
| **边界抖动** | 稳态单位位置的**高频能量**低于行进时的 50%（这条最重要，专门防第 2 条修正漏做） |
| 面状覆盖（L2） | 最近邻间距 ≥ `0.8 × 期望间距`，且不出现半径小于 `2×r₁` 的核心团 |
| 抗推挤 | 另一队经过后 2 s 内恢复到原区域 |

### 进攻

| 指标 | 判据 |
|---|---|
| 阵面宽度保持 | `width ± 20%`（横线模式） |
| 队列不脱节 | 最落后单位与命令点的距离 **< 1.5×width** |
| 到达时间 | 与设定速度的偏差 **< 15%** |
| 命令点不跑飞 | 命令点与部队重心的距离始终 **< 3×width** |
| 曲率适应 | 90° 急弯处不出现"甩尾"（最外侧单位滞后 < 1 width） |

## 10. 风险与待定项

| 风险 | 说明 | 建议 |
|---|---|---|
| 驻守被推挤变形 | 分离是全局的，路过的队伍会挤压驻守部队 | 提高驻守中的单位"质量"（降低被推开比例），或让驻守单位 `w_sep` 略高 |
| 多小队视觉混乱 | 5 队以上颜色难分辨 | 队色 + 单位描边 + 悬停高亮整队 |
| 自动识别放大抖动 | 身份是力场边界，抖动会变成物理抖动 | 只做"建议"，玩家确认 |
| 命令点走走停停 | 反馈增益调不好会震荡 | `vCmd` 加一阶低通（`τ ≈ 0.3s`） |
| 有向矩形的 sdf | 旋转矩形的内外距离易写错 | 先只做圆 + 轴对齐矩形 |
| 跨队分离权重 | 0.85 / 1.35 是拍脑袋值 | 用"两队对冲"场景扫参数 |

---

## 11. 一句话总结

> **小队不是新系统，是"力的作用域"的一次重划：分离归物理（全局），吸引与定向归身份（同队），命令归指挥（按队分发）。**
> 驻守与进攻也不是新系统，而是目标场的两种构造：一个是"排斥出界"，一个是"吸向推进线"。
> 唯一需要小心的是：**凡是开关式（0/1）的力，都会变成抖动**——所以软墙要渐变、身份要玩家确认、命令点速度要反馈。
