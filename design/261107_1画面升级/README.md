## 0. 约束（先说清楚边界）

这三条是从现有玩法里来的，它们决定了架构能怎么选：

| 约束        | 含义                                |
| --------- | --------------------------------- |
| **全屏可见**  | 没有摄像机滚动，双方基地 + 整个战场必须一屏放下         |
| **单位小且多** | 单场 200~400 个单位，单个单位目前约 14px       |
| **要上手机**  | 同一套资产要从 1693×733 缩到 390×844 还能认得出 |

结论：**像素不能靠"放大"得来**。经典像素游戏（320×180 渲染后放大 4 倍）在手机上会把
单位放到 40px 以上，一屏塞不下 400 个单位。所以我们的像素密度必须跟着屏幕走，
像素颗粒大小由屏幕决定，而不是固定虚拟分辨率。

真正要控制的不是"多少像素"，而是"**每个像素是不是方的、大小是不是一致**"。

## 1. 五条早期决策

### D1 · 像素是"投影"，不是模拟单位

模拟层继续用浮点世界坐标（`u.x = 312.47`），**渲染器负责把它量化成整数像素**：

```js
// 只在这里发生取整，模拟层永远不知道"像素"这回事
const sx = Math.round((u.x - cam.ox) * cam.zoom * dpr) / dpr;
```

好处：

- 群体行为、武器判定、差分测试全部不用改（10 组测试是换渲染时的保险）
- 量化只影响观感，不影响碰撞/寻敌，不会出现"像素对齐导致命中判定漂移"
- 想调像素颗粒大小，只改渲染器一个参数

**反例**（不要这么做）：把 `u.x` 改成整数、把 hitR 改成整像素。那会把渲染细节
泄漏进模拟层，之后每个武器/群体参数都要跟着像素网格走。

### D2 · 缩放用整数，量化到设备像素

现在是 `ZOOM = 1.2`。分数缩放 + 最近邻 = **像素颗粒大小不均**（一个源像素有时占 1 个屏幕像素，
有时占 2 个），静态看还行，动起来会"呼吸"。

建议：

| 方案 | 做法 | 评价 |
|---|---|---|
| A（推荐） | `ZOOM` 取 **1 或 2**，每个精灵坐标 `Math.round` 到设备像素 | 最简单，颗粒绝对均匀 |
| B | 世界画到低分辨率 RT，再整数放大 | 整屏均匀，但文字/UI 要单独处理，且多一次全屏 blit |
| C | 保持分数缩放，靠 `imageSmoothingEnabled=false` | 便宜，但颗粒不均，**不建议** |

选 A。代价：单位视觉尺寸会变一点（`ZOOM 1.2 → 1`，14px 的船变成 14px 而不是 16.8px），
但这正好是像素风想要的"小格子"感。

设备像素比也要整数化：

```js
const dpr = Math.max(1, Math.round(window.devicePixelRatio || 1));
canvas.width  = W * dpr;           // 后备缓冲按设备像素
canvas.height = H * dpr;
ctx.setTransform(dpr, 0, 0, dpr, 0, 0);   // 逻辑坐标仍是 CSS px
```

这样"1 个艺术像素 = 1 个设备像素"，在 DPR=1 的桌面上就是 1:1，在 DPR=3 的手机上
每个艺术像素占 3×3 设备像素 —— 手机上天然更"粗"，正是想要的。

### D3 · 连续旋转，不量化角度

**为什么不量化**：单位的朝向 = 速度方向，而群体行为（Couzin / boids）是全队沿同一条
平滑弧线转向的。把角度吸到 16 档，编队转向时精灵会一格一格地"咔哒"——
这恰好毁掉涌现感最直观的那一部分（"鸟群在拐弯"）。

所以角度必须连续，直接：

```js
sprite.rotation = Math.atan2(u.vy, u.vx);   // 不取整、不分档
```

**代价**：最近邻旋转会让边缘"爬行"（像素随角度变化时明灭）。这是允许旋转的
必然结果，而且**不能用取整消除——因为一旦取整就是量化**。接受它。

**不消除，而是让它不显眼**，四条实际有效的做法：

| 做法 | 说明 |
|---|---|
| `imageSmoothingEnabled = false` | 必须。开了平滑就是"低分辨率图片在转"，不是像素在转 |
| **位置**量化、**角度**不量化 | 半像素位置才是抖动的主因；角度保持连续 |
| 精灵用偶数边长（16 / 20 / 32） | `-w/2` 是整数，旋转中心落在像素边界上，不会整体偏半个像素 |
| 美术上：2px 最小特征、1px 深色描边、明确的前向轮廓 | 1px 细线转起来会碎成点；有轮廓的剪影怎么转都认得出 |

**顺带一个结论：连续旋转比"旋转缓存"更省。**

- Canvas2D：每帧 `drawImage` 400 次完全没问题（比现在每个单位画 3~5 次 path 还便宜）
- Pixi：`sprite.rotation = a` 是顶点变换，零成本

所以**不需要旋转缓存模块**。`art/tint.js` 只缓存"灰阶源图 → 阵营配色"这一层
（按阵营，18 个位图，与角度无关）。

### D4 · 灰阶源图 + 运行时染色

阵营只改配色、形状完全一样。所以：

- 图集里单位/建筑只存**一套灰阶（或白色蒙版）**
- 载入时按阵营生成 2 套着色位图（Canvas 上 `source-in` 填充或预生成 LUT）
- 后续 `受击闪白 / 护盾泛蓝` 都走同一个染色通道

这样素材量直接减半，而且不用给 Canvas2D 写 shader。

### D5 · 特效分两类处理

| 类型                     | 现在                | 像素化后                                                |
| ---------------------- | ----------------- | --------------------------------------------------- |
| **几何型**（激光、轨道炮光束、护盾连线） | `ctx.lineTo` + 渐变 | **Bresenham 像素线**：算必掉 `lineTo`，自己打点，2px 亮芯 + 1px 外框 |
| **贴图型**（爆炸、命中火花、枪口焰、烟） | 渐变 + 圆            | **序列帧精灵**：6~10 帧，26×26 或 32×32                      |

像素风里"发光"不靠渐变，靠：**同心色带 + 抖动（dither）**，或者接受一层
"加色软光"叠在像素画上（现代像素游戏普遍这么做，见 §7 的光照层）。

## 2. 分层：模拟 → 艺术适配 → 渲染后端

```
┌─────────────────────────────────────────────────────┐
│ 模拟层  units / squads / projectiles / fx  (浮点)    │
└───────────────┬─────────────────────────────────────┘
                │ view（只读投影，契约见 renderer.js）
┌───────────────▼─────────────────────────────────────┐
│ 艺术适配层  art/                                     │
│   · 对象 → 精灵描述（纹理名 / 帧 / 方向 / 染色 / 层） │
│   · 纯函数，无 canvas、无 Pixi                       │
│   · 两个渲染后端共用这一层                            │
└───────────────┬─────────────────────────────────────┘
                │ sprite desc
┌───────────────▼─────────────────────────────────────┐
│ 渲染后端  renderer-canvas2d.js  |  renderer-pixi.js  │
│   · 加载图集、管理批次、执行绘制                      │
└─────────────────────────────────────────────────────┘
```

关键点：**共享"对象→精灵"的映射，不共享绘制**。

映射函数长这样（纯函数，可单测）：

```js
// art/sprites.js
export function unitSprite(u, sq) {
  return {
    tex: "unit/" + (sq.art || "default"),   // 纹理名（只有 1 张，不按方向拆）
    rot: Math.atan2(u.vy, u.vx),            // 直接给角度，渲染器负责量化 + 查缓存
    tint: sq.faction,                       // 阵营染色
    layer: LAYER.UNIT,
  };
}
```

角度不进精灵描述也没关系——渲染器每帧从 `vx/vy` 自己算也行。关键是
**"量化 + 缓存"发生在渲染器/缓存层，不在 `art/sprites.js`**，
这样映射函数保持纯函数、可单测，缓存策略可以单独换。

为什么不搞"绘制指令流"（先构建一个 draw-command 数组再执行）：
每个对象每帧一条指令 = 每秒 2.4 万次分配。等真的出现第三个后端、或者要做
"渲染与模拟分线程"时再引入，并且必须配对象池。现在不值得。

## 3. 尺寸预算

以 `ZOOM = 1`、桌面 1693×733 为基准（战场约 1400×590 艺术像素）：

| 对象 | 艺术尺寸 | 说明 |
|---|---|---|
| 单位（小船） | **16×16** | 三角/箭头轮廓，**1 张，靠旋转动画** |
| 单位（要塞） | **20×20** | 比小船大一号，一眼能分出来 |
| 空间站 | **96×96** | 外环建议拆成独立环带单独转，内核不转 |
| 防御塔 | **40×40** | 静止，6 个发射器用帧/染色呼吸 |
| 导弹 / 鱼雷 | 8×8 | 1 张，靠旋转 |
| 链炮弹 | 4×2 | 不分方向，就是一道亮痕 |
| 爆炸 | 32×32 × 8 帧 | |
| 命中火花 | 16×16 × 4 帧 | |
| 枪口焰 | 16×16 × 3 帧 | |
| 护盾环 | 24×24 | 无方向，染色 |

素材量估算（按 D4 灰阶源图 + D3 连续旋转，**全部不按方向拆**）：

| 类别 | 帧数 |
|---|---|
| 单位 6 种 × **1 张** | **6** |
| 空间站 96×96（内核 1 + 外环 1） | 2 |
| 防御塔 40×40（1 底 + 灯闪烁 3 帧） | 4 |
| 弹丸 3 种 × **1 张** | 3 |
| 特效 4 套序列帧 | 25 |
| **合计** | **≈ 40 帧** |

比"8 方向"方案（120 帧）少三分之二，而且**新增单位类型只要画 1 张**——
这正是允许旋转换来的最大好处：内容扩展成本是常数，不是 ×8。

一个 256×256 的图集（或 512×512）就装得下。**这是可控的工作量**，不需要美术外包。

## 4. 调色板

每阵营一套 8 色阶梯 + 4 个中性色：

```
中性： #0a0f16 (底)  #1d2a38 (暗)  #4a5f75 (中)  #dbe6f0 (亮)
蓝方： #1b3a5c → #2f6ea8 → #5fa8e8 → #a8d8ff → #e8f6ff
红方： #4a1e1e → #8f3a32 → #e8614f → #ff9d8a → #ffe0d8
```

规则（像素风三条铁律）：

1. 同一色相**不超过 5 阶**，多了就"脏"
2. 不用纯黑纯白（`#000` / `#fff` 只在特效芯部用）
3. 描边用本阵营最暗一阶，不用黑色描边（黑色描边会让单位在暗背景上消失）

染色实现：源图集是灰阶（0~255），载入后按"亮度 → 调色板索引"映射生成两套位图。
这样"闪白"= 直接画全亮版，"受击变暗" = 画最暗一阶，都是零成本查表。

## 5. 绘制顺序（layer）

一次绘制按层走，每层内部尽量同纹理成批：

| 层 | 内容 | 混合 |
|---|---|---|
| 0 | 战场背景（星云/网格/暗角） | normal |
| 1 | 地面光环 / 基地光圈 | **add** |
| 2 | 单位阴影（1px 偏移的暗色剪影） | normal |
| 3 | 单位 | normal |
| 4 | 弹丸 + 拖尾 | add |
| 5 | 特效（爆炸/火花/光束） | add |
| 6 | 血条 / 护盾环 | normal |
| 7 | 光照层（可选，P3 之后） | multiply/add |

`add` 层在 Canvas2D 里用 `globalCompositeOperation = "lighter"`，在 Pixi 里用
`BlendMode.ADD`。注意：**加色层也要按像素网格画**，否则会出现半透明模糊边，
和像素主体不搭。

没有旋转缓存模块：角度连续，缓存只可能按角度量化，与 D3 矛盾。

## 7. 迁移路线（每步都能停）

| 步 | 内容 | 产出 | 估算 |
|---|---|---|---|
| **S1** | `pixel.js` + 像素化外壳：`ZOOM` 改 1、绘制坐标量化（DPR 已完成） | 现有矢量图形变成"硬边"，观感立刻变 | 半天 |
| **S2** | 单位换精灵：6 种单位各 1 张图 + 连续旋转 | 单位是像素、建筑还是矢量 | 2~3 天 |
| **S3** | 建筑换精灵（空间站 96×96、塔 40×40），外环建议拆成独立层单独转 | 主体全像素 | 2~3 天 |

后面 4 步都不用做 —— 这是最便宜的一次试错。

## 8. 对现有 `WorldRenderer` 契约的影响

接口不用改（`resize` / `draw(view)` / `destroy`），但 `view` 要扩字段：

| 新增 | 用途 | 谁提供 |
|---|---|---|
| `sq.art` | 战斗群的精灵名（`swarm`/`anvil`/…） | `templateDef()` 里加一行 |
| `base.artId` / `tower.artId` | 建筑精灵名 | `makeBase` / `buildTowers` |
| `dpr` | 设备像素比（整数化后） | 页面 |
| `palette` 或 `factionTint[2]` | 阵营染色表 | `art/palette.js` |

**不需要**新增的：方向/角度（渲染器从 `vx/vy` 自己算，或从 `art/sprites.js` 的
`rot` 字段拿）、动画计时（用 `pulse` / `combatT`）。

## 9. 待定问题

1. **旋转的观感能不能接受** —— 连续旋转 + 最近邻，慢速转的时候边缘会爬行。
   这是 D3 唯一的风险点。S2 拿 2~3 种单位试一眼：如果接受不了，唯一出路是
   **提高源图分辨率**（32×32 画 16×16 的船，细节翻倍），而不是改回量化
2. **空间站外环拆不拆** —— 96×96 整体转，外环和内核在同一个精灵里。
   拆成独立环带单独转，可以让"外环慢转、内核不动"，观感更像机械结构。
   S3 时按实际素材定
3. **要不要"像素级"碰撞** —— 现在的命中判定是圆形扫掠，和像素外观无关。
   建议**不要**改（D1），否则武器测试全部作废
4. **血条**：继续画矢量圆角条，还是做成像素条（2px 高、锯齿边）？倾向后者，但要
   和 UI 层的整体风格一起定
5. **字体**：UI 文案要不要换像素字体（如 Zpix / Fusion Pixel）？和 React 化的时机绑定

## 附录 A · 现状体检（2026-11-07 实测）

做设计前先在页面上量了一遍，有两个数字直接影响决策：

### A.1 画布一直在被浏览器上采样（已修）

| 项 | 修前 | 修后 |
|---|---|---|
| 后备缓冲 | 1693×773（= CSS px） | **1862×850**（= 设备像素） |
| 设备上是 | 1862×850 | 1862×850 |
| 结果 | 浏览器按 1.1× 双线性放大，**整屏是糊的** | 1:1，像素与线条清晰 |

`devicePixelRatio = 1.1`（Windows 110% 缩放）。修法是 `renderer.resize()` 里按
设备像素分配后备缓冲、每帧 `setTransform(dpr, 0, 0, dpr, 0, 0)`，绘制坐标继续用 CSS px。
UI 层同理。

**这件事必须在像素化之前做**：像素风的全部意义在于"像素是硬的"，
而后备缓冲不匹配会让每个像素都被插值一次，怎么画都不会硬。

### A.2 渲染开销（满编 405 单位）

| 状态 | 整帧 p50 | 纯渲染 p50 |
|---|---|---|
| 修前（1693×773 缓冲） | 2.6 ms | 2.8 ms |
| 修后（1862×850 缓冲） | **3.4 ms** | **3.3 ms** |

多填 21% 的像素，代价 +18%，仍然是 60fps 预算（16.6 ms）的 **20%**。
结论：现在的 Canvas2D 还有 5 倍余量，像素化本身不会让它变慢——
变慢的是后面加的光照层和粒子，那才是换 Pixi 的理由。
