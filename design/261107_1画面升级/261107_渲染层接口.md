# 渲染层接口（世界层 / UI 层分层）

日期：2026-11-07
对应代码：`prototype/js/renderer.js`、`prototype/js/renderer-canvas2d.js`、`prototype/plinko-battle.html`

## 1. 为什么要做这一步

现在画面是 Canvas 2D 手画的矢量图形。往后要加的是 **shader、光照、更复杂的特效**，
Canvas 2D 在原理上做不了（没有可编程管线）。所以渲染层迟早要换成 WebGL/WebGPU 方案
（PixiJS 是候选）。

但"换渲染器"最怕的不是图形 API，而是**图形代码和游戏逻辑长在一起**：
一旦某个绘制函数顺手改了 `u.hp`，或者某段逻辑顺手 set 了 `ctx.fillStyle`，
换引擎时就得把整个游戏重读一遍。

所以先做一件不起眼但决定后面成本的事：**把"画什么"和"用什么画"切开**。

## 2. 分成两层

```
┌──────────────────────────────────────────────┐
│ #ui 画布（UI 层）                             │  侧栏 / 落球机 / 战斗群介绍 /
│   screen 坐标，pointer-events: none           │  战况行 / 自动出兵 / 胜负提示
├──────────────────────────────────────────────┤
│ #c 画布（世界层，渲染器独占）                  │  战场边框 / 空间站 / 防御塔 /
│   world 坐标，camera 变换在渲染器内部处理       │  单位 / 特效 / 弹丸
├──────────────────────────────────────────────┤
│ 模拟层（无 DOM、无 canvas、可在 Node 里裸跑）  │  unit / squad / weapon / fx
└──────────────────────────────────────────────┘
```

**为什么 UI 要单独一张画布**：将来渲染器换成 Pixi，它会独占自己的 WebGL canvas，
Canvas 2D 的 UI 就画不上去了。UI 层先独立出来，之后无论是继续用 2D canvas，
还是换成 React + DOM，都不影响世界层。

**输入仍然挂在 `#c` 上**：`#ui` 设了 `pointer-events: none`，
所以指针事件穿透到底层，现有的命中测试代码一行没改。

## 3. 接口契约

```js
export class WorldRenderer {
  resize(width, height) {}   // 屏幕尺寸（CSS px）变了
  draw(view) {}              // 画一帧，view 只读
  destroy() {}               // 释放 GL 资源 / 纹理引用
}
```

`view` 的形状：

| 字段 | 说明 |
|---|---|
| `width` / `height` | 屏幕尺寸（CSS px） |
| `camera` | `{ ox, oy, zoom }`，世界 → 屏幕：`screen = world * zoom + o` |
| `world` | `{ w, h }` 战场世界尺寸（画边框用） |
| `bases` / `towers` | 基地、塔。**自带 `hue` / `radius` / `pulse`** |
| `units` / `squads` | 全部单位、小队表 |
| `fx` / `projectiles` | 特效、飞行弹 |

三条硬规矩，和空间索引层是同一个思路：

1. **只读 view** —— 渲染器不回写任何游戏状态，也不保存对数组的引用（下一帧会就地增删）
2. **不碰 ctx** —— 接口里没有 `CanvasRenderingContext2D` 字样，Pixi 实现自己管 GL
3. **不读配置** —— 色相、半径由调用方写进数据对象（`base.hue` / `base.radius`），
   渲染器不 import `TOWER_CFG` 之类的游戏参数表

第 3 条的实际作用：将来 Pixi 版可以直接把 `hue` 拿去当 sprite 的 `tint`，
把 `radius` 拿去定缩放，不需要在渲染器里复制一份阵营配色逻辑。

## 4. 这一层**不**管什么

- **不布局**：`SIDE`、`FW/FH`、`board` 的位置都还是页面算的，渲染器只画
- **不输入**：命中测试仍在页面里
- **不做 UI**：侧栏、按钮、图例、胜负文字全在 UI 层
- **不写状态**：哪怕"血条要不要显示"这种判断，也是读数据（`hp < maxHp`）而不是改数据

## 5. 换成 Pixi 时要动哪里

只用改两处：

```js
// plinko-battle.html
import { createCanvas2DRenderer } from "./js/renderer-canvas2d.js";
const renderer = createCanvas2DRenderer(cvs);
```

换成

```js
import { createPixiRenderer } from "./js/renderer-pixi.js";
const renderer = await createPixiRenderer(cvs);   // Pixi v8 的 init 是异步的
```

模拟层、UI 层、测试一行不动。Pixi 实现里要做的事：

| 现在的绘制 | Pixi 里的对应 |
|---|---|
| `drawUnitGlyph` 三角形路径 | 池化的 `Sprite` + hash 纹理，按 `squads[u.squad].hue` 调 tint |
| `glowDot` 径向渐变 | 预渲染的软光贴图 + `BlendMode.ADD` |
| `drawFx` 的 beam / blast / spark | 池化的 `Graphics` 或几张序列帧 |
| 战场边框 | 一个 `Graphics`，`camera` 变了就重设 `stage.position/scale` |
| 血条 | `Graphics` 或 9-slice sprite |

关键点：**渲染器内部要做对象池和差量同步**（上一帧有多少单位、这一帧新增/删除哪些），
这是 Pixi 实现的真正工作量，也是为什么要把接口先定好。

## 6. 验收标准（这次改动）

- 画面像素级不变（同一个相机、同一套绘制调用，只是搬了位置）
- 输入不变（悬停光标、点色标出兵、自动出兵开关都正常）
- 性能不变：满编 ~400 单位时整帧 p50 ≈ 2.6 ms、纯渲染 ≈ 2.8 ms（60fps 预算 16.6 ms）
- 测试不变：`spatial.test.mjs` / `structures.test.mjs` 全过（模拟层没被碰）
